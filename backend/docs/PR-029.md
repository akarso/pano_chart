# PR-029 — Ranking Percentile Normalization (Backend)

## Goal

Introduce stable percentile-based normalization for ranking results.

Purpose:

* Improve interpretability of ranking scores
* Avoid misleading frontend min/max stretching
* Preserve cross-page and cross-session consistency
* Keep visualization independent from ranking logic

This PR does NOT change ranking algorithms.
This PR adds distribution context.

---

# Problem

Current state:

* Each algorithm outputs raw score in [0, 1]
* Distributions differ dramatically across algorithms

  * Sideways may cluster around 0.6–0.9
  * Trend may cluster around 0.01–0.08

Result:
Raw scores are mathematically normalized but not distribution-normalized.
Users may misinterpret small raw values as "weak" even when they are relatively strong.

Frontend stretching per-page is NOT acceptable because:

* Breaks pagination stability
* Causes layout shifts with infinite scroll
* Makes identical scores appear different across requests

---

# Solution Overview

Compute percentile rank per symbol within the full ranked universe for the current request.

For each ranking response:

1. Compute raw scores for all symbols (existing behavior)
2. Sort descending by selected sort mode (existing behavior)
3. Compute percentile for each symbol based on its rank position
4. Return percentile alongside raw score

Percentile definition:

percentile = 1 - (rank_index / (N - 1))

Where:

* rank_index = 0 for highest score
* N = total number of ranked symbols

Result:

* Top symbol → percentile ≈ 1.0
* Median symbol → percentile ≈ 0.5
* Bottom symbol → percentile ≈ 0.0

Stable across pagination.

---

# API Changes

Extend ranking response item:

Before:

{
symbol: string,
score: number,
sideways: number,
trend: number,
gain: number
}

After:

{
symbol: string,
score: number,
percentile: number,
sideways: number,
trend: number,
gain: number
}

Optional (future-safe):
Add component percentiles:

sidewaysPercentile
trendPercentile
gainPercentile

Not required for this PR unless trivial to compute.

---

# Implementation Details

Inside ranking service after full scoring + sorting:

for i, item := range rankedSymbols {
item.Percentile = 1.0 - float64(i)/float64(len(rankedSymbols)-1)
}

Edge case:
If N == 1 → percentile = 1.0

No floating point rounding required beyond JSON precision.

---

# Caching Considerations

No additional cache keys required.

Percentile is deterministic given:

* Universe
* Algorithm
* Sort mode
* Timeframe

Therefore:
Existing Redis cache for /api/rankings remains valid.

No cache invalidation changes needed.

# Why Percentile Instead of Min/Max Stretching

* Stable across infinite scroll
* Stable across sessions
* Comparable between users
* Preserves statistical integrity
* Easy to reason about

Raw score remains available for debugging and advanced inspection.

---

# Acceptance Criteria

* Ranking API returns percentile field
* Values in [0,1]
* Correct ordering correspondence
* No regression in performance
* Redis cache still valid

---

# Out of Scope

* Changing ranking formulas
* Z-score normalization
* Dynamic algorithm weighting
* Frontend visual redesign

---

This PR improves interpretability without altering algorithm behavior.
It increases trust and clarity while keeping architecture clean.
