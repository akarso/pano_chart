## PR-071: fix(payments): bind purchase verification to authenticated device + secrets hygiene
🎯 Objective

Two separate holes found in the audit:

1. `POST /api/payments/verify` activates a subscription for whatever `userId` is in the
   request body — Google's verification only proves the purchase token is valid for the app,
   not that it belongs to that `userId`. One valid token (even a cheap own purchase) can
   currently unlock pro for an attacker-chosen account.
2. A live-looking API key (`financeflow.key`) is committed in plaintext in `backend/config.yaml`.

Depends on **PR-070** (authenticated device identity) — this PR is the reason PR-070 exists.

🧱 Scope

Backend (Go):
- `adapters/http/payment_handler.go` — `VerifyPurchase` stops reading `userId` from the
  request body; uses `middleware.UserIDFromContext(r.Context())` (from PR-070) instead and
  passes that value into the existing `Verify(ctx, userID, ...)` signature unchanged (see
  1️⃣) — the use case still takes an explicit `userID` parameter (keeps it testable/reusable
  without a context dependency), it's just no longer the *handler's* job to trust a
  client-supplied one
- `backend/config.yaml` — remove `financeflow.key`; load from `FINANCEFLOW_API_KEY` env var
- rotate the exposed key with the provider (out-of-band, not a code change — flag as a manual
  step in the PR checklist)
- `.gitignore` — no change needed (config.yaml itself isn't the problem, hardcoding secrets in
  it is); add a `config.example.yaml` documenting the env var instead

1️⃣ Handler change
```go
// before
var req struct {
    UserID        string `json:"userId"`
    PurchaseToken string `json:"purchaseToken"`
    ProductID     string `json:"productId"`
}
json.NewDecoder(r.Body).Decode(&req)
sub, err := h.subs.Verify(r.Context(), req.UserID, req.PurchaseToken, req.ProductID)

// after
var req struct {
    PurchaseToken string `json:"purchaseToken"`
    ProductID     string `json:"productId"`
}
json.NewDecoder(r.Body).Decode(&req)
userID := middleware.UserIDFromContext(r.Context())
sub, err := h.subs.Verify(r.Context(), userID, req.PurchaseToken, req.ProductID)
```

2️⃣ Duplicate-token check stays, but now means something
`subscription_service.go` already rejects reuse of the *same* purchase token
(`existing transaction` check) — that logic is correct and unchanged. The fix is upstream:
once `userID` can only be the authenticated caller, a stolen/observed purchase token from
another user's request can at most be replayed against *their own* account (no-op), not used
to activate someone else's.

3️⃣ Secret out of git

The real shape (per `infrastructure/events/config.go`'s `apiKeysConfig`) is a list under
`api_keys.financeflow`, not a flat map — match that, don't invent a simpler shape:
```yaml
# backend/config.example.yaml — committed, key left blank
api_keys:
  financeflow:
    - name: "Finance flow API"
      key: ""   # set via FINANCEFLOW_API_KEY env var, do not commit a real value here
```
YAML has no env-var expansion here (`gopkg.in/yaml.v3` doesn't do that, and nothing in this
loader does either) — `${FINANCEFLOW_API_KEY}` in the YAML itself would just be a literal
string, not an expanded value. The env var must be consulted in Go, ahead of (or instead of)
reading the YAML value:
```go
// infrastructure/events/config.go — LoadFinanceFlowAPIKey
if key := os.Getenv("FINANCEFLOW_API_KEY"); key != "" {
    return key, nil
}
// existing config.yaml-based lookup stays as the fallback for local dev
```
Add `config.example.yaml` with the key field blank/commented, and a one-line note in
`RUNBOOK.md` on setting `FINANCEFLOW_API_KEY` for local/prod.

4️⃣ Manual steps (not code, must happen alongside this PR)
- Rotate the FinanceFlow key with the provider; the old one must be treated as compromised
  since it's been in git history (rewriting history is optional/separate — rotation is not).
- Set `FINANCEFLOW_API_KEY` in the production environment before deploying this PR, or the
  service fails closed on startup (`MustLoadConfig` already panics on missing required config
  — confirm this key is added to that validation).

🚀 Result

- Activating a subscription now requires the purchase token *and* proof of ownership of the
  target account (the auth secret from PR-070) — no more cross-account activation via a stray
  valid token.
- No live credential in the git tree going forward.

📝 Addendum — code review fix (applied before merge)

**Blocker found and fixed: the first version of this PR wasn't actually a fix under default
config.** It reused PR-070's shared, log-only-by-default `authMW` — but `AUTH_ENFORCE` defaults
to `false`, and in log-only mode a request with no `Authorization` header at all (not even a
bad one) falls through to the same `req.UserID`-from-body trust this PR exists to remove. An
attacker didn't even need a stolen token — any cheap self-issued purchase, any victim `userId`
in the body, zero auth header, and the exploit this PR claims to close was still live.

Fixed by giving `/api/payments/verify` its own hard-enforced wiring, independent of
`AUTH_ENFORCE`:
- `NewVerifyPurchaseHandler` no longer has a migration-window fallback at all — it reads
  `userID` via the plain panicking `middleware.UserIDFromContext`, same as `device/unregister`
  (the one other route with no legacy identity to fall back to).
- New `NewVerifyPurchaseRoute(uc, store)` wires `middleware.RequireAuth(store, true)` — literal
  `true`, not the shared `authMW`/`AUTH_ENFORCE` flag — around the handler. `cmd/api/main.go`
  calls this constructor rather than hand-assembling the middleware, so the route's auth
  requirement can't be silently dropped or downgraded by a local edit to `main.go` without
  also touching (and re-reviewing) this constructor.
- Added router-level tests (`TestVerifyPurchaseRoute_*`) that call `NewVerifyPurchaseRoute`
  directly — the same construction `main.go` uses — rather than only the bare handler with a
  hand-injected context. A prior version of this route was, per an old code comment,
  "deliberately left unwrapped"; these tests are specifically aimed at catching that class of
  regression happening again.

Rationale for treating this route differently from subscription-status/device-register/
notification-config (which keep the shared log-only fallback): those endpoints' worst case
under log-only is a data/UX problem (stale prefs, wrong device binding). This endpoint's worst
case is unpaid entitlement — real financial loss — so the migration grace period bought for
the others isn't worth extending here. A pre-PR-070 app build simply can't complete a purchase
until it's updated to claim a device secret; that's the deliberate tradeoff.

Also extracted `middleware.UserIDOrLegacyFallback(ctx, legacyValue)` to collapse the
duplicated "authenticated? else fall back to legacy field, else 401" block that had been
hand-copied across `payment_handler.go` (subscription-status), `device_register_handler.go`,
and `notification_config_handler.go` — one place to eventually delete once `AUTH_ENFORCE=true`
makes it unreachable everywhere at once, rather than three.
