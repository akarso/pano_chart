## PR-071: fix(payments): bind purchase verification to authenticated device + secrets hygiene
🎯 Objective

Two separate holes found in the audit:

1. `POST /api/payments/verify` activates a subscription for whatever `userId` is in the
   request body — Google's verification only proves the purchase token is valid for the app,
   not that it belongs to that `userId`. One valid token (even a cheap own purchase) can
   currently unlock pro for an attacker-chosen account.
2. A live-looking API key (`financeflow.key`) is committed in plaintext in `backend/config.yaml`.

Depends on **PR-070** (authenticated device identity) — this PR is the reason PR-070 exists.

🧱 Scope

Backend (Go):
- `adapters/http/payment_handler.go` — `VerifyPurchase` stops reading `userId` from the
  request body; uses `middleware.UserIDFromContext(r.Context())` (from PR-070) instead
- `application/usecases/subscription_service.go` / `VerifyPurchase` use case — signature drops
  the caller-supplied `userID string` parameter in favor of the context-derived one, so it's
  structurally impossible to call it with an unverified ID
- `backend/config.yaml` — remove `financeflow.key`; load from `FINANCEFLOW_API_KEY` env var
- rotate the exposed key with the provider (out-of-band, not a code change — flag as a manual
  step in the PR checklist)
- `.gitignore` — no change needed (config.yaml itself isn't the problem, hardcoding secrets in
  it is); add a `config.example.yaml` documenting the env var instead

1️⃣ Handler change
```go
// before
var req struct {
    UserID        string `json:"userId"`
    PurchaseToken string `json:"purchaseToken"`
    ProductID     string `json:"productId"`
}
json.NewDecoder(r.Body).Decode(&req)
sub, err := h.subs.Verify(r.Context(), req.UserID, req.PurchaseToken, req.ProductID)

// after
var req struct {
    PurchaseToken string `json:"purchaseToken"`
    ProductID     string `json:"productId"`
}
json.NewDecoder(r.Body).Decode(&req)
userID := middleware.UserIDFromContext(r.Context())
sub, err := h.subs.Verify(r.Context(), userID, req.PurchaseToken, req.ProductID)
```

2️⃣ Duplicate-token check stays, but now means something
`subscription_service.go` already rejects reuse of the *same* purchase token
(`existing transaction` check) — that logic is correct and unchanged. The fix is upstream:
once `userID` can only be the authenticated caller, a stolen/observed purchase token from
another user's request can at most be replayed against *their own* account (no-op), not used
to activate someone else's.

3️⃣ Secret out of git
```yaml
# backend/config.yaml
financeflow:
  key: ${FINANCEFLOW_API_KEY}   # loaded from env, not committed
```
```go
// infrastructure/events/config.go
key := os.Getenv("FINANCEFLOW_API_KEY")
if key == "" {
    key = cfg.FinanceFlow.Key // fallback to config.yaml only for local dev override
}
```
Add `config.example.yaml` with the key field blank/commented, and a one-line note in
`RUNBOOK.md` on setting `FINANCEFLOW_API_KEY` for local/prod.

4️⃣ Manual steps (not code, must happen alongside this PR)
- Rotate the FinanceFlow key with the provider; the old one must be treated as compromised
  since it's been in git history (rewriting history is optional/separate — rotation is not).
- Set `FINANCEFLOW_API_KEY` in the production environment before deploying this PR, or the
  service fails closed on startup (`MustLoadConfig` already panics on missing required config
  — confirm this key is added to that validation).

🚀 Result

- Activating a subscription now requires the purchase token *and* proof of ownership of the
  target account (the auth secret from PR-070) — no more cross-account activation via a stray
  valid token.
- No live credential in the git tree going forward.
