## PR-070: fix(auth): server-issued device identity + request authentication
🎯 Objective

Close the "trust the client" hole found in the security audit: every handler today accepts
`userId`/`user_id`/`device_id` straight from the request body/query with zero verification.
Introduce a minimal, install-bound identity the server actually controls, and require it on
every user-scoped endpoint.

Explicitly out of scope: full login/signup, Firebase Auth, social sign-in. This app has no
accounts today — the fix should not force one into existence. A signed, server-issued device
secret is enough to stop impersonation/IDOR without changing the no-login UX.

🧱 Scope

Backend (Go):
- new `POST /api/device/claim` (or extend existing `/api/device/register`) — server generates
  a random 256-bit secret, stores `sha256(secret) -> userId` in a new `device_credentials`
  sqlite table, returns the raw secret once (never stored/logged in plaintext)
- new `backend/adapters/http/middleware/auth.go` — reads `Authorization: Bearer <secret>`,
  looks up the hash, injects verified `userID` into `context.Context`
- every handler that currently reads `userId`/`user_id` from body/query for a mutating or
  data-scoped call switches to reading it from context instead:
  - `adapters/http/payment_handler.go` (`GET /api/subscription/status`, `POST /api/payments/verify`)
  - `adapters/http/device_register_handler.go`
  - `adapters/http/notification_config_handler.go`
- reject requests with a missing/invalid/unknown secret with `401`

Frontend (Flutter):
- `preferences_service.dart` — on first launch, call `/api/device/claim`, persist the returned
  secret alongside the existing local `device.userId` (SharedPreferences)
- `infrastructure/` HTTP layer — attach `Authorization: Bearer <secret>` to every authenticated
  call; on `401`, re-claim a fresh identity (handles the case where local storage/DB was wiped
  server-side or the row was pruned)

1️⃣ Data model
```sql
CREATE TABLE IF NOT EXISTS device_credentials (
    secret_hash TEXT PRIMARY KEY,   -- sha256(secret), hex
    user_id     TEXT NOT NULL,
    created_at  INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_device_credentials_user ON device_credentials(user_id);
```

2️⃣ Claim endpoint
```go
// backend/adapters/http/device_claim_handler.go
func (h *DeviceClaimHandler) Claim(w http.ResponseWriter, r *http.Request) {
    userID := uuid.NewString() // server decides the ID now, not the client
    secret := make([]byte, 32)
    if _, err := rand.Read(secret); err != nil {
        http.Error(w, "internal error", 500)
        return
    }
    raw := base64.RawURLEncoding.EncodeToString(secret)
    hash := sha256.Sum256(secret)

    if err := h.store.Save(hex.EncodeToString(hash[:]), userID); err != nil {
        http.Error(w, "internal error", 500)
        return
    }
    json.NewEncoder(w).Encode(map[string]string{
        "userId": userID,
        "secret": raw, // shown once — client must persist it
    })
}
```

3️⃣ Middleware
```go
// backend/adapters/http/middleware/auth.go
func RequireAuth(store DeviceCredentialStore) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            secret := strings.TrimPrefix(r.Header.Get("Authorization"), "Bearer ")
            if secret == "" {
                http.Error(w, "unauthorized", 401)
                return
            }
            hash := sha256.Sum256([]byte(secret))
            userID, ok := store.Lookup(hex.EncodeToString(hash[:]))
            if !ok {
                http.Error(w, "unauthorized", 401)
                return
            }
            ctx := context.WithValue(r.Context(), ctxUserID, userID)
            next.ServeHTTP(w, r.WithContext(ctx))
        })
    }
}
```

4️⃣ Handlers stop trusting the body
```go
// before
var req struct{ UserID string `json:"userId"` }
json.NewDecoder(r.Body).Decode(&req)
sub, _ := h.subs.Status(req.UserID)

// after
userID := middleware.UserIDFromContext(r.Context())
sub, _ := h.subs.Status(userID)
```
If a request body still contains a `userId` field for backward compatibility during rollout,
ignore it — never let it override the context value.

5️⃣ Migration path (existing installs)
Existing installs already have a locally-generated `userId` in `SharedPreferences` with rows
in the backend keyed by that ID (subscriptions, device tokens, notification config). The claim
endpoint must accept an optional `existingUserId` on first call and, if provided, bind the new
secret to that ID instead of minting a new one — otherwise every existing user silently loses
their subscription/notification history on next app update.
```go
func (h *DeviceClaimHandler) Claim(w http.ResponseWriter, r *http.Request) {
    var req struct{ ExistingUserID string `json:"existingUserId,omitempty"` }
    _ = json.NewDecoder(r.Body).Decode(&req)
    userID := req.ExistingUserID
    if userID == "" {
        userID = uuid.NewString()
    }
    // ...generate + store secret bound to userID as above
}
```

6️⃣ Rollout order
1. Ship backend with `/api/device/claim` + middleware, but middleware in **log-only** mode
   (record would-be-401s, don't block) for one release.
2. Ship frontend claiming + attaching the secret.
3. Once telemetry shows claim adoption is near-100%, flip middleware to enforcing.

👉 Known limitation (not fixed by this PR): the secret lives in `SharedPreferences`, so an
app reinstall still mints a fresh identity — this PR stops *impersonation of other users*, it
does not stop trial-reset-by-reinstall (tracked separately, see PR-078).

🚀 Result

- No endpoint can be pointed at an arbitrary `userId` anymore — subscription status, device
  tokens, and notification config are only readable/writable by whoever holds the matching
  secret.
- `/api/payments/verify` gains a trusted `userID` to bind purchases to (feeds PR-071).

📝 Addendum — code review fixes (applied before merge)

The first pass of this PR still let anyone mint a credential for any `existingUserId` by
simply knowing it (leaked via logs, screenshots, or the app's own — now-removed — plaintext
query strings). Fixed as follows, all shipped in this PR rather than deferred:

- **First-claim-wins.** `existingUserId` can only be claimed once — `ClaimDevice` now checks
  `CredentialStore.UserHasCredential` and rejects a second claim with `409` +
  `ErrUserIDAlreadyClaimed`. Once the real owner's app has claimed its local ID post-upgrade,
  learning that ID later can no longer mint a credential for it. Residual risk: a narrow race
  window per user between backend go-live and that specific user's first launch on the new
  app version — inherent to not having real accounts, not worth a bigger fix for it.
- **Input validation.** `existingUserId` is validated against `^[A-Za-z0-9_-]{1,128}$` before
  it touches the database (`ErrInvalidUserID` → `400`).
- **Abuse protection on the now-public endpoint.** Per-IP rate limit (10/min, burst 5,
  `middleware.PerIPRateLimit`) and a 1KB body cap (`http.MaxBytesReader`) on
  `/api/device/claim`.
- **`Register` IDOR closed too.** The audit only scoped `Unregister` to the owning user;
  `Register`'s upsert unconditionally reassigned `user_id` on a `device_id` conflict, so any
  authenticated caller (including a freshly self-claimed one) could hijack another user's
  `device_tokens` row by knowing/guessing their `device_id` — and since the client sets
  `deviceId: prefs.userId`, that's the same value as the just-fixed leak above. Fixed via an
  `ON CONFLICT ... WHERE device_tokens.user_id = excluded.user_id` guard — a conflicting row
  owned by someone else is left untouched and `Register` returns
  `appsocial.ErrDeviceOwnedByAnotherUser` (`409`) instead of silently reassigning it.
- **Dead `userId`/`user_id` query params removed** from `getStatus`/`fetch` on the frontend —
  the server ignores them (reads the authenticated context instead), so they were pure
  exposure with no function.
- **Reclaim-on-401.** `sendAuthenticated()` (frontend) retries once with a freshly re-claimed
  secret on a 401 before giving up, so a paying user doesn't silently look free-tier for an
  entire session just because the one-shot startup claim hit a flaky network.
- **`/api/payments/verify` left fully out of scope** — the frontend no longer attaches a
  (currently ineffective) `Authorization` header to it, so nothing about this endpoint looks
  more secured than it is until PR-071 actually wires server-side enforcement.

Not fixed here, explicitly deferred: `device_credentials` rows are never expired/cleaned up
(unbounded growth from reinstalls that don't pass `existingUserId`) — needs a retention-policy
decision, not a mechanical fix, tracked as a follow-up.

📝 Addendum 2 — second review pass

- **TOCTOU in first-claim-wins, closed.** The addendum-1 fix used a separate
  `UserHasCredential` read followed by a `Save` write — two concurrent claims for the same
  `existingUserId` could both pass the read before either had written, so both would succeed.
  `CredentialStore.Save` + `UserHasCredential` are replaced by a single
  `SaveIfUserUnclaimed(ctx, secretHash, userID) (ok bool, err error)`, implemented as one
  guarded SQL statement (`INSERT ... SELECT ... WHERE NOT EXISTS (...)`) — the same
  check-and-set-in-one-statement pattern already used for `Register`'s ownership guard.
  Verified with a real concurrency test (`TestSQLiteCredentialStore_SaveIfUserUnclaimed_ConcurrentClaims_OnlyOneWins`,
  run under `-race`): 8 goroutines racing to claim the same user ID across a shared-cache
  in-memory DB with multiple real connections — exactly one wins.
- **Reclaim-on-401 known limitation (not fixed, documented).** `sendAuthenticated()`'s retry
  always resends the same `existingUserId`. Combined with first-claim-wins, that id can only
  ever be claimed once — so the retry only recovers the cold-start case (no secret claimed
  yet, or the whole `device_credentials` row is gone). If the locally stored secret is
  corrupted/mismatched while the server-side row for that user is still intact, the retry
  hits `409 ErrUserIDAlreadyClaimed`, not a fresh secret, and the install is permanently
  locked out of authenticated endpoints until app data is cleared (which mints a new identity
  from scratch — losing subscription/notification history, same as any fresh install). This
  isn't a regression: there was no recovery path from any 401 before this PR either. Flagging
  it so it doesn't read as "401s are now fully handled" — they're not; only the specific
  cold-start case is. A real fix needs either a server-side "prove you're the same install"
  recovery mechanism or accepting that this class of corruption requires a fresh identity,
  which is a product decision, not left implicit here.

📝 Addendum 3 — third review pass

- **Auth was enforcing from the moment this deploys, with no migration window.** The rollout
  order in section 6️⃣ above always called for a log-only period before enforcement; the
  implementation skipped straight to hard-enforcing `RequireAuth`, which would 401 every
  pre-PR-070 install's subscription-status/device-register/device-unregister/notification-config
  calls the instant this backend ships, before those installs have a build that calls
  `/api/device/claim` at all. Fixed: `RequireAuth(store, enforce bool)` now takes an explicit
  mode. `enforce=false` ("log-only", the default via `AUTH_ENFORCE` unset/not `"true"`) lets an
  unauthenticated request through — logged, not rejected — but with no verified identity in
  context. `UserIDFromContextOK` replaces the panicking accessor on the three handlers that
  still have a legacy identity field to fall back to while unauthenticated
  (`?userId=`/`?user_id=`/body `user_id` on subscription-status, notification-config, and
  device-register respectively) — those branches are migration-window-only and become dead
  code once `AUTH_ENFORCE=true` is set (unauthenticated requests never reach the handler after
  that). `device/unregister` has no legacy fallback at all — the pre-PR-070 version of that
  route never took a client-supplied identity (that absence was the original IDOR), so an
  unauthenticated caller is rejected there regardless of the enforce setting; in practice this
  is moot since no shipped client build calls it. **Operational note:** flip
  `AUTH_ENFORCE=true` once logs show adoption is high enough, then delete the fallback
  branches — they're intentionally temporary.
- **Concurrent 401s could race the reclaim and strand the loser.** `sendAuthenticated`'s retry
  calls `onUnauthorized` independently per request; a burst of requests all hitting 401 around
  the same moment (e.g. several calls firing at app startup before a secret is claimed) each
  started their own `/api/device/claim` call. Combined with Addendum 2's first-claim-wins,
  only one of those concurrent claims can succeed — the others get `409`, their catch block
  swallows it same as any other failure, and their retry re-sends the still-stale/absent
  secret with no further attempt. Fixed with `core/async/single_flight.dart`: `main.dart`'s
  `reclaimDeviceSecret` is now wrapped in `singleFlight()`, so every concurrent caller —
  whether the cold-start claim or any `onUnauthorized` callback across all three API clients —
  awaits the exact same in-flight claim and observes its outcome, instead of racing separate
  attempts.
- **Scope: this changeset previously bundled unrelated roadmap docs (PR-071 through PR-078).**
  Those are pure planning artifacts (no code yet), but committing them alongside this
  security-relevant auth PR made the auth diff noisier to review and harder to revert as a
  standalone unit. Split into a separate commit — this PR's commit now contains only the
  device-auth implementation and this doc.
