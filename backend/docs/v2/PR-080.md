## PR-080: fix(backend): calibrate setup volatility scoring per timeframe

🎯 Objective

`SetupService`'s `volatilityFromSeries` normalizes average candle range against a single
hardcoded constant tuned for daily candles ("typical crypto daily range: 0-10%"), regardless of
the timeframe actually requested. `VolatilityFit` treats `0.5` as the ideal input and carries 30%
of `ComputeConfidence`'s weight for the `sideways` and `compression` regimes. On sub-daily
timeframes the miscalibration silently pins the volatility component near its floor — most
severely at 15m, where a typical average candle range (~0.1-0.5% of price) normalizes to ~0.01-0.05
against a divisor built for ~10%. The result: every 15m sideways/compression setup gets its
confidence systematically dragged down by this one component, independent of whether conditions
are actually good for range trading.

⚠️ Status: provisional divisor, not calibrated

The `sqrt(time)` scaling below is a principled *starting point* — it turns "every timeframe uses
a divisor built for 1d" into "every timeframe gets its own, direction-correct divisor" — but it is
**not validated against real market data**. Real crypto intraday `(high-low)/close` doesn't
necessarily follow clean random-walk sqrt-time scaling (fee/tick-size floors, session effects), so
1m/5m/1h/4h in particular should be treated as plausible, not confirmed. Revisit once real
per-timeframe score-distribution telemetry exists (same precedent as PR-074's
`LoggingScoreCalculator` sampling) — do not treat this PR as having "solved" volatility
calibration, only as having removed the much larger, definitely-wrong 1d-divisor-everywhere bug.

🧱 Scope

Backend only (Go):
- `application/setups/service.go` — `volatilityFromSeries`

1️⃣ Per-timeframe divisor

```go
// before
func volatilityFromSeries(series domain.CandleSeries) float64 {
	...
	avg := total / float64(n)
	// Typical crypto daily range: 0-10% ≈ 0-0.1.
	return clamp(avg / 0.1)
}
```

```go
// after
func volatilityFromSeries(series domain.CandleSeries) float64 {
	...
	avg := total / float64(n)
	divisor := volatilityDivisorForTimeframe(series.Timeframe())
	if divisor <= 0 {
		return 0
	}
	return clamp(avg / divisor)
}
```

`volatilityDivisorForTimeframe` scales the existing daily divisor (0.1) down by
`sqrt(timeframe duration / 1 day)` — the standard random-walk volatility-scaling assumption
(volatility scales with the square root of elapsed time). This keeps 1d behavior byte-for-byte
identical (scale = 1 → divisor = 0.1) while giving every shorter timeframe its own, proportionally
smaller divisor instead of reusing the daily one. `domain.CandleSeries` already carries its own
`Timeframe()`, so no call-site signature changes are needed — `Timeframe.Duration()` already
exists and is used the same way elsewhere in this codebase (e.g. `SidewaysV5`'s
`IdealATRRangeMap`).

This is a scaling heuristic, not an empirically fitted constant — it's an honest, principled
starting point (matching the existing constant's own "0-10%" comment, which was itself never
empirically fitted either), not a claim of precision. Worth revisiting once real score-distribution
telemetry exists per timeframe (the codebase already has precedent for this — see PR-074's
`LoggingScoreCalculator` sampling).

2️⃣ Verification

- Regression test: same candle shape (identical average `(high-low)/close`) scored at 15m must
  produce a materially higher `VolatilityFit` under `"sideways"` than the pre-fix behavior, and
  land close to the ideal `0.5` input when the range is genuinely typical for 15m — proving the
  fix, not just that *something* changed.
- 1d behavior must be unchanged (regression test pinning the divisor at exactly 0.1 for `Timeframe1d`).
- Full `go test ./...` — no unrelated regressions.

🚀 Result

- `Confidence` for 15m/5m/1m sideways and compression setups stops being silently capped by a
  volatility component that was never actually measuring volatility at those timeframes — moving
  it into the range `VolatilityFit` was designed to reward or penalize.
