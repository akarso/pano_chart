# PR-054 — Directional Trend Score

## Problem

The "Trend Predictability" score was direction-agnostic: `math.Abs(slopeNorm) * R²`.
A 30% downtrend with high R² scored identically to a 30% uptrend.

When the frontend sorted by "trend up," a coin falling 30% appeared first because
it had the highest absolute trendiness. The direction toggle (up/down) was
effectively useless for the trend sort mode.

## Root Cause

`TrendPredictabilityScoreCalculator.Score()` strips the slope sign with
`math.Abs()`. All downstream consumers (TotalScore, percentiles, badges, sorting)
only ever saw unsigned values.

## Fix

Added `signAdjustTrend()` in `get_rankings.go Execute()`, called **after** all
internal processing (TotalScore, percentiles, badges). It negates the
"Trend Predictability" score for symbols whose sparkline slopes downward
(`last close < first close`).

The result is a signed score in the API response:
- Positive = uptrend
- Negative = downtrend

The frontend's existing `_sortItems` already handles direction correctly:
- `direction='up'` → descending sort → positive (uptrend) scores first
- `direction='down'` → ascending sort → negative (downtrend) scores first

### Why sign-adjust at the end?

Applying the sign after all internal processing preserves:
- **TotalScore**: Computed by `Rank()` using unsigned values — unchanged
- **EvaluationSnapshot/classify**: `BuildSnapshot` runs before sign-adjust — unchanged
- **TrendPercentile**: `computeComponentPercentiles` runs before sign-adjust —
  measures absolute trendiness, not direction
- **Badges**: Based on TrendPercentile — unchanged
