## PR-076: chore(backend): operational hardening
🎯 Objective

A grab-bag of low-risk, high-value cleanup found during the audit — none of these change
business behavior, they fix operational robustness and remove clutter. Bundled into one PR
because each item is small; keep as separate commits within the PR for easy review/revert.

🧱 Scope

Backend only (Go):
- graceful shutdown in `cmd/api/main.go`
- remove startup smoke-test code that blocks boot on live network calls
- tighten CORS now that PR-070 adds real auth
- delete duplicated `topTwo`/`topTwoFloats`
- fix the stale doc comment on `EvaluationProvider`

1️⃣ Graceful shutdown

`cmd/api/main.go` replaced `log.Fatal(http.ListenAndServe(addr, mux))` with an `http.Server` run
in its own goroutine, a `signal.Notify` wait for `SIGINT`/`SIGTERM`, `srv.Shutdown` with a 10s
deadline (falling back to `srv.Close()` if it's exceeded), then `socialCancel()` to stop the three
background goroutines (`socialWatcher`, `pushConsumer`, `notifyScheduler` — all already running
off `socialCtx`), then a `sync.WaitGroup`-bounded wait (5s) for them to actually exit, and only
then closing the stores they depend on (`paymentRepo`, `socialAccountStore`, `socialSubStore`,
`deviceStore` — the last of which also backs `credentialStore`/`notifConfigStore` via its shared
DB connection).

Each of the three `go xyz.Run(socialCtx)` call sites was wrapped in `backgroundWG.Add(1)` +
`defer backgroundWG.Done()` so shutdown can wait for them specifically, not just fire-and-forget
context cancellation. The four `defer func() { _ = x.Close() }()` calls for the stores above were
removed in favor of explicit, ordered `Close()` calls in the shutdown sequence — leaving them as
`defer` would have double-closed each store (once explicitly, once via `defer` at `main`'s actual
return), and more importantly they never ran at all before this fix: `log.Fatal` calls `os.Exit`
immediately, which skips every deferred function, and an unhandled `SIGTERM` from a container
orchestrator kills the process without unwinding the stack either way.

Verified by building a standalone binary and sending it `SIGTERM` directly: it logs "shutting
down...", then "shutdown complete", and exits with code 0 within ~1s — see the addendum diary for
the exact repro. (`go run` wraps the compiled binary in a way that made a first attempt at this
inconclusive — signals sent to the wrapper process's PID don't reliably propagate the way a direct
`kill -TERM` on the real binary's PID does; switched to a directly-built binary for the real test.)

2️⃣ Removed boot-blocking smoke-test code

Deleted the `cmd/api/main.go:169-204`-ish block (`// Test universe` / `// Test volume provider` /
dangling `// Test ranker` with no code under it) that made live Binance calls purely to
`fmt.Printf` sample output at startup. It had no functional purpose, added a real network
dependency to server boot with nothing to do with actually serving traffic, and the `ctx :=
context.Background()` that only existed to feed it was removed along with it (unused after the
deletion — confirmed by `go build` after the change; the very next `err` usage a few lines down is
a fresh `:=`, so nothing downstream referenced the removed `univ`/`vols`/`ctx`).

3️⃣ CORS

Locked down `AllowedOrigins`/`AllowedHeaders` from wide-open `"*"` to the actual production
origins now that PR-070 auth headers exist. The roadmap doc's placeholder guessed
`panocharts.app`; checked the real domain against the frontend instead of trusting the guess —
`frontend/lib/bootstrap/main.dart` points `apiBaseUrl` at `https://api.panocharts.com`, and
`overview_widget.dart` links to `https://panocharts.com/help.html` and
`.../blog.html#how_not_to_get_scammed` — so the real apex domain is `panocharts.com`, not
`panocharts.app`. Used `rs/cors`'s single-wildcard-segment support
(`github.com/rs/cors@v1.11.1`, confirmed via its `utils.go` wildcard matcher) to allow
`https://panocharts.com` and `https://*.panocharts.com` together, covering `www` and any future
subdomain (e.g. an `app.` web client) without hardcoding each one. `AllowedHeaders` narrowed to
`Content-Type, Authorization`, matching what the API/web clients actually send.

Verified end-to-end against a running instance: an `OPTIONS` preflight with
`Origin: https://panocharts.com` and `Origin: https://app.panocharts.com` both get
`Access-Control-Allow-Origin` echoed back; `Origin: https://evil.example.com` gets no CORS header
at all (204 with no `Access-Control-Allow-Origin`), i.e. correctly rejected by the browser's own
CORS enforcement.

4️⃣ Dedupe `topTwo` — moot, already resolved

Grepped for `topTwo`/`topTwoFloats`: only one definition exists today
(`application/market/market_state_service.go:459`), and `regime_detector.go` (the file the

5️⃣ Stale `EvaluationProvider` comment — moot, already resolved

The file the roadmap doc named (`application/market/metrics/metrics_service.go`) no longer exists.
`EvaluationProvider`'s current home (`application/market/evaluation_provider.go`) carries only a

different comment in `application/market/regimehistory/tracker.go` describing when the tracker is

📝 Addendum 1 — CR follow-up (shutdown-race fix, unclosed store, unbounded snapshot-logger stop)

**Major 1 (valid, confirmed, fixed): the 5s worker-drain deadline raced the RSS provider's 10s HTTP
timeout.** `Watcher.Run`'s `select` only re-checks `ctx.Done()` between ticks — once `pollNext()`
is entered it can't observe cancellation until it returns, and `RSSProvider.Fetch` used
`client.Get(url)` with no context at all, bounded only by the client's own 10s `Timeout`. So
`socialCancel()` firing mid-`Fetch` couldn't unblock it: the shutdown sequence's 5s
`backgroundWG.Wait()` could (and, on a slow/hung Nitter bridge, would) expire and fall through to
"closing stores anyway" while `pollNext` was still blocked inside `Fetch`, and the `Upsert`/
`UpdateAccount` calls that follow a *successful* fetch would then run against an already-closed
`socialAccountStore`.

Fixed at the root rather than by bumping the 5s deadline (a fatter deadline would have shrunk the
race window without closing it): threaded `context.Context` through the whole call chain —
`domain/social.Provider.Fetch(ctx, account)` → `infrastructure/social.RSSProvider.Fetch` now
builds its request via `http.NewRequestWithContext` and calls `client.Do` instead of `client.Get`,
so the request's entire round trip (dial/TLS/headers/body) is bound to ctx, not just wall-clock
capped — → `Watcher.pollNext(ctx)` → `Run`'s `pollTicker.C` case now passes its own `ctx` through.
A cancelled ctx now aborts an in-flight fetch immediately (network cancellation, not a timeout
wait), so `pollNext` returns promptly and `Run`'s next loop iteration sees `ctx.Done()` — well
within the existing 5s wait. `application/social.Service.Feed`'s unrelated live-fetch call site
(no request-scoped context of its own, not part of any background-worker shutdown path) was
updated to pass `context.Background()` explicitly rather than left broken by the interface change.

Two test doubles (`countingProvider`, `stubProvider` in both `tests/application/social` and
`tests/adapters/social/handler_test.go`) and all `RSSProvider.Fetch` test call sites were updated
to the new signature. Added two regression tests: `TestRSSProvider_AbortsOnContextCancellation`
(a real HTTP round trip against a handler that never responds on its own — proves cancellation,
not the client's `Timeout`, is what unblocks `Fetch`) and
`TestWatcher_RunReturnsPromptlyWhenFetchBlocksOnCancelledContext` (a `blockingProvider` that hangs
on `ctx.Done()` — proves `Run` returns promptly once `Fetch` is cancellable, the actual property
the shutdown sequence depends on).

**Major 2 (valid, confirmed, fixed): `regimeHistoryRepo` was opened but never closed.** Every
other SQLite store got an explicit `Close()` in the shutdown sequence; this one was missed. Added
`_ = regimeHistoryRepo.Close()` alongside `paymentRepo.Close()` — both are written from HTTP
handlers (via `marketService.SetObserver(regimeTracker)`, invoked synchronously during request
handling), not from the three background goroutines, so they're protected by `srv.Shutdown`'s own
drain rather than `backgroundWG`, same reasoning as `paymentRepo` already had.

**Major 3 (valid, acknowledged, not separately fixed): `srv.Close()`'s fallback path doesn't
guarantee in-flight handlers have actually returned.** Confirmed against the stdlib docs:
`Close()` force-closes listeners and connections but doesn't (and structurally can't) kill a
handler goroutine mid-execution — a slow handler could still be running application code, touching
`paymentRepo`/`deviceStore`, right as the following lines close them. This is a real, narrower
version of the same class of race as Major 1, but only reachable when graceful `Shutdown` has
*already* failed to complete within its 10s deadline — an already-degraded fallback, not the
common path. Rather than build a second handler-tracking mechanism (a real fix would need its own
`sync.WaitGroup` around every HTTP handler, disproportionate for an edge case one level past an
already-abnormal timeout), verified the actual failure mode is bounded: every store in this path
wraps a plain `*sql.DB`, whose `Query`/`Exec`/etc. return the ordinary `sql.ErrConnDone` after
`Close()` — never a panic — and every call site here already handles its error by logging, not by
assuming success. Documented this explicitly in the shutdown block's comment instead of adding
code, per the reviewer's own suggested fix #4 ("confirm no direct `*sql.DB` panics").

**Minor 1 (valid, fixed): `snapshotLogger.Stop()` had no timeout of its own.** Confirmed
`AsyncChannelLogger.Stop()` blocks unconditionally on `<-l.done` until its drain goroutine finishes
flushing whatever's buffered via the sink — fine today (this instance's sink only does
`log.Printf`), but this whole path only became *reachable* once `main()` returns normally instead
of via `log.Fatal`→`os.Exit` (this PR's own change), and nothing stops a future sink from doing
real, potentially slow I/O. Wrapped the `defer` in a goroutine + `select` with a 5s deadline,
logging and moving on if it's exceeded rather than hanging shutdown indefinitely.

**Minor 2 (acknowledged, no code fix): `AllowedHeaders` can drift from what clients actually
send.** This is a process/maintenance observation, not a code defect with a concrete fix — no
change made.

**Minor 3 (partially addressed): no automated test for the shutdown sequence itself.** Testing
`main()`'s OS-signal handling directly isn't consistent with this repo's conventions (`cmd/api` has
no test files today, and there's no existing pattern for exercising a `main()` shutdown path via
the test runner rather than a manually-built binary). Added the two automated tests described
under Major 1 instead, which cover the actual mechanism the shutdown sequence depends on
(cancellable `Fetch`) rather than the OS-signal plumbing around it. The full manual verification
checklist actually run against a built binary for this addendum: `SIGTERM` → clean exit code 0
within ~1-2s logging "shutting down..." then "shutdown complete"; CORS preflight from
`https://panocharts.com` and `https://app.panocharts.com` (wildcard subdomain) both get
`Access-Control-Allow-Origin` echoed back; a preflight from an unrelated origin gets no CORS header
at all.

📝 Addendum 2 — CR follow-up (Scheduler Outlives Repository, plus two test-fixture races)

**Issue 1 (valid, confirmed, fixed): the notification scheduler had the exact same shutdown race
as Addendum 1's Watcher/Fetch case, this time via `regimeHistoryRepo`.** `Scheduler.Run`'s `select`
only re-checks `ctx.Done()` between ticks — once `checkMarketState(ctx)` is entered it can't
observe cancellation until it returns, and `MarketStateService.Calculate` (which
`checkMarketState` calls, and which invokes the regime observer — i.e. `regimeTracker.Update`,
writing to `regimeHistoryRepo` — synchronously as its last step) took no context at all. So
`socialCancel()` firing mid-`Calculate` couldn't unblock it: the shutdown sequence's bounded
`backgroundWG.Wait()` could expire and fall through to "closing stores anyway" while
`checkMarketState` was still blocked inside `Calculate`, and a resumed call would then try to
write to an already-closed `regimeHistoryRepo` (logged, not a crash — `MarketStateService` already
just logs an observer-update error — but a silently dropped regime-history observation).

Investigated whether this was fixable at the same small scope as the RSS case, or whether it
needed a disproportionate refactor: `Calculate` → `EvaluationProvider.GetLatestEvaluations` →
`RankingsEvaluationProvider.GetLatestEvaluations` → `RankingsUseCase.Execute`. Checked
`GetRankings.Execute` directly — it's already fully cancellation-aware end to end (universe fetch,
volume fetch, per-symbol candle fetch, and the bounded worker pool all already take and honor
`ctx`, via `errgroup.WithContext` + a `semaphore`-gated pool). The only broken link was
`RankingsEvaluationProvider.GetLatestEvaluations` hardcoding `context.Background()` instead of
forwarding a real context — and `Calculate` not accepting one to forward in the first place. Given
the deep plumbing already existed, threading a real `ctx` through was the proportionate fix, not a
scope-creeping refactor:

- `EvaluationProvider.GetLatestEvaluations(ctx, timeframe)` and
  `RankingsEvaluationProvider.GetLatestEvaluations` now forward `ctx` to `rankings.Execute(ctx,
  ...)` instead of `context.Background()`.
- `MarketStateService.Calculate(ctx, timeframe)` now forwards `ctx` into
  `GetLatestEvaluations`; `CalculateWithCandleMetrics` (which already had `ctx`, previously only
  for its own candle fan-out) now forwards the same `ctx` into `Calculate` too.
- `MarketProvider` (two separate, structurally-identical local interfaces — one in
  `application/notifications/scheduler.go`, one in `application/setups/service.go`) both updated
  to `Calculate(ctx, timeframe)`.
- All four call sites updated: `scheduler.go`'s two `checkMarketState`/legacy-broadcast calls
  (already had `ctx` in scope), `setups/service.go`'s market-modifier call (already had `ctx` in
  scope, inside `Evaluate`), and `adapters/http/market_handler.go`'s HTTP handler (now passes
  `r.Context()` instead of implicitly running every request against `context.Background()`).
- Updated every test fake with a stale signature: `fakeMarketProvider` (`scheduler_test.go`, also
  used by `config_test.go`), `fakeEvalProvider` (`market_state_test.go`, shared by
  `market_state_metrics_test.go`), `realisticEvalProvider` (`realistic_pipeline_test.go`), and
  ~35 call sites across those files plus `health_test.go` passing `context.Background()`.
- Added `TestScheduler_RunReturnsPromptlyWhenCalculateBlocksOnCancelledContext` (a
  `blockingMarketProvider` that hangs on `ctx.Done()`, mirroring Addendum 1's Watcher test) —
  proves `Run` returns promptly once `Calculate` is cancellable, the actual property the shutdown
  sequence depends on.

While in this area, also threaded `ctx` through the *unrelated* `Service.Feed`/`FilteredFeed` path
in `application/social/service.go` (flagged in the same CR round): `SocialFeedHandler.ServeHTTP`
now passes `r.Context()` through `FilteredFeed(ctx, ...)` → `Feed(ctx, ...)` →
`provider.Fetch(ctx, ...)`, replacing the `context.Background()` (and the comment arguing it was
fine, written in Addendum 1) that ignored a disconnecting client entirely. Small, well-contained
blast radius (one production caller, one internal call, ~7 test call sites in
`service_test.go`) now that `Provider.Fetch` was already `ctx`-aware from Addendum 1.

**Issue 2 (valid, confirmed, fixed): `blockingProvider.Fetch`'s `close(fetchStarted)` (Addendum 1's
own Watcher test) could double-close and panic.** The comment claiming "pollNext calls Fetch
synchronously, so this fires at most once" was true within one tick but missed a real path: once
the first `Fetch` unblocks on `ctx.Done()` and returns, `Run`'s loop re-enters `select` with BOTH
`ctx.Done()` and (if `pollTicker` also fired while `Fetch` was blocked — likely, since the test
waits for the fetch-started signal before cancelling, which usually takes longer than the test's
5ms poll interval) `pollTicker.C` ready. Go's `select` picks among ready cases at random, so a
second `Fetch` call — and a second, panicking `close` — was a real, if narrow, possibility, not
just a hypothetical. Fixed by guarding the close with `sync.Once`, preserving the "signal only
once" semantics the test actually needs.

**Issue 3 (valid, confirmed, fixed): `TestRSSProvider_AbortsOnContextCancellation` (Addendum 1's
own RSS test) used a fixed `time.Sleep(50ms)` to guess when the request was in flight before
cancelling.** A sleep-based guess is a race against real scheduling/network-stack timing, not a
guarantee — usually fine locally, a plausible source of CI flakiness under load. Replaced with a
`requestStarted` channel the test server's handler closes the instant it's actually invoked; the
test now waits on that channel (with its own 2s failure-mode timeout) before calling `cancel()`,
guaranteeing the cancellation exercises a request already in flight on every run.

All three issues fixed. Full suite re-verified: `go build`, `go vet`, `go test ./... -race
-count=3` (repeated 3x specifically to shake out flakiness in the newly-added synchronization,
all green), `gofmt -l` clean on every changed file, and a live `SIGTERM` smoke test against a
freshly built binary still exits cleanly (code 0, "shutting down..." → "shutdown complete") after
the `Calculate` signature change.

📝 Addendum 3 — CR follow-up ("Cancellation Still Reaches Observer")

**Valid, confirmed, fixed.** Addendum 2's `ctx` threading made the rankings pipeline *abortable*,
but didn't stop `Calculate` from reaching the regime-observer write on an already-cancelled `ctx`.
Root cause, confirmed by re-reading `GetRankings.Execute`: each per-symbol worker in the bounded
pool swallows its own errors by design (`if err != nil { return nil }` — "skip symbols with fetch
errors, partial failure tolerance"), and that includes a context-cancellation error from
`GetLastNCandles`. So `grp.Wait()` — and therefore `Execute`, and therefore
`GetLatestEvaluations` — can return a **successful, partial result with a nil error** even when
`ctx` was cancelled mid-run, as long as at least one worker had already completed before
cancellation propagated. `Calculate`'s `if err != nil` check right after fetching evaluations
never sees this: `err` is nil, so it fell straight through to computing a summary and calling
`s.observer.Update(...)` — reaching `regimeHistoryRepo` regardless of `ctx`, exactly the race
Addendum 1/2 were meant to close.

Verified the mechanism empirically rather than trusting the description: reused the existing
`fakeEvalProvider` (which returns its configured evaluations unconditionally, ignoring `ctx`
entirely) to model the "pipeline returned success despite cancellation" case directly, without
needing to reproduce the real worker-pool race — added
`TestMarketStateService_Calculate_CancelledContext_SkipsObserver`, confirmed it failed before the
fix (`obs.calls` was 1, not 0) and passed after.

First fix attempt was wrong and caught by a pre-existing test: added an early
`if ctx.Err() != nil { return mkt.Summary{}, err }` right after the evaluations fetch, which broke
`TestMarketStateService_CalculateWithCandleMetrics_CancelledContextReturnsPromptly` (a PR-073 CR
follow-up test asserting that a cancelled context makes `CalculateWithCandleMetrics` return a
**best-effort summary promptly, with no error** — cancellation there is meant to abandon the
optional, slower candle-metrics fan-out gracefully, not fail the whole call). Reworked to the
correct, narrower fix: `Calculate` still returns its computed summary and no error on a cancelled
`ctx` — only the observer write itself is now gated on `ctx.Err() == nil`, right where the
observer is called. This satisfies both tests: cancellation suppresses the specific side effect
(the regime-history write) without changing `Calculate`'s "always return a best-effort summary"
contract for its other callers.

Full suite re-verified after the correction: `go build`, `go vet`, `go test ./... -race`, both
cancellation tests passing together, `gofmt -l` clean.
