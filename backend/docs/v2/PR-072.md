## PR-072: fix(scoring): trend direction correctness across regime/setup/notification pipeline
🎯 Objective

`TrendPredictabilityScoreCalculator.Score` returns `|slope| * R²` — magnitude only, direction
is discarded. Every downstream consumer that assumes "trend score high = uptrend" is silently
wrong roughly half the time:

- `application/setups/service.go:dominantRegime` assigns "uptrend"/"downtrend" purely from
  score magnitude (comment in code admits "direction not in scores")
- `application/notifications/scheduler.go` — the `Downtrend` config toggle is wired to
  `sum.Scores.Expansion` (breakout activity), not to any bearish signal at all; `Uptrend` fires
  off the undirected trend score without checking `summary.Bias`
- `ComputeTrendHealth` then applies the wrong drawdown/bounce formula for whatever direction
  was guessed, feeding a fabricated health score into Setup-of-the-Day and market labels

This is the highest-value fix in the whole roadmap: it's the one that puts genuinely wrong
financial signals in front of users today.

🧱 Scope

Backend only (Go):
- `domain/scoring/trend_predictability_score_calculator.go` — keep `Score()` returning
  magnitude (it's a *strength* metric and other callers rely on that), but expose direction
  alongside it rather than making callers guess
- `application/setups/service.go` — `dominantRegime` uses the real bias, not score sign-guessing
- `application/notifications/scheduler.go` — `Uptrend`/`Downtrend` toggles read actual
  direction; `Downtrend` case rewired off `Scores.Expansion` entirely
- `application/market/health.go` — `ComputeTrendHealth` receives a verified direction, not an
  inferred one

1️⃣ Expose direction from the calculator
```go
// domain/scoring/trend_predictability_score_calculator.go
// Score already computes slopeNorm before taking math.Abs() — return the sign too.
func (c *TrendPredictabilityScoreCalculator) ScoreWithDirection(closes []float64) (score float64, bias string) {
    // ...existing calculation up to `slopeNorm`...
    score = normalised // existing magnitude logic, unchanged
    switch {
    case slopeNorm > 0:
        bias = "up"
    case slopeNorm < 0:
        bias = "down"
    default:
        bias = "neutral"
    }
    return score, bias
}
```
Keep `Score()` as a thin wrapper (`s, _ := c.ScoreWithDirection(closes); return s`) so every
existing caller that only needs magnitude is untouched.

2️⃣ Fix `dominantRegime` in setups
```go
// application/setups/service.go — before
if trend > 0.5 {
    return "uptrend"
}
return "downtrend"

// after
_, bias := trendCalc.ScoreWithDirection(closes)
if bias == "neutral" {
    return "sideways" // or whatever the existing neutral bucket is named
}
return bias + "trend" // "uptrend" / "downtrend"
```
**Canonical direction source: `ScoreWithDirection`'s slope-sign bias, not
`EvaluationSnapshot.Bias`.** They're two different, both-legitimate signals — slope sign is a
price-*shape* judgment ("is this series trending up or down"), while `EvaluationSnapshot.Bias`
is a coarser aggregate-return judgment used for whole-market directional bias in
`MarketStateService.Calculate`. Layering also settles it: `domain/scoring` (where
`ScoreWithDirection` lives) has no access to the `application`-layer `EvaluationSnapshot` type,
so reusing `e.Bias` here would mean a domain type reaching into application, backwards from
the existing dependency direction. Every consumer that needs "is this specific trend score's
direction up or down" — `dominantRegime` here, `MetricsService.CalculateRegime`,
`MarketStateService.Calculate`'s per-token trend bookkeeping, the scheduler's Uptrend/Downtrend
toggles (3️⃣), and `ComputeTrendHealth` — must read the bias paired with *this* score
(`ScoreWithDirection`'s return value, or whatever field it's threaded into downstream), not a
separately-computed aggregate. `EvaluationSnapshot.Bias`/`Summary.Bias` (whole-market
directional bias) stays as its own, independent signal — this PR doesn't touch it.

3️⃣ Fix the scheduler
```go
// application/notifications/scheduler.go — before
if cfg.Uptrend {
    if sum, ok := summaries[cfg.UptrendTimeframe]; ok && sum.Regime != mkt.RegimeIndecisive {
        p := sum.Scores.Trend
        ...
    }
}
if cfg.Downtrend {
    if sum, ok := summaries[cfg.DowntrendTimeframe]; ok && sum.Regime != mkt.RegimeIndecisive {
        p := sum.Scores.Expansion // <-- wrong metric entirely
        ...
    }
}

// after
if cfg.Uptrend {
    if sum, ok := summaries[cfg.UptrendTimeframe]; ok &&
        sum.Regime != mkt.RegimeIndecisive && sum.Bias == "up" {
        p := sum.Scores.Trend
        ...
    }
}
if cfg.Downtrend {
    if sum, ok := summaries[cfg.DowntrendTimeframe]; ok &&
        sum.Regime != mkt.RegimeIndecisive && sum.Bias == "down" {
        p := sum.Scores.Trend
        ...
    }
}
```
`RegimeSummary` needs a `Bias` field populated the same way `MarketStateService` already does
it (aggregate directional bias with return-sign validation) — if it's not already there, add
it alongside `EffectiveTrend`/`BreakdownRate`/`Label` (which were already "backported" per the
PR-063 trend-health work, per the same pattern).

4️⃣ Regression tests to add (this pipeline currently has zero direction-specific coverage)
- `TestScoreWithDirection_UptrendVsDowntrend` — same magnitude, opposite slope, assert bias flips
- `TestCheckMarketForUser_DowntrendAlert_FiresOnBearishRegime` — currently would need to assert
  it fires on `Scores.Expansion`, which is the bug; rewrite to assert it fires on `Bias == "down"`
- `TestDominantRegime_DirectionMatchesPriceAction` — synthetic falling-price series must not
  return "uptrend"

🚀 Result

- "Downtrend" notifications actually mean downtrend.
- A user subscribed to "Uptrend" alerts can no longer receive one during a confirmed decline.
- Setup-of-the-Day direction label and trend-health scoring use a verified bias instead of a
  50/50 guess disguised as a threshold.
