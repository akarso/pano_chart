## PR-072: fix(scoring): trend direction correctness across regime/setup/notification pipeline
🎯 Objective

`TrendPredictabilityScoreCalculator.Score` returns `|slope| * R²` — magnitude only, direction
is discarded. Every downstream consumer that assumes "trend score high = uptrend" is silently
wrong roughly half the time:

- `application/setups/service.go:dominantRegime` assigns "uptrend"/"downtrend" purely from
  score magnitude (comment in code admits "direction not in scores")
- `application/notifications/scheduler.go` — the `Downtrend` config toggle is wired to
  `sum.Scores.Expansion` (breakout activity), not to any bearish signal at all; `Uptrend` fires
  off the undirected trend score without checking `summary.Bias`
- `ComputeTrendHealth` then applies the wrong drawdown/bounce formula for whatever direction
  was guessed, feeding a fabricated health score into Setup-of-the-Day and market labels

This is the highest-value fix in the whole roadmap: it's the one that puts genuinely wrong
financial signals in front of users today.

🧱 Scope

Backend only (Go):
- `domain/scoring/trend_predictability_score_calculator.go` — keep `Score()` returning
  magnitude (it's a *strength* metric and other callers rely on that), but expose direction
  alongside it rather than making callers guess
- `application/setups/service.go` — `dominantRegime` uses the real bias, not score sign-guessing
- `application/notifications/scheduler.go` — `Uptrend`/`Downtrend` toggles read actual
  direction; `Downtrend` case rewired off `Scores.Expansion` entirely
- `application/market/health.go` — `ComputeTrendHealth` receives a verified direction, not an
  inferred one

1️⃣ Expose direction from the calculator
```go
// domain/scoring/trend_predictability_score_calculator.go
// Score already computes slopeNorm before taking math.Abs() — return the sign too.
func (c *TrendPredictabilityScoreCalculator) ScoreWithDirection(closes []float64) (score float64, bias string) {
    // ...existing calculation up to `slopeNorm`...
    score = normalised // existing magnitude logic, unchanged
    switch {
    case slopeNorm > 0:
        bias = "up"
    case slopeNorm < 0:
        bias = "down"
    default:
        bias = "neutral"
    }
    return score, bias
}
```
Keep `Score()` as a thin wrapper (`s, _ := c.ScoreWithDirection(closes); return s`) so every
existing caller that only needs magnitude is untouched.

2️⃣ Fix `dominantRegime` in setups
```go
// application/setups/service.go — before
if trend > 0.5 {
    return "uptrend"
}
return "downtrend"

// after
_, bias := trendCalc.ScoreWithDirection(closes)
if bias == "neutral" {
    return "sideways" // or whatever the existing neutral bucket is named
}
return bias + "trend" // "uptrend" / "downtrend"
```
**Canonical direction source: `ScoreWithDirection`'s slope-sign bias, not
`EvaluationSnapshot.Bias`.** They're two different, both-legitimate signals — slope sign is a
price-*shape* judgment ("is this series trending up or down"), while `EvaluationSnapshot.Bias`
is a coarser aggregate-return judgment used for whole-market directional bias in
`MarketStateService.Calculate`. Layering also settles it: `domain/scoring` (where
`ScoreWithDirection` lives) has no access to the `application`-layer `EvaluationSnapshot` type,
so reusing `e.Bias` here would mean a domain type reaching into application, backwards from
the existing dependency direction. Every consumer that needs "is this specific trend score's
direction up or down" — `dominantRegime` here, `MetricsService.CalculateRegime`,
`MarketStateService.Calculate`'s per-token trend bookkeeping, the scheduler's Uptrend/Downtrend
toggles (3️⃣), and `ComputeTrendHealth` — must read the bias paired with *this* score
(`ScoreWithDirection`'s return value, or whatever field it's threaded into downstream), not a
separately-computed aggregate. `EvaluationSnapshot.Bias`/`Summary.Bias` (whole-market
directional bias) stays as its own, independent signal — this PR doesn't touch it.

3️⃣ Fix the scheduler
```go
// application/notifications/scheduler.go — before
if cfg.Uptrend {
    if sum, ok := summaries[cfg.UptrendTimeframe]; ok && sum.Regime != mkt.RegimeIndecisive {
        p := sum.Scores.Trend
        ...
    }
}
if cfg.Downtrend {
    if sum, ok := summaries[cfg.DowntrendTimeframe]; ok && sum.Regime != mkt.RegimeIndecisive {
        p := sum.Scores.Expansion // <-- wrong metric entirely
        ...
    }
}

// after
if cfg.Uptrend {
    if sum, ok := summaries[cfg.UptrendTimeframe]; ok &&
        sum.Regime != mkt.RegimeIndecisive && sum.Bias == "up" {
        p := sum.Scores.Trend
        ...
    }
}
if cfg.Downtrend {
    if sum, ok := summaries[cfg.DowntrendTimeframe]; ok &&
        sum.Regime != mkt.RegimeIndecisive && sum.Bias == "down" {
        p := sum.Scores.Trend
        ...
    }
}
```
`RegimeSummary` needs a `Bias` field populated the same way `MarketStateService` already does
it (aggregate directional bias with return-sign validation) — if it's not already there, add
it alongside `EffectiveTrend`/`BreakdownRate`/`Label` (which were already "backported" per the
PR-063 trend-health work, per the same pattern).

4️⃣ Regression tests to add (this pipeline currently has zero direction-specific coverage)
- `TestScoreWithDirection_UptrendVsDowntrend` — same magnitude, opposite slope, assert bias flips
- `TestCheckMarketForUser_DowntrendAlert_FiresOnBearishRegime` — currently would need to assert
  it fires on `Scores.Expansion`, which is the bug; rewrite to assert it fires on `Bias == "down"`
- `TestDominantRegime_DirectionMatchesPriceAction` — synthetic falling-price series must not
  return "uptrend"

🚀 Result

- "Downtrend" notifications actually mean downtrend.
- A user subscribed to "Uptrend" alerts can no longer receive one during a confirmed decline.
- Setup-of-the-Day direction label and trend-health scoring use a verified bias instead of a
  50/50 guess disguised as a threshold.

📝 Addendum — as actually implemented

The real code differed from this doc's pseudo-code in a few ways worth recording:

- `TrendPredictabilityScoreCalculator.Score` takes `series domain.CandleSeries` and returns
  `(float64, error)`, not `(closes []float64) float64` — `ScoreWithDirection` mirrors that
  real signature: `(series domain.CandleSeries) (score float64, bias string, err error)`. The
  full regression body moved into `ScoreWithDirection`; `Score` is now the thin wrapper.
- **`mkt.RegimeSummary.Bias` already existed and was already computed correctly** —
  `MetricsService.CalculateRegime` derives it from aggregate period return across all symbols,
  with a hard gate ("if aggregate return is negative, bias cannot be up"). Likewise
  `domain.EvaluationSnapshot.Bias` (sparkline first-vs-last) was already correct and already
  correctly consumed for `ComputeTrendHealth`'s state param. Neither needed a code change —
  only the scheduler's Uptrend/Downtrend toggles were failing to *read* the already-correct
  `sum.Bias`. This narrowed the actual fix to exactly two call sites:
  `application/setups/service.go:dominantRegime` (needed a real direction — added
  `ScoreWithDirection` for this) and `application/notifications/scheduler.go` (needed to
  consult the `Bias` field that was sitting right there, unused).
- `application/market/health.go` needed **no change** — `ComputeTrendHealth` already takes an
  externally-supplied `state` string and applies the right formula for whatever it's given;
  the bug was always upstream, in what callers passed it, both of which are fixed above.
- `dominantRegime` gained a `series domain.CandleSeries` parameter (it already had a `series`
  available one call frame up, in `computeRegimeAndHealth`) and calls `ScoreWithDirection` on
  it directly — a small, self-contained recomputation of the regression rather than restructuring
  `SymbolStats`/`WeightedSymbolScorer` to thread a bias value through the generic multi-calculator
  scoring engine, which would have meant special-casing one calculator inside code designed to
  treat all calculators uniformly.
- Also gave the legacy (no-config-store) broadcast path's "Market trending today" message a
  direction when `summary.Bias` is available ("trending up/down today") — cheap, same-spirit
  fix, not previously called out in this doc.
- Found in passing, NOT fixed (out of scope — a different, pre-existing bug in a different
  gate): `domain/scoring/trend_predictability_score_calculator.go`'s `closePricesClustered`
  step-function detector can false-positive on a short (≤~10 candles), perfectly evenly-spaced
  trending series — every sorted-adjacent gap in such a series exceeds its 10%-of-range
  threshold, so it reads as "clustered" and zeroes the score. Only surfaced because a synthetic
  test series tripped it; real candle data is noisier and less likely to hit this exact shape,
  but it's worth a dedicated look. Flagged as a separate task rather than folded into this PR.

📝 Addendum 2 — CR round 2 (dominantRegime/scheduler follow-ups)

- `dominantRegime` recomputed `ScoreWithDirection` on every call but never checked it against
  `scores["Trend Predictability"]` — the two are two independent computations that happen to run
  the same calculator over the same series today, an implicit not enforced invariant. Added a
  package-level `trendDirectionCalc` (avoids reallocating the calculator per call) and a
  `scoresAgree(a, b float64) bool` epsilon check (`1e-9`); `dominantRegime` now falls back to
  `"sideways"` if the recomputed magnitude doesn't match what was already scored, rather than
  trusting a bias that might belong to a different series/scorer than the score did.
  `tests/application/setups/service_test.go`'s `TestDominantRegime_DirectionMatchesPriceAction`
  fixtures were changed from a hardcoded `Trend Predictability: 0.9` to the real score computed
  by the calculator for each fixture series (`trendDominantStatsFor` helper) — the hardcoded
  constant would never agree with the real recomputed value and made every subtest fall through
  to "sideways".
- `ScoreWithDirection`'s bias was derived from the raw slope sign before `closePricesClustered`,
  `trendShapePenalty`, and `SeriesDirectionAgreement` could crush the score to 0 — a fragile
  coincidence that every disqualifying penalty path today also zeroes the score outright. Added
  an explicit guard: `bias = "neutral"` whenever the final `normalised` score is below `1e-9`,
  so this stays true by construction even if a future penalty tweak leaves a tiny-but-nonzero
  score.
- `checkMarketState`'s per-user market-summary log line (`scheduler.go`) logged trend/sideways/
  compression/expansion scores but not `Bias` — added `bias=%s` to the format string.
- `DowntrendMinDominance` now thresholds `Scores.Trend` instead of `Scores.Expansion` (the
  actual bug fix). Existing users' stored threshold values were tuned against Expansion score
  magnitudes, which have a different distribution than Trend scores — flagged in a code comment
  at the call site at this point; see Addendum 3 below for the actual migration this led to.
- Added `TestScheduler_PerUser_NeutralBias_NeitherUptrendNorDowntrendFires` — both Uptrend and
  Downtrend configured with thresholds at 0, `Bias == "neutral"`: neither must fire.
- `closePricesClustered`'s short-series false-positive (noted above) was flagged as a standalone
  follow-up task rather than fixed here — out of scope for a direction-correctness PR.
- The `Uptrend`/`Downtrend` per-user notification body was overriding the direction-explicit
  "Uptrend"/"Downtrend" label with `sum.Label` (from `BuildMarketLabel`) whenever it was
  non-empty — that label is direction-agnostic ("Strong trend", "Trend breaking down"), so a
  bearish alert could read "Market is Strong trend" with no hint it was bearish. Fixed by always
  using the literal "Uptrend"/"Downtrend" label in these two branches (the Sideways branch
  already didn't have this problem).

📝 Addendum 3 — CR round 3 (DowntrendMinDominance migration)

- `DowntrendMinDominance` previously thresholded `Scores.Expansion`; PR-072 repoints it at
  `Scores.Trend`, a metric with a different distribution. A value a user had tuned before this
  change means something else now, and reusing it silently could make their downtrend alerts
  fire far more or less often than they expect. Added a `config_version` field to the SQLite
  store's persisted JSON (`infrastructure/notifications/sqlite_config_store.go`); rows with no
  version (i.e. every row written before this change) have `DowntrendMinDominance` reset to the
  current default (0.75) on read, rather than reusing a value tuned for a different metric. New
  saves stamp the current version so this reset only ever applies once, on first read after
  upgrade — the same pattern already used for the legacy single `macro` bool → `MacroHigh`/
  `MacroModerate` split a few lines above it in the same file.
  `TestConfigStore_ResetsDowntrendMinDominanceForPreMigrationConfigs` covers this directly by
  seeding a raw pre-migration JSON row.
