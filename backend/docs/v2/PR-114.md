## PR-114: fix(events): backoff on FinanceFlow errors (stop 1/min retry storm)

🎯 Objective

FinanceFlow usage is usually ~50 calls/day (healthy: notification scheduler every
1 minute absorbed by a 30‑minute in-memory cache). On some days it jumps to
~1440 (= 1/min for 24h) and stays there. Root cause: after the normal TTL
expires, a failing upstream still gets called every scheduler tick because the
stale-cache fallback returned data **without** extending freshness.

See ROADMAP “Hotfixes” — PR-114. Independent of the killer-app tracks; land ASAP.

🧱 Scope

Backend only:
- `application/usecases/get_events.go` — error hold, cancel filter, singleflight, cache cap, injectable clock
- `adapters/http/events_handler.go` — max 31-day span, allowlisted countries
- tests under `tests/application/usecases/` and `tests/adapters/http/`

Out of scope: Redis events cache, changing `MacroCheckInterval`, adaptive/jittered backoff, frontend.

1️⃣ Error hold (exactly `errorBackoff`, default 15m)

On upstream `FetchEvents` error (not cancel/deadline):
- Stale present → arm `errorHoldUntil = now + errorBackoff`; force `fetchedAt` past
  normal TTL so after the hold elapses `getCached` returns **nil** (revalidate),
  never a warm hit via upcomingTTL (30m) or pastTTL (6h).
- No stale → insert empty entry under the same hold (negative cache) with
  `fetchedAt` already past any success TTL.
- While `now < errorHoldUntil` → soft-hit (no FinanceFlow call).
- On success → `putCache` replaces the entry (hold cleared).

2️⃣ Cancel / deadline poisoning

`context.Canceled` / `context.DeadlineExceeded` from the provider **do not**
install or extend holds. Caller `ctx` cancel while waiting on singleflight returns
stale/empty **without** writing a hold. Shared fetch uses `context.WithoutCancel`
so one aborted HTTP client cannot abort siblings.

3️⃣ Singleflight + cache bound

Concurrent misses for the same key coalesce via `singleflight`. Cache map is capped
at 256 entries (oldest by freshness score evicted) so public arbitrary keys cannot
grow unboundedly under error holds.

4️⃣ HTTP edge

- Reject date spans &gt; 31 days (400).
- Allowlist countries: United States, Euro Area, China (case-insensitive).

5️⃣ Verification

- Hold expires → provider called again (fake clock + 1m backoff).
- Success after hold → normal upcoming TTL applies; hold cleared.
- `context.Canceled` → no empty hold; next call hits provider.
- Fully-past cold fail → retry at errorBackoff, **not** pastTTL (6h).
- Stale-after-TTL-fail → soft-hit during hold.
- Singleflight coalesces concurrent misses to 1 fetch.
- Handler rejects Germany / 60-day range.

✅ Definition of Done

- [x] contract tests above pass
- [x] gofmt / go test for usecases + events handler
- [x] ROADMAP Hotfixes text matches 15m retry ceiling

🚀 Result

A FinanceFlow blip after TTL expiry costs ~1 call per **15 minutes** of downtime
per cache key (~96/day/key during a full-day outage), not ~1/min (~1440). Healthy
days stay ~50. Cancelled clients cannot blank the shared calendar for the scheduler.

📝 Implementation notes

- Fixed 15m is not adaptive (no jitter). Acceptable for a hotfix.
- Multi-replica still multiplies (process-local cache); Redis is a follow-up.
- `SetErrorBackoff` / `SetNow` are intentional test seams on `GetEvents`.
