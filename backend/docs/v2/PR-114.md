## PR-114: fix(events): backoff on FinanceFlow errors (stop 1/min retry storm)

🎯 Objective

FinanceFlow usage is usually ~50 calls/day (healthy: notification scheduler every
1 minute absorbed by a 30‑minute in-memory cache). On some days it jumps to
~1440 (= 1/min for 24h) and stays there. Root cause: after the normal TTL
expires, a failing upstream still gets called every scheduler tick because the
stale-cache fallback returned data **without** extending freshness.

See ROADMAP “Hotfixes” — PR-114. Independent of the killer-app tracks; land ASAP.

🧱 Scope

Backend only:
- `application/usecases/get_events.go` — error hold, singleflight, LRU cap, injectable clock
- `adapters/http/events_handler.go` — max 31-day span, allowlisted countries
- tests under `tests/application/usecases/` and `tests/adapters/http/`

Out of scope: Redis events cache, changing `MacroCheckInterval`, adaptive/jittered backoff, frontend.

1️⃣ Error hold (exactly `errorBackoff`, default 15m)

On **any** upstream `FetchEvents` error — including wrapped `context.DeadlineExceeded`
from `http.Client.Timeout` (the common FinanceFlow blip when the shared fetch uses
`context.WithoutCancel`):
- Stale present → arm `errorHoldUntil = now + errorBackoff`; force `fetchedAt` past
  normal TTL so after the hold elapses `getCached` clears the hold and returns **nil**
  (revalidate) but **keeps** the entry for stale fallback — never a warm hit via
  upcomingTTL/pastTTL, and never wipe last-known events into an empty hold.
- No stale → insert empty entry under the same hold (negative cache); empty entries
  may be deleted when their hold elapses (GC only).
- While `now < errorHoldUntil` → soft-hit (no FinanceFlow call); bumps LRU `lastAccess`.
- On success → `putCache` replaces the entry (hold cleared).

2️⃣ Caller abort (not provider deadlines)

“No hold write” applies only when the **waiting** `Execute` caller’s `ctx` is done
(`select` on `ctx.Done()`). That path returns stale/empty without installing a hold.
Shared fetch uses `WithoutCancel` so one aborted HTTP client cannot abort siblings.
Provider-side `DeadlineExceeded` / transport / 5xx **do** arm holds.

3️⃣ Singleflight + LRU cache bound

Concurrent misses for the same key coalesce via `singleflight`. Cache map is capped
at 256 entries; eviction is **LRU by lastAccess** (bumped on soft-hit and write) so
API date-scanning cannot thrash the hot scheduler key during an outage.

4️⃣ HTTP edge

- Reject date spans > 31 days (400).
- Allowlist countries: United States, Euro Area, China (case-insensitive).

5️⃣ Verification

- Hold expires → provider called again (fake clock + 1m backoff).
- Success after hold → normal upcoming TTL applies; hold cleared.
- Wrapped `DeadlineExceeded` (Client.Timeout shape) → empty hold + soft-hit.
- Fully-past cold fail → retry at errorBackoff, **not** pastTTL (6h).
- Stale-after-TTL-fail → soft-hit during hold; second fail after hold still serves CPI.
- LRU: hot soft-hit key survives eviction pressure at maxEntries=3.
- Singleflight coalesces concurrent misses to 1 fetch.
- Handler rejects Germany / 60-day range.

✅ Definition of Done

- [x] contract tests above pass
- [x] gofmt / go test for usecases + events handler
- [x] ROADMAP Hotfixes text matches: holds on upstream timeouts; no-hold only for cancelled waiters

🚀 Result

A FinanceFlow blip (including Client.Timeout) after TTL expiry costs ~1 call per
**15 minutes** of downtime per cache key (~96/day/key during a full-day outage),
not ~1/min (~1440). Healthy days stay ~50. Hot scheduler key is LRU-protected
against public date scanning.

📝 Implementation notes

- Fixed 15m is not adaptive (no jitter). Acceptable for a hotfix.
- Multi-replica still multiplies (process-local cache); Redis is a follow-up.
- `SetErrorBackoff` / `SetNow` / `SetMaxEntries` are test seams (mutex-guarded).
- Singleflight may still complete a FinanceFlow call after the scheduler context
  dies; secondary to the Timeout/hold fix.
