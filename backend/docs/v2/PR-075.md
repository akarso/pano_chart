## PR-075: fix(notifications): regime-aware dedup + payment endpoint rate limiting
🎯 Objective

Two independent hardening fixes for the notification/payment surface:

1. Per-user market notification dedup key is `market_<timeframe>_<dateKey>` — no regime
   component. Once a user gets one market push today, a genuine regime change later the same
   day produces no further notification until tomorrow.
2. `POST /api/payments/verify` has no rate limiting, unlike outbound exchange calls
   (`infrastructure/ratelimiter/` is wired into `freetier_candlerepository.go` but nowhere near
   payments). Combined with the pre-PR-070 auth gap this was a bigger deal; even post-auth it's
   still an easy cost/abuse amplification vector (each call triggers a live Google API request).

🧱 Scope

Backend only (Go):
- `application/notifications/scheduler.go` — dedup key includes the regime/state, not just the
  date
- `adapters/http/payment_handler.go` — wrap `VerifyPurchase` with the existing rate limiter
  middleware, keyed per authenticated user (from PR-070)

1️⃣ Dedup key fix
```go
// before
Key: fmt.Sprintf("market_%s_%s", summary.Timeframe, summary.Regime),
// (legacy broadcast path already includes regime — this is only the per-user path missing it)

// checkMarketForUser — before
key := fmt.Sprintf("market_%s_%s", cfg.UptrendTimeframe, dateKey)

// after
key := fmt.Sprintf("market_%s_%s_%s", cfg.UptrendTimeframe, summary.Regime, dateKey)
```
(`summary` here is a `mkt.RegimeSummary` — its regime field is `Regime`, not `State`; `State`
belongs to the other `mkt.Summary` type. Scheduler.go was kept on `RegimeSummary` per the
PR-070 merge resolution, so this must match that, not the type PR-073 would have unified onto
if it had landed first.)
Keep the date component — it still caps a user to one notification per (timeframe, regime,
day), which is the intended behavior (don't re-alert on every scheduler tick while the regime
holds steady), it just needs to reset when the regime actually changes rather than only at
midnight.

2️⃣ Rate limiting
```go
// cmd/api/main.go
paymentLimiter := ratelimiter.New(ratelimiter.Config{
    PerUserLimit: 5,             // verify attempts
    Window:       time.Hour,
})
paymentHandler := adhttp.NewPaymentHandler(subscriptionSvc, paymentLimiter)
```
```go
// adapters/http/payment_handler.go
func (h *PaymentHandler) VerifyPurchase(w http.ResponseWriter, r *http.Request) {
    userID := middleware.UserIDFromContext(r.Context())
    if !h.limiter.Allow(userID) {
        http.Error(w, "too many attempts", http.StatusTooManyRequests)
        return
    }
    // ...existing verify logic
}
```
Reuse the existing `ratelimiter` package rather than adding a new dependency — check its
current API (`freetier_candlerepository.go` usage) for the exact `Allow`/`Config` shape before
copying the snippet above verbatim.

3️⃣ Tests
- `TestCheckMarketForUser_RegimeChangeSameDay_SendsSecondNotification`
- `TestVerifyPurchase_RateLimited_Returns429`

🚀 Result

- A real intraday regime flip (e.g. trend → breakout) reaches subscribed users instead of
  waiting for the next calendar day.
- Payment verification can't be hammered for cost/abuse purposes.

📝 Addendum — as actually implemented

The real code had moved on from this doc's assumptions in both scoped areas — written before
PR-072/PR-073 landed, and before checking the real `ratelimiter` package API, both of which it
explicitly flagged as open questions ("check its current API... before copying the snippet
above verbatim").

1️⃣ Dedup key
- `scheduler.go` no longer has a `mkt.RegimeSummary`/`Regime` type at all — PR-073 unified the
  two regime pipelines onto `mkt.Summary`/`State`. The per-user path also doesn't look up
  `summary.State` directly the way this doc's pseudocode assumes; it already computes a
  `candidate{label, prevalence, timeframe}` per regime (`"Uptrend"`/`"Downtrend"`/`"Sideways"`/
  `"Silent"`) and picks the strongest one as `best`. `best.label` is the more natural,
  already-computed value to key on — it's literally what the notification body says — so the
  fix is `Key: fmt.Sprintf("market_%s_%s_%s", best.timeframe, best.label, dateKey)`, not a
  `summary.Regime`/`State` lookup.
- The legacy broadcast path (`checkMarketState`'s no-config-store branch) already included
  `summary.State` in its key before this PR — confirmed via `grep`, matches the doc's own note
  that only the per-user path was missing it.
- `TestCheckMarketForUser_RegimeChangeSameDay_SendsSecondNotification`
  (`tests/application/notifications/config_test.go`) exercises this against the real
  `Scheduler`/`Engine` dedup, not a bare key-format assertion: sends once (Uptrend), confirms a
  same-input re-check stays deduped, flips the fake market's `Bias` to `"down"` (same simulated
  day), and confirms a second notification (`Downtrend`) goes out.

2️⃣ Rate limiting
- `infrastructure/ratelimiter.RateLimiter` (this doc's `ratelimiter.New(...)`/`Config{PerUserLimit,
  Window}` snippet) is a **global**, blocking token-bucket limiter (`Acquire(ctx) error`, waits
  for a token or context cancellation) used for outbound Binance request throttling — wrong
  shape entirely for "reject the 6th request from this user with 429": it has no per-key
  dimension, and blocking an HTTP handler for up to an hour isn't how this needs to behave.
- Used `adapters/http/middleware.PerIPRateLimit` instead — already exactly the right shape
  (TTL-bounded per-key map, `rate.Limiter` per key, reject-with-429), just hardcoded to key on
  IP. Extracted the shared TTL-map/eviction/Allow logic into an unexported `perKeyRateLimit`
  helper and added `middleware.PerUserRateLimit(requestsPerHour, burst)` alongside the existing
  `PerIPRateLimit(requestsPerMinute, burst)` — same underlying mechanism, keyed on the
  authenticated user ID (`UserIDFromContextOK`) instead of IP, expressed per-hour since "5/hour"
  doesn't have a clean whole-number per-minute equivalent the way `PerIPRateLimit`'s existing
  call sites do. `PerIPRateLimit`'s own tests pass unchanged after the extraction — confirms no
  behavior change to the existing endpoint it guards (`/api/device/claim`).
- Wired into `NewVerifyPurchaseRoute` itself (`adapters/http/payment_handler.go`), not
  `cmd/api/main.go` — this route already has a hard rule (enforced by its own router-level
  tests) that `main.go` must always call this constructor rather than hand-assembling the
  middleware chain, so putting the rate limiter inside it means it can't be silently dropped by
  a future wiring change the way a `main.go`-level addition could be. `PerUserRateLimit` must
  run as the *inner* layer (wrapping the handler, then `RequireAuth` wraps that) since it reads
  the user ID `RequireAuth` puts in context — got this backwards on the first pass conceptually
  while reading the doc's pseudocode (which composes them in the same inside-out order once you
  read the doc's own `Allow`-inside-the-handler sketch closely) and confirmed the correct
  ordering against `RequireAuth`'s actual signature before wiring it.
- 5/hour, burst 5 (burst == the full hourly allowance, so a legitimate user isn't blocked
  retrying a few times after a flaky provider response, but sustained hammering past 5/hour is
  rejected).
- Tests: `TestVerifyPurchaseRoute_RateLimited_Returns429` and
  `_RateLimitTracksUsersIndependently` drive requests through the real `NewVerifyPurchaseRoute`
  wiring (matching the existing auth router-tests' rationale — catch a wiring regression, not
  just a middleware-unit regression), plus `PerUserRateLimit`-specific unit tests
  (`tests/adapters/http/middleware/ratelimit_test.go`): burst/reject, per-user independence, and
  (updated below) shared-bucket behavior when no user is in context.

📝 Addendum — CR follow-up (flapping blocker, rate-limiter hardening)

**Blocker: regime-flap notification spam — confirmed and fixed.** Including `best.label` in the
dedup key was necessary for the PR's stated goal but not sufficient on its own: two candidates
sitting close to a threshold can flip the "strongest" label every single `MarketCheckInterval`
tick (1 minute by default), producing a new key — and a new notification — every tick, exactly
the noise this PR set out to reduce. Added `SchedulerConfig.MarketRegimeHoldDuration` (default 15
minutes): `checkMarketForUser` now tracks, per `(user, timeframe)`, the label and timestamp of
the last regime *change* it acted on, and a label change within the hold window since that last
change is suppressed before it ever reaches the per-key dedup. A same-label repeat is left alone
(the existing per-key dedup already handles that correctly). The hold anchor only moves on an
accepted change, deliberately not on every check — an earlier version of this fix updated the
anchor on every check that cleared the hold window regardless of whether the underlying send was
actually novel, which meant a steady regime re-evaluated just past the hold window could reset
the clock via a call the per-key dedup then silently swallowed, pushing a genuine subsequent
change further out than intended; anchoring only to accepted changes guarantees a decision point
every `MarketRegimeHoldDuration`, not a window that can be indefinitely slid forward.
`TestCheckMarketForUser_RegimeChangeSameDay_SendsSecondNotification` was updated to advance the
clock past the hold window before its regime flip (it previously flipped at the exact same
instant, which is not realistic and would now correctly be held);
`TestCheckMarketForUser_FlappingRegime_StaysBoundedWithinHoldWindow` is the new test — 10 checks
one simulated minute apart, oscillating the winning label every tick, asserting exactly 1
notification goes out.

**Major: `perKeyRateLimit`'s implicit double-division convention — fixed.** Changed the shared
function to take an explicit `perSecond float64` instead of `requestsPerMinute`; `PerIPRateLimit`
now converts minutes→seconds itself (`/60`) and `PerUserRateLimit` converts hours→seconds itself
(`/3600`), each at its own call site, so there's no shared unit convention for a future caller to
misread.

**Major: `PerUserRateLimit`'s unlimited pass-through with no user in context — fixed.** Added
`noKeySentinel`, a reserved key that every request with no derivable key (empty `keyFunc` result)
now shares, instead of bypassing the limiter entirely. This doesn't make `PerUserRateLimit`
correct if it's ever wired behind log-only auth — rejecting unauthenticated requests is still
`RequireAuth`'s job, not this middleware's — but it closes the specific gap the CR flagged: that
misconfiguration now yields one shared, still-enforced bucket for all such requests, not zero
rate limiting for the exact traffic most likely to abuse a costly endpoint. Updated the "no user"
test to assert the new bounded-shared-bucket behavior, and added a test confirming the shared
bucket never draws from a real authenticated user's own allowance.

**Minor: burst == hourly limit boundary-doubling — fixed.** `verifyPurchaseRateLimitBurst`
lowered from 5 to 3 (limit stays 5/hour) — burst equal to the full hourly allowance let a user
spend it entirely right at the top of one hour and again right at the top of the next, ~10 calls
in a short window straddling the boundary rather than a smooth 5/hour. Burst 3 still covers a
legitimate user retrying a few times after a flaky provider response. Updated both router-level
rate-limit tests' burst-loop counts to match.

**Minor: sweep-every-500-requests understates staleness on low-traffic callers — fixed.** Added a
time-based sweep trigger alongside the existing count-based one: `perKeyRateLimit` now also
sweeps stale entries whenever more than `keyLimiterTTL` has elapsed since the last sweep,
regardless of request count. `PerUserRateLimit` on `/api/payments/verify` (a few calls per user,
ever, not per hour) could otherwise take a very long time in production to reach the 500-request
threshold at all. Not a leak either way (map size was always bounded by distinct-key count), just
a narrower staleness window now. No dedicated test added: exercising the time-based path
deterministically would need either an injected clock (a larger refactor than this fix) or a real
10-minute sleep in the test suite; the existing cleanup-sweep test already covers that a sweep
(via either trigger) doesn't break rate-limiting correctness, which is the only externally
observable behavior here — cleanup timing itself isn't.

**Minor: `""` sentinel could be confused with a legitimate empty key — addressed.** Covered by
the `noKeySentinel` fix above: the doc comment on `perKeyRateLimit` now explicitly names `""` as
the reserved "no key" signal rather than describing it only as "empty."
