## PR-101a: Watchlist with state-transition alerts (backend)

**Layer:** application + adapters + infrastructure. **Depends on:** PR-099.

### Scope

- `infrastructure/watchlist.SQLiteStore` — two tables: `watchlist(user_id,
  symbol, added_at)` and `watchlist_state(user_id, symbol, timeframe, state,
  notified_at)`. `Replace` (PUT semantics) prunes symbols no longer in the
  request and inserts new ones with `ON CONFLICT DO NOTHING`, so a symbol
  that was already on the list keeps its original `added_at` — a full
  resync must not make every remaining symbol look freshly added. Capped
  at `ports.WatchlistMaxSymbols` (50) — counted *after* de-duplicating the
  incoming list (CR fix), so 51 duplicate entries of the same symbol don't
  spuriously trip the cap; over the (deduplicated) cap writes nothing and
  returns `ports.ErrWatchlistTooLarge`
- `GET/PUT/DELETE /api/watchlist`, body `{ "symbols": [...] }` for PUT/DELETE
  — wired via `adhttp.NewWatchlistRoute`, which hard-enforces auth
  (`enforce=true`) unconditionally, unlike most other endpoints that share
  the migration-window `AUTH_ENFORCE` flag: this is a brand-new endpoint
  with no pre-auth client to migrate, so there's no reason to ever run it
  log-only. Also rate-limited (`WatchlistRateLimitPerHour`/`Burst`, CR fix
  — this endpoint originally shipped without one, unlike every other
  mutating endpoint since PR-075's payment limiter). Every symbol is
  normalized through `domain.NewSymbol` (non-empty, valid chars,
  uppercased) and capped at `ports.WatchlistMaxSymbolLength` (32 chars)
  before it ever reaches the store (CR fix) — `"btcusdt"` and `"BTCUSDT"`
  collapse to one entry instead of two, and an empty/invalid/oversized
  symbol is rejected with `400` instead of being persisted and fed into
  the scheduler forever. PUT/DELETE bodies are capped at 8KB via
  `http.MaxBytesReader` before decoding (CR fix — a legitimate payload is
  under 2KB), and DELETE also enforces `WatchlistMaxSymbols` itself (CR
  fix — unlike PUT/`Replace`, `Remove` has no cap of its own, so nothing
  previously stopped a request naming far more distinct symbols than any
  real watchlist could hold from building an unbounded SQL `IN (...)`
  clause)
- `NotificationConfig` gains `WatchlistTransitions bool` (default true —
  harmless with an empty watchlist, since there's nothing to check yet) and
  `WatchlistTimeframe string` (default `1h`). `notification_config`'s
  schema version bumps to 3: a config row saved before this field existed
  has no such JSON key at all, so it would otherwise silently unmarshal to
  `WatchlistTransitions: false` forever with no way for the user to
  discover the feature — `config_version < 3` migrates it to `true`, same
  reasoning as `DefaultNotificationConfig` (inert until the user actually
  stars a symbol). An explicit choice saved at `config_version >= 3` — an
  explicit `false` included — is never re-forced. `watchlist_timeframe` is
  validated against `appeval.DefaultTimeframes` on PUT (CR fix — `1m`/`5m`
  are valid for every *other* timeframe field on this config but
  `application/mtf.Service` never produces a frame for them, so accepting
  them here would silently and permanently never fire, with no error
  anywhere)
- `notificationConfigDTO.WatchlistTransitions` is a `*bool`, unlike every
  other bool field on this DTO (CR fix): an app built before this field
  existed sends a PUT body with no `watchlist_transitions` key at all, and
  since `handlePut` does a full-replace write (no partial-PATCH semantics),
  a plain `bool` can't tell "not sent" apart from an explicit `false` —
  every unrelated setting change from an old client would otherwise
  silently and permanently disable watchlist alerts (the write also stamps
  `config_version`, so the migration above only ever helps a genuinely
  untouched row). `handlePut` now reads the existing stored config and
  falls back to it when the pointer is `nil`, instead of defaulting to
  `false`
- `Scheduler.checkWatchlistTransitions` scans `WatchlistProvider.Users`
  (every user ID with ≥1 watchlisted symbol) rather than
  `NotificationConfigStore.All()`'s saved-config rows (CR fix): a user who
  has never saved any notification preference — plausible for someone who
  goes straight to starring a symbol — has no row there at all, so `All()`
  silently skipped them forever even though `Get(userID)` (now called
  per-user) correctly defaults `WatchlistTransitions` to `true` for exactly
  that case. Batches by unique symbol per tick
  (a `map[string]{stack, err}` cache) before fanning out to each
  subscribed user, so N users watching the same symbol share one
  `RegimeStackProvider.Calculate` call instead of triggering N redundant
  evaluation-store reads (CR fix — was `O(users × symbols)`); both the
  per-config and per-symbol loops also check `ctx.Err()` so a scheduler
  shutdown mid-scan doesn't run a large backlog to completion first (CR
  fix). Ticking on
  `SchedulerConfig.WatchlistCheckInterval` (default 5m — a single
  scheduler-wide poll cadence; the roadmap's "tf/2" is per-user, and
  polling more often than any one user's cadence needs just costs a cheap
  extra store read, since the per-(user,symbol) dedup window, not the poll
  interval, is what actually bounds notification frequency): for each
  pro-tier user with the flag on, for each watchlisted symbol, reads
  `RegimeStackProvider.Calculate` (satisfied by the existing PR-099
  `application/mtf.Service` — no new regime computation) and compares the
  frame at the user's `WatchlistTimeframe` against the last-observed state
  in `WatchlistStateStore`. Three transitions notify:
  `compression → expansion` ("Breakout starting"),
  `sideways → trend` ("Trend starting, bias up/down"),
  `trend → sideways|compression` ("Trend pausing"). Any other transition
  (including the first-ever observation, which has no "from" to compare)
  updates the persisted state without notifying
- Dedup: at most one push per `(user, symbol)` per 4 bars of the user's
  `WatchlistTimeframe`, checked via `WatchlistStateStore.LastNotifiedAt`
  (CR fix) — the most recent `NotifiedAt` across *every* timeframe that
  `(user, symbol)` has ever been tracked under, not just the row matching
  the currently-configured timeframe: `GetState`/`SetState` are necessarily
  scoped per-timeframe (a "current regime" only means anything relative to
  one specific timeframe), so reading only the current row would let a
  user reset their own cooldown just by changing `WatchlistTimeframe`.
  Also independent of `Engine`'s own fixed 24h per-`Key` TTL (which would
  otherwise silently re-suppress a legitimate second occurrence of the
  same `(symbol, from, to)` transition inside 24h but outside this dedup
  window — the notification `Key` includes the send instant precisely to
  avoid colliding with that unrelated, coarser safety net)
- Neither a failed `SendToUser` nor a quiet-hours tick advances the
  persisted state to the new dominant regime (CR fix): `Engine.SendToUser`
  returns `nil` both for a genuine successful delivery *and* for a
  quiet-hours no-op, so the two are indistinguishable from the return
  value alone. Advancing state unconditionally on any `nil` meant a
  transient send failure, or simply a transition landing at 3am, could
  permanently lose that transition — the next tick would then compare
  against the already-updated state and never detect it again. A new
  `Engine.WithinAllowedHours()` lets the scheduler check for the
  quiet-hours case explicitly before sending; both branches now leave the
  state unchanged so the identical transition is retried once hours open
  again / the send is retried next tick, as long as the market hasn't
  moved on to a third state meanwhile
- `SQLiteStore.Remove` and the pruning half of `Replace` also clear
  `watchlist_state` for every symbol they drop (CR fix): a symbol's
  transition state used to survive being unwatched, so re-adding it later
  could report a false "transition" on the very first post-re-add scan
  (comparing against a regime observed before the unwatch gap, as if
  nothing happened in between) or wrongly suppress a fresh alert as if
  still inside a dedup window that predates the symbol even being
  re-added

### Out of scope

Frontend star toggle, watchlist filter chip, settings toggle (PR-101b).
Contextual alert payloads / big-picture notification rendering (PR-102).

### Tests

- `SQLiteStore`: round-trip, ordering by `added_at`, resync preserves
  original `added_at` for symbols that stay, drops symbols that leave,
  empty PUT clears, over-cap PUT errors and writes nothing, duplicates
  don't count toward the cap, per-user isolation, transition-state
  round-trip (including zero `NotifiedAt`), overwrite, per-timeframe
  scoping
- `WatchlistHandler` + `NewWatchlistRoute`: GET/PUT/DELETE happy paths,
  empty watchlist serializes as `[]` not `null`, invalid body, store error,
  method not allowed; case-variant duplicates collapse to one canonical
  entry on both PUT and DELETE; empty-string and overlong symbols are
  rejected with 400; an oversized PUT/DELETE body is rejected before
  decoding; DELETE with more than `WatchlistMaxSymbols` distinct symbols is
  rejected; and — driven through the real route wiring, not just the bare
  handler — an unauthenticated request is rejected with 401 and a burst
  past the rate limit gets 429
- `SQLiteStore`: `Users` returns exactly the distinct users with ≥1 symbol
  (empty once cleared); `LastNotifiedAt` finds the most recent notify
  across timeframe rows, is zero when never notified, and is scoped per
  user+symbol; `Remove`/`Replace` clear `watchlist_state` only for the
  symbols they actually drop, leaving retained/other symbols' state intact
- `NotificationConfigHandler`: an omitted `watchlist_transitions` preserves
  the existing stored value (not forced to `false`); an explicit `false` is
  still honored; an invalid `watchlist_timeframe` (e.g. `5m`) is rejected
  with 400, a valid one is saved, and an omitted one (empty string) is
  allowed as the "use stored/default" sentinel
- `SQLiteConfigStore`: a pre-PR-101 row (`config_version` 2, or missing
  entirely) migrates `WatchlistTransitions` to `true`; an explicit `false`
  saved at the current schema version is never re-forced; a brand-new user
  gets the same default via `DefaultNotificationConfig`
- `Engine.WithinAllowedHours` matches `Send`/`SendToUser`'s own quiet-hours
  check
- Scheduler: first sighting doesn't notify; each of the three tracked
  transitions notifies with the right title/payload; an untracked
  transition and a no-change tick don't notify (but still persist state);
  the dedup window suppresses a repeat and allows one again once the
  window elapses; the feature flag, pro-gating, nil providers, and a
  missing frame for the configured timeframe are all covered; two users
  watching the same symbol share one `Calculate` call; a failed send
  leaves the state untouched and the identical transition is retried (and
  succeeds) on the next tick; a quiet-hours tick likewise leaves the state
  untouched and the transition still fires once hours open; a user with no
  saved config row is still scanned and notified; the dedup window is
  correctly checked against the most recent notification even after the
  user changes `WatchlistTimeframe`
