## PR-101a: Watchlist with state-transition alerts (backend)

**Layer:** application + adapters + infrastructure. **Depends on:** PR-099.

### Scope

- `infrastructure/watchlist.SQLiteStore` — two tables: `watchlist(user_id,
  symbol, added_at)` and `watchlist_state(user_id, symbol, timeframe, state,
  notified_at)`. `Replace` (PUT semantics) prunes symbols no longer in the
  request and inserts new ones with `ON CONFLICT DO NOTHING`, so a symbol
  that was already on the list keeps its original `added_at` — a full
  resync must not make every remaining symbol look freshly added. Capped
  at `ports.WatchlistMaxSymbols` (50) — counted *after* de-duplicating the
  incoming list (CR fix), so 51 duplicate entries of the same symbol don't
  spuriously trip the cap; over the (deduplicated) cap writes nothing and
  returns `ports.ErrWatchlistTooLarge`
- `GET/PUT/DELETE /api/watchlist`, body `{ "symbols": [...] }` for PUT/DELETE
  — wired via `adhttp.NewWatchlistRoute`, which hard-enforces auth
  (`enforce=true`) unconditionally, unlike most other endpoints that share
  the migration-window `AUTH_ENFORCE` flag: this is a brand-new endpoint
  with no pre-auth client to migrate, so there's no reason to ever run it
  log-only. Also rate-limited (`WatchlistRateLimitPerHour`/`Burst`, CR fix
  — this endpoint originally shipped without one, unlike every other
  mutating endpoint since PR-075's payment limiter). Every symbol is
  normalized through `domain.NewSymbol` (non-empty, valid chars,
  uppercased) and capped at `ports.WatchlistMaxSymbolLength` (32 chars)
  before it ever reaches the store (CR fix) — `"btcusdt"` and `"BTCUSDT"`
  collapse to one entry instead of two, and an empty/invalid/oversized
  symbol is rejected with `400` instead of being persisted and fed into
  the scheduler forever
- `NotificationConfig` gains `WatchlistTransitions bool` (default true —
  harmless with an empty watchlist, since there's nothing to check yet) and
  `WatchlistTimeframe string` (default `1h`). `notification_config`'s
  schema version bumps to 3: a config row saved before this field existed
  has no such JSON key at all, so it would otherwise silently unmarshal to
  `WatchlistTransitions: false` forever with no way for the user to
  discover the feature — `config_version < 3` migrates it to `true`, same
  reasoning as `DefaultNotificationConfig` (inert until the user actually
  stars a symbol). An explicit choice saved at `config_version >= 3` — an
  explicit `false` included — is never re-forced (CR fix)
- `Scheduler.checkWatchlistTransitions` batches by unique symbol per tick
  (a `map[string]{stack, err}` cache) before fanning out to each
  subscribed user, so N users watching the same symbol share one
  `RegimeStackProvider.Calculate` call instead of triggering N redundant
  evaluation-store reads (CR fix — was `O(users × symbols)`); both the
  per-config and per-symbol loops also check `ctx.Err()` so a scheduler
  shutdown mid-scan doesn't run a large backlog to completion first (CR
  fix). Ticking on
  `SchedulerConfig.WatchlistCheckInterval` (default 5m — a single
  scheduler-wide poll cadence; the roadmap's "tf/2" is per-user, and
  polling more often than any one user's cadence needs just costs a cheap
  extra store read, since the per-(user,symbol) dedup window, not the poll
  interval, is what actually bounds notification frequency): for each
  pro-tier user with the flag on, for each watchlisted symbol, reads
  `RegimeStackProvider.Calculate` (satisfied by the existing PR-099
  `application/mtf.Service` — no new regime computation) and compares the
  frame at the user's `WatchlistTimeframe` against the last-observed state
  in `WatchlistStateStore`. Three transitions notify:
  `compression → expansion` ("Breakout starting"),
  `sideways → trend` ("Trend starting, bias up/down"),
  `trend → sideways|compression` ("Trend pausing"). Any other transition
  (including the first-ever observation, which has no "from" to compare)
  updates the persisted state without notifying
- Dedup: at most one push per `(user, symbol)` per 4 bars of the user's
  `WatchlistTimeframe` — tracked explicitly via `NotifiedAt` in
  `WatchlistTransitionState`, independent of `Engine`'s own fixed 24h
  per-`Key` TTL (which would otherwise silently re-suppress a legitimate
  second occurrence of the same `(symbol, from, to)` transition inside 24h
  but outside this dedup window — the notification `Key` includes the send
  instant precisely to avoid colliding with that unrelated, coarser safety
  net)
- A failed `SendToUser` leaves the persisted state unchanged rather than
  advancing it to the new dominant regime (CR fix): advancing it
  unconditionally meant a single transient push failure permanently lost
  that transition, since the next tick would then compare against the
  already-updated state and never detect it again. The next tick now
  re-compares against the same unchanged "from" and retries the identical
  transition if the market hasn't moved on to a third state meanwhile

### Out of scope

Frontend star toggle, watchlist filter chip, settings toggle (PR-101b).
Contextual alert payloads / big-picture notification rendering (PR-102).

### Tests

- `SQLiteStore`: round-trip, ordering by `added_at`, resync preserves
  original `added_at` for symbols that stay, drops symbols that leave,
  empty PUT clears, over-cap PUT errors and writes nothing, duplicates
  don't count toward the cap, per-user isolation, transition-state
  round-trip (including zero `NotifiedAt`), overwrite, per-timeframe
  scoping
- `WatchlistHandler` + `NewWatchlistRoute`: GET/PUT/DELETE happy paths,
  empty watchlist serializes as `[]` not `null`, invalid body, store error,
  method not allowed; case-variant duplicates collapse to one canonical
  entry on both PUT and DELETE; empty-string and overlong symbols are
  rejected with 400; and — driven through the real route wiring, not just
  the bare handler — an unauthenticated request is rejected with 401 and a
  burst past the rate limit gets 429
- `SQLiteConfigStore`: a pre-PR-101 row (`config_version` 2, or missing
  entirely) migrates `WatchlistTransitions` to `true`; an explicit `false`
  saved at the current schema version is never re-forced; a brand-new user
  gets the same default via `DefaultNotificationConfig`
- Scheduler: first sighting doesn't notify; each of the three tracked
  transitions notifies with the right title/payload; an untracked
  transition and a no-change tick don't notify (but still persist state);
  the dedup window suppresses a repeat and allows one again once the
  window elapses; the feature flag, pro-gating, nil providers, and a
  missing frame for the configured timeframe are all covered; two users
  watching the same symbol share one `Calculate` call; a failed send
  leaves the state untouched and the identical transition is retried (and
  succeeds) on the next tick
