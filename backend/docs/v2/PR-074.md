## PR-074: fix(market): sideways channel regression bug + data-outage visibility
🎯 Objective

Two separate correctness bugs bundled because they're both "the app quietly shows a plausible
but wrong number":

1. `DetectSidewaysV5` fits the upper *and* lower channel boundary from the same combined
   highs+lows point set (copy-paste — `compression_score_calculator.go` right next to it does
   this correctly with separate `regressionThroughHighs`/`regressionThroughLows`). Result:
   `upperSlope == lowerSlope` always, `parallelScore` is permanently 1.0 (a "perfect channel"
   regardless of actual shape), and both boundaries are scored against one shared line instead
   of real support/resistance.
2. When candle-fetch/evaluation data is empty or every symbol fails to fetch, both regime
   pipelines return a normal, error-free "Indecisive"/"Sideways, confidence 0" result — a full
   exchange-API outage is indistinguishable from a genuinely quiet market. No flag reaches the
   client.

🧱 Scope

Backend (Go):
- `domain/scoring/sideways_v5_score_calculator.go` — fix the duplicated regression call
- same bug pattern check in `quickStructure` (same file, flagged as duplicated logic)
- `application/market/market_state_service.go` / `application/market/metrics/metrics_service.go`
  — surface a `DataQuality` (or similar) field on `Summary` when the input evaluation set is
  empty or below a sane minimum symbol count, instead of silently returning a confident-looking
  zero-confidence state
- `adapters/http/market_state_handler.go` (or `market_regime_handler.go`, depending on outcome

Frontend (Flutter):

- `market_pulse_screen.dart` / `market_state_dialog.dart` — show a distinct "data unavailable"
  state (not the same visual as a legitimate "Indecisive" reading) when the flag is set

1️⃣ Fix the regression bug

`sideways_v5_score_calculator.go` already computes separate `highsIdx`/`lowsIdx` index lists
earlier in the same function (used for `peakSlope`/`troughSlope` a few lines up) — the bug is
that the channel fit below ignores both and rebuilds a third, combined `extremaIdx` list
instead:
```go
// before (both boundaries fit through the SAME combined, re-indexed candle list)
extremaCandles := make([]domain.Candle, len(extremaIdx))
for i, idx := range extremaIdx {
    extremaCandles[i] = candles[idx]
}
upperSlope, upperIntercept := linearRegression(extremaCandles)
lowerSlope, lowerIntercept := linearRegression(extremaCandles)

// after — reuse the highsIdx/lowsIdx already computed above, and the existing
// regressionThroughHighs/regressionThroughLows helpers from
// compression_score_calculator.go (same package, don't reimplement)
upperSlope, upperIntercept := regressionThroughHighs(candles, highsIdx)
lowerSlope, lowerIntercept := regressionThroughLows(candles, lowsIdx)
```
Note why `extremaCandles` (a compacted, re-indexed slice) was itself part of the bug, separate
from the highs/lows mixing: `regressionThroughHighs`/`Lows` use `float64(idx)` — the
candle's *original* chronological position in `candles` — as the regression's x-coordinate.
Rebuilding a compacted `extremaCandles` slice and fitting `linearRegression` (which uses the
compacted slice's own `0..n` position as x) silently shifts every point's x-coordinate away
from its true chronological spacing. Fitting straight off `candles` + the original index list,
as above, avoids reintroducing that on top of the highs/lows mixing fix.
`quickStructure` (same file, ~line 573) has the identical pattern — fix it the same way.

2️⃣ Data-quality flag
```go
// domain/market/market_state.go
type Summary struct {
    // ...existing fields
    DataQuality DataQuality
}

type DataQuality string
const (
    DataQualityOK      DataQuality = "ok"
    DataQualityDegraded DataQuality = "degraded" // fewer symbols than expected, some fetch failures
    DataQualityUnavailable DataQuality = "unavailable" // zero usable evaluations
)
```
```go
// application/market/market_state_service.go
if len(evaluations) == 0 {
    return mkt.Summary{
        Timeframe:   timeframe,
        State:       mkt.StateSideways,
        DataQuality: mkt.DataQualityUnavailable,
        // ...
    }, nil
}
// Static threshold, not a new EvaluationProvider.ExpectedSymbolCount method —
// EvaluationProvider (application/market/evaluation_provider.go) has exactly one method
// today (GetLatestEvaluations); adding a second would mean implementing it on every real
// provider AND every test fake for a number that's really just "the usual universe size",
// which doesn't change per-call. A package-level const (or a field on
// MarketStateService set at construction) is simpler and avoids the interface churn.
const expectedSymbolCount = 150 // tune from the real universe size, not a guess kept forever
quality := mkt.DataQualityOK
// 2*n < expected, not n < expected/2 — integer division floors, so with an odd
// `expectedSymbolCount` the /2 form under-flags right at the boundary (e.g. expected=151:
// expected/2==75, so n==75 reads as "not degraded" even though 75 is less than half of 151).
if 2*len(evaluations) < expectedSymbolCount {
    quality = mkt.DataQualityDegraded
}
```
(Exact threshold for "degraded" is a judgment call — start conservative, e.g. less than half
the usual universe size, and tune from real outage telemetry rather than guessing precisely.)

📝 Addendum 2 — CR follow-up (scale-mismatch blocker, production-rollout risk, telemetry)

**Blocker: `stddevFromLine`'s x-axis didn't match the new fit basis — confirmed and fixed.**
The regression fix switched `upperSlope`/`upperIntercept` to `regressionThroughHighs(candles,
highsIdx)`, which fits against each point's real chronological index. `deviationScore`'s
`stddevFromLine(extremaCandles, upperSlope, upperIntercept)` call was left evaluating at the
*loop position* within the compacted `extremaCandles` slice (0..n-1) instead — the two disagreed
on what "x" meant for the same line, inflating measured deviation for anything but tightly-packed
extrema. Verified empirically before fixing: reintroduced the mismatch and confirmed every
existing test, including this PR's own `TestDetectSidewaysV5_NonParallelChannel`, still passed —
none of them are sensitive to this failure mode (most real "sideways" channels have near-zero
slope, where `predicted ≈ intercept` regardless of which x is used, masking the bug; the
black-box `NonParallelChannel` test only asserts relative ordering, which the mismatch distorts
symmetrically). Fixed by giving `stddevFromLine` an explicit `indices []int` parameter so the
evaluation basis always matches whatever basis the line was fit on — both call sites (`
DetectSidewaysV5` and `quickStructure`) now pass `extremaIdx` alongside `extremaCandles`.
Added `domain/scoring/sideways_v5_internal_test.go` (`package scoring`, not the `tests/`
external-package convention this repo otherwise uses everywhere) — a deliberate, narrow
exception: this bug class is only reliably testable at the unexported-function level with known
slope/intercept/spacing, exactly as the CR suggested, and no realistic black-box scenario through
the full `DetectSidewaysV5` pipeline reliably discriminates it (confirmed by trying several
before settling on the direct unit test). The test asserts ~0 deviation for points placed exactly
on a nonzero-slope line at widely-spaced real indices, and includes a self-check that evaluating
the same points at compacted indices does *not* read as ~0 — so the test itself would fail loudly
if it stopped being sensitive to a reintroduction of this exact bug.

**Major: production blast radius from the CCS fix.** The CR's specific claim (this feeds
`SuppressSidewaysThreshold`) doesn't hold up — `SuppressSidewaysThreshold` (`config.go:121`,
`config.yaml:84`, defaulted to `0.7`) has zero consumers anywhere in the code; it's unused
configuration, not a live gate. The underlying concern is still real, though: `SidewaysV5ScoreCalculator`
is one of three equally-weighted (1.0 each) calculators feeding the main composite ranking score
(`cmd/api/main.go:140-144`, alongside Trend Predictability and Gain/Loss), so this fix does shift
1/3 of every symbol's ranking score, for every symbol, on every ranking run — with no historical
data available in this environment to measure the shift's real-world magnitude before shipping.
Surfaced this tradeoff directly rather than silently shipping or silently blocking: the person
who owns this app chose to ship now and monitor rather than stage behind a flag, reasoning that
the fix corrects a uniform distortion (parallelScore was inflated to the same 1.0 for essentially
every symbol alike, not a random one), so relative ranking order is less likely to reshuffle
dramatically than an absolute-threshold change would. Added a `log.Printf` inside
`DetectSidewaysV5` reporting the final Score and all five components (CCS/OQS/DCS/VOS/SRM) on
every call — this replaces three pre-existing, unconditional `fmt.Fprintf(os.Stderr, ...)` debug
dumps (noisy, unstructured, inconsistent with the rest of the codebase's `log.Printf` convention)
with one line that's actually useful for observing the post-fix distribution in production, which
is the concrete ask behind "monitor after deploy."

**Major: `expectedSymbolCount` telemetry and per-timeframe variance.** Added a `log.Printf` in
`MarketStateService.Calculate`, timeframe-tagged, whenever `DataQuality != ok` — logs the actual
evaluation count against the expected constant. Deliberately not unconditional: `Calculate` is
called from `/api/market/state` (a live per-request HTTP path per the PR-073 CR round) and from
scheduler/setup loops, so logging on every single call — including the steady-state OK case —
would be materially noisier than the existing app's logging conventions elsewhere. This means the
telemetry captures *when and how badly* degradation trips, not the full healthy-baseline
distribution — a real limitation, noted rather than silently claimed as fully solved.
Per-timeframe variance: `RankingsEvaluationProvider.GetLatestEvaluations` runs the ranking
pipeline over the same `cachedUniverse` for every timeframe (`infrastructure/market/
rankings_evaluation_provider.go`) — structurally there's one shared symbol universe, not a
per-timeframe list, so a persistent skew would only come from per-symbol candle-fetch failures at
specific timeframes (e.g. newly-listed symbols lacking longer-timeframe history), not a
by-design difference. This is a code-reading conclusion, not something verified against live
data — flagged as moderate- rather than full-confidence.

**Minor concerns:**
- The `2*n < expected` vs `n < expected/2` boundary comment was previously untested — added
  `TestMarketStateService_Calculate_DataQuality_ExactlyHalf_Boundary`, pinning both `n ==
  expectedSymbolCount/2` (75, must read OK) and `n == expectedSymbolCount/2 - 1` (74, must read

- `isDataUnavailable` was duplicated verbatim across `market_state_data.dart` and

- `DataQualityDegraded` getting no UI treatment, and `market_state_dialog.dart` only

📝 Addendum 3 — follow-up on the new `[SidewaysV5]` score log's volume

Flagged after the CR round closed: the score/component `log.Printf` added in Addendum 2 is
per-symbol inside the ranking pipeline (~150 symbols per refresh). Rankings are Redis-cached
(`rankingsCacheTTL`, 3 minutes by default, `cmd/api/main.go`), so this isn't per-HTTP-request as
initially worried — `RankingsEvaluationProvider` reads through the cached `rankingsUC` — but a
full unconditional per-symbol log would still burst on every cache refresh, across however many
timeframes are actively polled. Changed to a ~5% random sample
(`sidewaysV5LogSampleRate`, `rand.Float64()` — the default global `Source` is safe for concurrent
use, so no locking needed for this). A representative sample is actually a better fit for the
stated goal (observe the Score *distribution*) than logging every single symbol would have been,
not just a volume compromise.
