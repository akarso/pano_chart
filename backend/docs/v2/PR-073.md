## PR-073: refactor(market): unify dual regime-classification pipeline
🎯 Objective

The codebase runs two independently-evolved market classifiers that can disagree on the same
market at the same instant:

| | `MetricsService.CalculateRegime` | `MarketStateService.Calculate` |
|---|---|---|
| Result type | `RegimeSummary` / `RegimeScores` | `Summary` / `Breadth` |
| Breadth source | fresh re-scoring of raw candle windows, market-wide average | per-symbol `EvaluationSnapshot`, proportionally split |
| Normalization | softmax, temperature=4.0 | proportional weighting |
| Indecisive gap threshold | 20pp (`regime_detector.go`) | 30pp (`market_state_service.go`) |
| Consumers | notification scheduler, setup scanner (`/api/market/regime`) | `/api/market/state` HTTP endpoint |

This grew from two branches independently bolting the same "trend health" and
"indecisive/silent override" features onto two different base systems (confirmed during the
recent `feature`→`dev`→`main` merge). Users hitting different endpoints/notification paths can
get contradictory regime readings for the same moment — this is not a hypothetical, the two
pipelines use different inputs and different math, they *will* diverge.

Depends on **PR-072** landing first — no point unifying around a pipeline that still has the
direction bug.

🧱 Scope

Backend only (Go), and this is the largest single PR in the roadmap — consider splitting into
073a (pick + wire the canonical pipeline) / 073b (delete the other) if review load is a
concern, but land 073a and 073b in the same release so there's no window with a partially-
migrated state.

Decision needed before writing code (flag to product owner, don't just pick one silently):
which pipeline becomes canonical. Recommendation: **`MarketStateService`/`Summary`/`Breadth`**,
because:
- it already reuses real per-token evaluation data (`EvaluationSnapshot`) rather than
  re-scoring candles from scratch — cheaper, and single-sourced with whatever the
  overview/rankings pipeline already computed
- `AggregateActivityMetrics` (the silent-state detector) is already correctly exported and
  reused from here by `metrics_service.go` today — the dependency direction already points
  this way
- the softmax approach in `regime_detector.go` has a tunable-magic-number smell
  (`temperature = 4.0`, hand-picked evidence weights) that's harder to reason about and test
  than the proportional-weighting approach

1️⃣ Collapse the type
- `mkt.RegimeSummary`/`mkt.RegimeScores`/`mkt.Regime` → deleted; `mkt.Summary`/`mkt.Breadth`/
  `mkt.State` become the only market-state vocabulary in the codebase
- `MetricsService.CalculateRegime` → deleted; anywhere it's called switches to
  `MarketStateService.Calculate`

2️⃣ Re-point every consumer
- `application/notifications/scheduler.go` — `MarketProvider` interface goes back to
  `Calculate(timeframe string) (mkt.Summary, error)` (this is exactly what PR-072's `Bias`
  field addition should target — add it to `Summary`, not to a type about to be deleted)
- `application/setups/service.go` — same
- `adapters/http/market_regime_handler.go` (`/api/market/regime`) — re-point to
  `MarketStateService`, or merge this endpoint into `/api/market/state` outright and mark
  `/api/market/regime` deprecated (check `frontend/lib` for which endpoint the client actually
  calls before deciding — no point keeping two live HTTP routes for one concept). Field
  mapping from the current `RegimeSummary`-based response, so nothing silently vanishes from
  the JSON contract:
  - `Prevalence` → `Confidence` (same concept, renamed)
  - `Scores` (Expansion/Compression/Trend/Sideways) → `Breadth` (same four values, renamed)
  - `Bias`, `EffectiveTrend`, `BreakdownRate`, `Label` → same-named fields already on
    `Summary` (backported in the PR-063 trend-health work) — straight passthrough, and this
    is exactly where PR-072's new `Bias` field lands
  - `Metrics` (`TrendBreadth`/`SidewaysBreadth`/`CompressionBreadth`/`ExpansionBreadth`/
    `VolatilityExpansion`/`Dispersion`) → **no equivalent on `Summary`.** `MarketStateService`
    never computed these — they're specific to the softmax pipeline being deleted. If
    anything (frontend or otherwise) reads `metrics.volatility_expansion` /
    `metrics.dispersion` today, dropping them is a real breaking change to this endpoint, not
    a rename. Confirm via the frontend check in 4️⃣ before deciding whether to drop them
    silently, keep a deprecated `metrics` block computed a different way, or block this PR on
    a coordinated API version bump.
- `cmd/api/main.go` composition root — `metricsService` wiring for regime purposes removed;
  confirm nothing else still depends on `MetricsService` for non-regime concerns (it also does
  breadth/composite-index work — only the regime-detection slice is being deleted, not the
  whole service, check call sites carefully)

3️⃣ Threshold reconciliation
Pick one number for the indecisive gap (recommend keeping the 30pp/`market_state_service.go`
value — it was the more conservative of the two, less prone to flapping between indecisive and
a real regime) and delete the 20pp softmax-based one along with `regime_detector.go`.

4️⃣ Frontend impact check
Before merging, grep `frontend/lib/` for any call to `/api/market/regime` specifically (vs
`/api/market/state`) and any Dart model shaped around `RegimeScores`/`Scores.Expansion` etc. —
this PR is backend-only in code scope but the HTTP contract for `/api/market/regime` may change
or disappear, which needs a coordinated frontend PR if that endpoint is still called anywhere.

5️⃣ Tests
- Delete `tests/application/market/regime_test.go`'s coverage of the deleted pipeline; verify
  `tests/application/market/market_state_test.go` and `transition_test.go` cover the same
  scenarios (indecisive gap, silent override, breakdown) that the deleted tests exercised —
  don't lose coverage in the collapse, migrate the meaningful cases.
- Add one test asserting `/api/market/regime` and `/api/market/state` (if both still exist as
  routes) return `State`/consistent values for the same underlying data — this is the
  regression test that would have caught the original divergence.

🚀 Result

- One market classification, one set of thresholds, one place to fix bugs like PR-072/PR-074
  going forward instead of two.
- Eliminates the specific failure mode of "the app told me two different things about the same
  market."

📝 Addendum — as actually implemented

Decision on the `Metrics` block (flagged to the product owner before coding, per this doc's own
instruction): **add VolatilityExpansion/Dispersion to `MarketStateService`/`Summary`**, not drop
the "Market Metrics" card or fork the endpoints. Concretely:

- `MarketStateService` gained an *optional* `CandleProvider` dependency
  (`SetCandleProvider`, same pattern as `SetupService.SetMarketProvider`/`SetFragilityProvider`)
  used only to compute `VolatilityExpansion` (median short/long ATR ratio) and `Dispersion`
  (MAD of period returns vs. the mean market return) — both genuinely need raw candle history
  (ATR needs multi-window OHLC, dispersion needs real percentage returns to stay calibrated
  against the frontend's existing 0.02/0.05 thresholds), which `EvaluationSnapshot` doesn't
  carry. Without a `CandleProvider` configured, these two fields default to 1.0/0 and
  `Calculate` remains fully usable — every existing `MarketStateService` test still constructs
  it with zero args, unchanged.
  - Considered and rejected: deriving `Dispersion` from `EvaluationSnapshot.RecentReturn`
    directly (zero extra fetches). Rejected because `RecentReturn` is documented as "return in
    ATR units", a completely different scale than the plain percentage returns the frontend's
    `_dispersionLabel`/`_dispersionColor` thresholds (0.02/0.05) are calibrated against — reusing
    it would have silently miscalibrated every dispersion reading in the UI without breaking
    anything loudly enough to notice, the exact kind of semantic drift prior CR rounds
    (PR-072) flagged repeatedly.
  - `volatility_metric.go`/`dispersion_metric.go` were moved verbatim from
    `application/market/metrics` into `application/market` (package rename only, same
    functions) rather than duplicated.
- `mkt.RegimeSummary`/`RegimeScores`/`RegimeMetrics` are deleted as planned. **`mkt.Regime` and
  its six constants are kept, not deleted** — after removing `RegimeSummary`/`RegimeScores`,
  `Regime`'s only remaining role is as the persisted label in `regimehistory` (SQLite column,
  `Tracker.Update`, `RegimePeriod`) and in `transition`'s pressure math
  (`TransitionEngine.Calculate(regime mkt.Regime, ...)`). Both are just "label + math", not a
  second classification pipeline, and `Regime`'s values are string-identical to `State`'s — a
  full rename to `mkt.State` throughout `regimehistory`/`transition`/the SQLite schema would
  have been a substantial mechanical change (new package, new column semantics to reason about)
  for zero behavior difference. `MarketStateService.Calculate` notifies the (renamed, now
  service-owned) `RegimeObserver` with `mkt.Regime(dominant)` — a one-line, lossless cast at the
  boundary where the two vocabularies meet.
- `MetricsService`, `regime_detector.go`, `breadth.go` (candle-rescoring breadth), and
  `Backfiller` are deleted entirely — confirmed via full call-site audit that `MetricsService`
  had no responsibility beyond `CalculateRegime` (the `compositeService` field it held was
  dead weight; `/api/market/composite` is wired directly off `CompositeIndexService`,
  independent of `MetricsService`, both before and after this change).
- **Regime-history backfill (`main.go`'s "runs once when DB is empty" block) was removed, not
  reimplemented.** `Backfiller` worked by re-simulating history over sliding windows of raw
  candles using the softmax pipeline's `detectRegime`/`scoreBreadthFromCandles` — there is no
  equivalent for the proportional pipeline, since it classifies from `EvaluationSnapshot`
  (latest-only, no historical time series) rather than re-scoring arbitrary past candle
  windows. Reimplementing backfill against the new pipeline would mean re-deriving historical
  evaluation-equivalents from raw candles, which is a materially bigger undertaking than this
  PR's scope. This only affects a *fresh* `regime_history.sqlite` (new environment or DB wipe)
  — the existing production DB already has real history from when backfill last ran, and going
  forward, history accumulates live from every `Calculate()` call via the unchanged
  `RegimeObserver`/`Tracker` path. Flagged here rather than silently dropped.
- Threshold reconciliation (§3, 20pp vs. 30pp indecisive gap) resolved itself: deleting
  `regime_detector.go`'s `applyIndecisiveGuard` (20pp) leaves `MarketStateService`'s existing
  30pp gap as the only implementation — no code change needed beyond the deletion.
- Endpoints: **kept both `/api/market/regime` and `/api/market/state` as separate routes**,
  both now backed by the same `*MarketStateService` instance — confirmed via
  `frontend/lib/features/market_state/http_regime_api.dart` and `http_market_state_api.dart`
  that the Flutter client actively calls both, so merging them would have required a
  coordinated frontend change out of scope here. `market_regime_handler.go` maps
  `mkt.Summary` onto the pre-existing `regimeResponse` JSON shape byte-for-byte (`Metrics`'
  four breadth sub-fields now mirror the single `Breadth` computation instead of a second one)
  — zero frontend changes needed; `TestRegimeAndStateHandlers_AgreeOnSameSummary` asserts both
  endpoints report the same `state`/`bias` for the same underlying `Summary`, which is the
  actual regression test for the bug this PR fixes.
- Tests: `tests/application/market/regime_test.go` and `backfiller_test.go` (100% about the
  deleted pipeline) were deleted; `TestDetectRegime_Dispersion` and
  `TestMetrics_VolatilityExpansion_InsufficientData`'s scenarios were ported to
  `market_state_metrics_test.go` against the new `SetCandleProvider` path, and the handler
  tests were ported to `regime_handler_test.go` against the new `mkt.Summary`-based fake.
  `transition_test.go`/`regime_history_test.go`'s `fakeTransitionRegimeProvider` was updated to
  the new `RegimeProvider.Calculate(timeframe) (mkt.Summary, error)` shape;
  `notifications/scheduler_test.go` and `config_test.go`'s `mkt.RegimeSummary` fixtures were
  mechanically converted to `mkt.Summary`/`mkt.Breadth`/`mkt.State`.

📝 Addendum 2 — CR follow-up round (threshold recalibration, cost/ctx regressions)

**Blocker: notification thresholds unreachable under the new scale.** Confirmed empirically
(synthetic evaluation mixes through the real `MarketStateService`): a quiet market's
`Breadth.Trend` sits around 0.15, a mixed market around 0.23, a realistic *strong* trending
market (50% of the symbol universe clearly trending) around 0.43 — and the overall `State` still
resolves to `indecisive` at that point, because the 30pp dominance-gap guard is also harder to
clear once breadth is averaged across the whole universe rather than pushed toward extremes by
the deleted softmax pipeline (`temperature=4.0`). `0.75` was reachable only in an unrealistic
"~100% of the market trending in unison" scenario. Fixed two ways, together (fixing only the
number without the second change would still have left this broken):
- `UptrendMinDominance`/`DowntrendMinDominance`/`SidewaysMinDominance`
  (`notifications.DefaultNotificationConfig`) and `MarketMinConfidence`
  (`notifications.DefaultSchedulerConfig`) changed from 0.75 to 0.35 — comfortably above the
  quiet/mixed noise floor (0.15–0.25), reachable by a genuinely trending market (0.4+).
- Existing per-user configs get these three fields reset via `SQLiteConfigStore`'s
  `config_version` migration (bumped to 2) — the same mechanism introduced in PR-072 for
  `DowntrendMinDominance` alone, now covering all three fields for the same reason: a value
  tuned against a metric that no longer exists carries no information under the new one.
- The `Uptrend`/`Downtrend` branches in `scheduler.go` no longer additionally require
  `sum.State != mkt.StateIndecisive` — that gate gave `Breadth.Trend` a market-wide dominance bar
  to clear on top of its own threshold, and per the measurement above, a real strong trend
  clears `Breadth.Trend >= 0.35` while still resolving to `indecisive` overall. `Bias` (already
  the canonical, purpose-built direction signal per PR-072) plus the per-regime dominance
  threshold is sufficient; `State`'s indecisiveness is a whole-market classification concern,
  not a per-regime one. `Sideways` keeps its indecisive gate — out of scope for this fix, since
  sideways/indecisive largely overlap conceptually and it wasn't reported as broken.
- Added `TestScheduler_RealisticStrongTrendMarket_FiresUptrend`
  (`tests/application/notifications/realistic_pipeline_test.go`): runs the real
  `MarketStateService` over a synthetic-but-plausible 100-symbol mix (not a hand-picked
  `mkt.Summary` fixture) through the real `Scheduler`, and asserts the notification actually
  fires — the end-to-end sanity check the CR round asked for.

**Major: `/api/market/state` got significantly more expensive, and request-scoped cancellation
was lost.** Both were true, and both had the same root cause: `Calculate` was doing the full
candle-based `VolatilityExpansion`/`Dispersion` fan-out (bounded 20-way concurrent
`GetLastNCandles`, 110 candles, whole symbol universe) unconditionally whenever a
`CandleProvider` was configured — which happens once, globally, on the single shared
`MarketStateService` instance — even though only two of five consumers
(`/api/market/regime`, the transition engine) ever read those two fields. `/api/market/state`,
the notification scheduler, and the setup scanner all paid for it despite never using it, and
the setup scanner's per-symbol evaluation loop meant paying for it once per symbol scored.
Fixed by splitting the method:
- `Calculate(timeframe string) (mkt.Summary, error)` — unchanged signature, now *never* touches
  the `CandleProvider`; `VolatilityExpansion` stays at its 1.0 default. This is what
  `/api/market/state`, the scheduler, and the setup scanner use — restoring their pre-PR-073
  cost profile exactly, and eliminating the setup-scanner's per-symbol compounding as a direct
  side effect (it never triggers the fan-out at all now).
- `CalculateWithCandleMetrics(ctx context.Context, timeframe string) (mkt.Summary, error)` —
  calls `Calculate` and additionally computes the two candle-derived fields. This is what
  `/api/market/regime`'s handler and the transition service use, and it takes a `ctx` that
  bounds the candle fan-out — restoring the cancellation propagation that was lost when
  `CalculateRegime(ctx, tf)` collapsed to a context-less `Calculate(tf)` earlier in this PR.
  `RegimeCalculator`/`transition.RegimeProvider` were re-pointed at this method name so
  `*MarketStateService` satisfies both interfaces (the cheap one via `Calculate`, the rich one
  via `CalculateWithCandleMetrics`) without a wrapper type.
- Added `TestMarketStateService_Calculate_SkipsCandleFanoutEvenWithProvider`, asserting
  `Calculate` never calls `CandleProvider.Symbols` even when one is configured.
- Not done: caching/memoizing `candleMetrics` per-timeframe (suggested as a "consider"). With
  the split above, the only remaining callers of the expensive path are two per-request HTTP
  handlers (`/api/market/regime`, `/api/market/transition`), not a tight loop — the systemic
  multiplication this CR flagged is gone. A short-TTL cache would still shave duplicate work if
  both endpoints are hit for the same timeframe close together, but that's a much smaller,
  request-scoped optimization than what prompted the finding; left for a future pass if it
  turns out to matter in practice.

**Minor concerns, all addressed:** `candleMetrics` now logs `Symbols()`/timeframe-parse
failures instead of silently defaulting forever; the `RegimeObserver.Update` error is now
logged instead of discarded; the empty-evaluations early return in `Calculate` now has a
one-line comment explaining why it skips the observer notification (no data ≠ an observation);
the bounded-parallelism limit is now a named constant (`candleMetricsFanoutLimit`) instead of a
bare `20`.

**Backfill operational gap:** added a startup-time warning log in `main.go` — if
`regime_history.sqlite` has no periods yet for `1h`/`4h`/`1d` (a fresh DB, since backfill no
longer runs), it's now logged loudly once at boot instead of silently starting empty with
nothing to notice it.

📝 Addendum 3 — CR follow-up (cancellation, legacy display semantics, method size)

**Cancellation left in-flight fetches blocking the caller.** Valid — the previous round's
`ctx.Done()` check only stopped goroutines still queued for a concurrency-limiter slot; anything
already past it and inside `GetLastNCandles` (a repo-wide interface with no `context.Context`
parameter at all — `RedisCandleRepository`, `FreeTierCandleRepository`, and
`CompositeCandleProvider` all lack one, not something specific to this PR) could not be aborted,
and `wg.Wait()` still waited for it unconditionally. True mid-flight cancellation would require
threading `context.Context` through `GetLastNCandles` everywhere it's implemented and consumed
across the whole candle-fetching subsystem — well beyond this PR's scope. Fixed the part that
is in scope: `candleMetrics` (split into `fetchCandleResults` + `aggregateCandleResults`, see
below) now races the fetch completion against `ctx.Done()` and returns to the caller as soon as
either happens, rather than always waiting for every goroutine. A straggler fetch still runs to
completion in the background — its result is simply discarded — but the HTTP handler is no
longer held open for it.
`TestMarketStateService_CalculateWithCandleMetrics_CancelledContextReturnsPromptly` covers this
with a `CandleProvider` whose `GetLastNCandles` blocks forever, asserting the call still returns
within a couple of seconds once its context is cancelled.

**Legacy `/api/market/regime` score semantics changed shape.** Valid observation, not a defect:
`scores` still sums to ~1.0 (proportional `Breadth` is normalised same as the deleted softmax
output was), so the JSON contract and the Flutter client's parsing are both intact — nothing
crashes or misparses. What changed is the *distribution shape* the numbers describe: the deleted
softmax pipeline (`temperature=4.0`) pushed the dominant regime toward the extremes (e.g.
75/10/8/7), while the proportional pipeline averaged across the whole symbol universe is
structurally flatter (e.g. 44/20/17/19 for a realistic strong-trend market — see Addendum 2's
measurements). Checked the actual Flutter rendering
(`frontend/lib/features/market_state/market_pulse_screen.dart`): each regime gets its own
independent progress bar and `%` label (`_regimeScoreBar`), not a pie/stacked chart whose
correctness depends on the old spiky shape, and no threshold logic in the client branches on
score magnitude — so this is a display/perception change (the same real market now "looks" less
dramatic), not a functional break. Not fixed, and not a good candidate for fixing: the only way
to make `scores` "look" spiky again would be applying a second, display-only rescaling on top of
`Breadth` — reintroducing exactly the "one field, two different numbers depending which endpoint
you ask" problem this PR exists to eliminate (`/api/market/state`'s `breadth` would then
disagree with `/api/market/regime`'s `scores` for the identical underlying data). Flagged here
for product-owner visibility rather than silently absorbed — worth a deliberate follow-up
Flutter design pass if the flatter numbers read badly in practice, but not a backend fix.

**`candleMetrics` mixed responsibilities.** Valid and fixed: split into
`fetchCandleResults(ctx, candles, tf, symbols) (results []candleResult, cancelled bool)`
(orchestration — concurrency, retrieval, cancellation) and
`aggregateCandleResults(results []candleResult) (volExpansion, disp float64)` (pure arithmetic,
no I/O). `candleMetrics` itself is now a thin sequence: validate timeframe → load symbols →
fetch → aggregate. This is also what made the cancellation fix above straightforward to express
and test.
