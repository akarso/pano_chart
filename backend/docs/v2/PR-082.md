## PR-082: feat(backend): fold intraday volatility seasonality into setup confidence

🎯 Objective

`infrastructure/volatility` already computes real historical time-of-day and day-of-week
volatility seasonality (average move + spike probability per minute-of-day/week — see
`aggregate.go`, `derive.go`, `weekly.go`), served live via `adapters/http/volatility_handler.go`
to its own frontend feature (`frontend/lib/features/volatility/`). It is entirely disconnected
from `application/setups`: `ComputeConfidence` and `VolatilityFit` only ever see *realized*
volatility computed from the last N candles (`volatilityFromSeries`, PR-080) — a purely backward-
looking measure. A trader has to manually cross-reference the volatility chart against a setup's
confidence score today; the app already has the data to do that automatically.

The specific gap this closes: realized volatility from the last N candles cannot see a spike that
hasn't happened yet. A setup can look calm and well-formed by every candle-derived measure while
sitting fifteen minutes before a funding settlement or a US-session open the historical seasonality
data already knows is statistically dangerous. Folding that forward-looking read into confidence
directly serves the "low risk" half of the app's premise, the same way PR-081 does for crowding.

🧱 Scope

Backend only (Go):
- `application/setups/setup_context.go` — new `SetupContext` field
- `application/setups/confidence.go` — `ComputeConfidence` gains a new weighted input
- `application/setups/service.go` — wire a volatility-seasonality source into `buildContext`
- `application/setups/service.go` — new `SeasonalityProvider` interface (optional dependency,
  same pattern as `MarketProvider`/`FragilityProvider`: nil means "no seasonality adjustment",
  not an error)
- `cmd/api/main.go` — wire `SetupService.SetSeasonalityProvider` to the existing
  `VolatilityHandler`'s loaded data (or a small adapter over it)

1️⃣ Scoping caveat to state up front

`cmd/vol_aggregate` currently computes seasonality for a single hardcoded symbol (`BTCUSDT`) — see
`cmd/vol_aggregate/main.go`. This PR should apply that curve as a **market-wide** timing signal
("is right now historically a dangerous time to hold *any* crypto position open"), not a per-symbol
one — which is a defensible simplification (crypto volatility clustering around funding settlements
and session opens is largely market-correlated), but must be documented as a known limitation, not
silently implied to be per-symbol. Extending `vol_aggregate` to multiple symbols is out of scope
here.

2️⃣ New signal: `SeasonalityRisk`

```go
// SeasonalityProvider returns the current spike-probability bucket for
// "right now", from the precomputed intraday/weekly volatility model.
type SeasonalityProvider interface {
	CurrentSpikeProbability(ctx context.Context, timeframe string) (float64, error)
}
```

Backed by `vol.FullResult`'s already-computed `SpikeProb` per minute-of-day bucket (see
`BucketResult.SpikeProb` in `infrastructure/volatility/model.go`) — look up the bucket matching
`time.Now()`'s minute-of-day (or minute-of-week, for the weekly result) at the timeframe closest to
the one requested (`DeriveTimeframe` in `derive.go` already produces 5m/15m/1h/4h buckets from the
1m base). No new computation, just a lookup into data that already exists.

3️⃣ Confidence integration

Add `SeasonalityRisk float64` to `SetupContext` and `SeasonalityFit float64` to `setup.SetupScores`
(0-1, mirroring `VolatilityFit`'s shape — `1 - clamp(spikeProb / referenceSpikeProb)`, i.e. high
historical spike probability right now → low fit). Extend `ComputeConfidence`'s per-regime weight
maps (`confidence.go`) with a `"seasonality"` entry, rebalancing the existing weights rather than
just adding a fifth unweighted input — e.g. sideways currently spends 30% on `volatility`; splitting
that regime's volatility-related budget between realized (`VolatilityFit`) and forward-looking
(`SeasonalityFit`) is more defensible than tacking on a fifth independent weight nobody has reasoned
about yet. Exact split is a tuning decision to make during implementation, not something to lock in
this spec.

4️⃣ Graceful absence

Like `MarketProvider`/`FragilityProvider`, `SeasonalityProvider` is optional — nil disables the
adjustment (weight redistributes to the remaining components, or `SeasonalityFit` defaults to a
neutral 0.5, matching `VolatilityFit`'s own "unknown regime" default) rather than failing the whole
`Evaluate` call. The existing `VolatilityHandler` already has a "data not loaded yet" failure mode
(`DATA_UNAVAILABLE`) — a `SetupService` wired to it must degrade the same way, not propagate that
as a setup-evaluation error.

5️⃣ Verification

- Unit tests for the minute-of-day/week bucket lookup (boundary cases: midnight rollover, week
  rollover, missing buckets).
- A `ComputeConfidence` regression test proving a setup with identical `TrendHealth`/
  `MarketEffective`/`Crowding`/`VolatilityFit` scores lower when `SeasonalityFit` reflects a known
  high-spike-probability window than when it doesn't — the actual point of this PR.
- Confirm existing `ComputeConfidence`/`VolatilityFit` tests in `tests/application/setups/confidence_test.go`
  still pass — most construct `setup.SetupScores` by hand and don't set the new field, so they
  should default it the same way a nil `SeasonalityProvider` would in production.

🚀 Result

- Setup confidence for every regime gains a forward-looking risk input the app already computes
  and shows to users, instead of leaving them to manually cross-reference two disconnected views
  before trusting a signal.

📝 Implementation notes

Implemented largely as designed, with two deliberate deviations from this doc's original sketch —
both made after actually looking at the surrounding code, not blind implementation:

**1️⃣ `SeasonalityFit` lives on `setup.SetupScores`, not `SetupContext`.** This doc originally
suggested adding `SeasonalityRisk` to `SetupContext` alongside the doc's other proposed field,
`SeasonalityFit` on `SetupScores`. Looking at how `MarketEffective` and `Crowding` — the two
existing externally-fetched, provider-based enrichments — are actually wired, neither lives on
`SetupContext` either: `SetupContext` holds only what's synchronously derivable from the candle
series itself (feeding `Engine.Evaluate`), while provider-fetched data is set directly on `result`
in `Evaluate`, after the engine has already run. `SeasonalityFit` fits that second category
exactly (fetched via `SeasonalityProvider`, not derived from candles), so it follows the same
pattern — no `SetupContext` changes at all.

**2️⃣ The lookup always uses 1-minute-of-day buckets, ignoring the requested timeframe.** The
`SeasonalityProvider` interface still takes a `timeframe` argument (for symmetry with
`MarketProvider`/`FragilityProvider` and future use), but `VolatilitySeasonalityProvider` doesn't
use it: `infrastructure/volatility`'s coarser derived timeframes (5m/15m/1h/4h — `DeriveTimeframe`)
group 1-minute buckets by array *position*, not by an explicit time range each resulting bucket
covers, so reliably matching "the bucket containing right now" against one of them would mean
reverse-engineering that grouping. The 1-minute data has no such ambiguity (`MinuteOfDay` means
exactly what it says) and is strictly finer-grained than any chart timeframe a caller might
request, so this is a simplification, not a loss of precision. Documented in both the interface
and the concrete provider's doc comments.

**Weight rebalancing.** Split each regime's existing "volatility" weight 2:1 between
`volatility` (realized) and `seasonality` (forward-looking) — sideways/compression's 0.3 became
0.2/0.1, trend's 0.1 became 0.07/0.03 — favoring the realized signal since it's a direct read of
actual recent price action, while seasonality is a coarser historical prior that (per this doc's
own §1 scoping caveat) is currently computed from a single reference symbol (BTCUSDT) applied
market-wide. Each regime's total weight distribution across trend/market/crowding/(volatility+
seasonality combined) is unchanged from before this split.

**`SeasonalityFit`'s shape is monotonic, not a bell curve.** Unlike `VolatilityFit` (a middling
value is ideal for trend/sideways), low spike probability is unconditionally better than high for
a forward-looking risk read — `SeasonalityFit(spikeProb) = clamp(1 - spikeProb/referenceSpikeProb)`,
a straight linear decay. `referenceSpikeProb` (0.3) is a provisional starting point, explicitly
labeled as such in the code comment — same honesty precedent as PR-080's provisional divisor,
revisit once real spike-probability distributions have been observed.

**Graceful absence, matching the doc's §4.** `result.SeasonalityFit` defaults to the neutral `0.5`
before checking whether a provider is even configured, then updates only on success — a nil
provider or a provider error both leave it at that default. This mirrors
`market.MarketStateService`'s existing "supplementary metric, failure must not fail the caller"
pattern for `VolatilityExpansion`/`Dispersion` more closely than it mirrors `FragilityProvider`'s
`ctx.Err()` escalation — that escalation exists specifically because `Crowding`'s zero default
would otherwise silently *maximize* crowding's contribution; `SeasonalityFit`'s neutral 0.5 default
carries no equivalent hidden failure mode, so no escalation was added.

**Wiring** (`cmd/api/main.go`): `VolatilityHandler` construction was hoisted from its mux
registration (further down `main`) to alongside the setup-engine wiring, so the same handler/cache
backs both `/api/volatility` and the new `VolatilitySeasonalityProvider` — no second independent
file read. Added `VolatilityHandler.CurrentResult()` (a thin exported wrapper around its existing
private `load()`) so the new provider can reuse that cache without reimplementing it.

**Verification.** New tests across three files:
- `tests/application/setups/confidence_test.go`: `SeasonalityFit` unit tests (ideal, at-threshold,
  beyond-threshold clamping, monotonic decrease) and a `ComputeConfidence` regression test proving
  lower confidence at high seasonality risk — the exact test this doc's §5 called for. Updated the
  three existing per-regime `ComputeConfidence` weight tests (`Trend_Weights`, `Sideways_Weights`,
  `Compression_Weights`) to the new split weights and added an explicit `SeasonalityFit` value to
  each, since their hand-written expected-value formulas hard-coded the old flat weights.
- `tests/adapters/http/volatility_seasonality_provider_test.go`: minute-of-day matching (built
  against the real clock rather than an injected one, matching every other `adapters/http` test
  file's external-black-box convention — no `now` override was added to the provider itself, since
  nothing in this package's test style could have used it), the "ignores timeframe, always 1m"
  simplification, missing-bucket and missing-1m-timeframe error cases, and source-error
  propagation.
- `tests/application/setups/service_test.go`: nil-provider default, successful-fetch computation,
  and error-degrades-gracefully-without-failing-Evaluate — verified the wiring test actually
  catches a regression by temporarily removing the `Evaluate` wiring and confirming
  `TestSetupService_SeasonalityProvider_ComputesFitFromSpikeProbability` failed (`SeasonalityFit`
  stuck at its neutral default instead of reflecting the fed-in spike probability); restored and
  confirmed green again.

**Full validation.** `go build ./...`, `go vet ./...` — clean. `go test ./... -race` (with
`go clean -testcache` first) — all packages pass, no data races, no regressions elsewhere.

📝 CR follow-up

**Major confirmed and fixed: weekly seasonality was never consulted.** `vol.FullResult.Weekly` was
computed and available but unused — a real scope gap this doc's own §5 originally anticipated
("minute-of-week bucket lookup... week rollover") but the implementation notes never called out as
skipped. Folded it in rather than just documenting the exclusion: `CurrentSpikeProbability` now
also looks up the current UTC minute-of-week (`dow*1440+minute`, matching
`BuildWeekly`/`DeriveDailyOfWeek`'s own convention in `infrastructure/volatility/weekly.go`) and
returns `max(dailySpikeProb, weeklySpikeProb)` rather than the daily reading alone. Max, not an
average: either signal being elevated — a historically dangerous minute-of-day, or a historically
dangerous day-of-week (weekend lull, Monday-open effects) — is reason for caution on its own, and
averaging would let a calm-looking one dilute a genuinely risky other. Weekly data is optional
(`Weekly.Buckets` can legitimately be empty, e.g. not enough history yet, or simply have no bucket
for the current minute-of-week) — falls back to the daily-only reading without failing the call.

**Major confirmed and fixed: `VolatilityHandler`'s cache had no refresh path.** Pre-existing gap
(the handler's `Reload()` method already existed, documented "call this after vol_aggregate runs",
but nothing ever called it) that this PR made more consequential by wiring the same stale snapshot
into every setup's live `Confidence`, not just a display endpoint. Checked `cmd/vol_aggregate`'s
own documentation (PR-059) before picking a fix: it's specified as a manually-triggered "one-time
script" with no fixed regeneration cadence, so there's no real interval to derive a reload schedule
from, and no existing admin/operator-only auth mechanism in this codebase to gate a
reload-triggering HTTP endpoint on (the one auth middleware here, `authMW`, is per-device user
auth, not appropriate for an ops trigger). Rather than inventing either an unfounded "real" cadence
or a new auth scheme disproportionate to this fix, added a conservative periodic ticker
(`volatilityReloadLoop`, 1 hour, in `cmd/api/main.go`) reusing the existing `socialCtx`/
`backgroundWG` graceful-shutdown machinery — picks up an out-of-band `vol_aggregate` re-run within
at most an hour, with `Reload()` failures logged rather than fatal (the handler keeps serving its
last-good cached snapshot either way).

**Minor confirmed and fixed: test raced `time.Now()` against a minute boundary.** Added
`NewVolatilitySeasonalityProviderWithClock(source, now func() time.Time)` alongside the existing
constructor (which still defaults to `time.Now`), and rewrote every test in
`volatility_seasonality_provider_test.go` to use one fixed, deterministic instant
(`2026-01-05T03:04:00Z`, a Monday — verified via `date -d`/Python, not assumed) instead of computing
"now" separately in the test and inside the provider.

**Minor confirmed and fixed: O(n) bucket scan.** Replaced the linear scan with a direct-index fast
path (`buckets[minuteOfDay]`, guarded by a `MinuteOfDay` equality check) falling back to a full scan
only when a data gap has shifted the array's alignment — `Aggregate` builds a dense, index-aligned
1440-slot array before filtering out empty minutes, so the fast path is expected to hit in the
common case. Applied the identical pattern to the new weekly lookup (`lookupWeeklyBucketSpikeProb`,
up to 10 080 slots). Added explicit tests for both paths: a dense fixture (proves the fast path
still returns the right value) and a fixture with a leading gap that misaligns index from
`MinuteOfDay` past that point (forces and proves the fallback scan).

**Verified, not just implemented.** Reverted the weekly fold-in and reran
`TestVolatilitySeasonalityProvider_WeeklySpikeHigherThanDaily_UsesWeekly` — failed with the daily-
only value (0.2) instead of the expected weekly one (0.8), confirming the test actually exercises
the fold-in rather than passing vacuously. Restored and confirmed green again.

**Full validation (this round).** `go build ./...`, `go vet ./...` — clean. `go test ./... -race`
(with `go clean -testcache` first) — all packages pass, no data races.
