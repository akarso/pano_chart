## PR-083: fix(payments): migrate Google Play verification to subscriptionsv2 + surface verification failures

🎯 Objective

Investigating a report of a real purchase (2-week trial, then a recurring monthly charge) completing
successfully in the Google Play purchase dialog, with the app returning to the main screen showing
no change at all — still "post-trial free version," no error, no confirmation, nothing.

Root cause: `infrastructure/googleplay/provider.go` verified purchases against
`purchases.subscriptions.get` (the "v3" flat `paymentState`/`expiryTimeMillis` shape) — the endpoint
Google announced as deprecated in November 2023 in favor of `purchases.subscriptionsv2.get`. A
failing verification call here means `/api/payments/verify` returns an error, which the frontend
(`BillingManager._verifyAndComplete`) only ever `debugPrint`'d — invisible outside a debug console,
with zero user-facing feedback. The two together produce exactly the reported symptom: the purchase
itself succeeds (that's Google Play's own UI, unrelated to this backend), verification against a
deprecated endpoint fails silently, and the user is left looking at an unchanged screen with no
indication anything went wrong.

🧱 Scope

Backend (Go):
- `infrastructure/googleplay/provider.go` — migrate `VerifyPurchase` from `purchases.subscriptions`
  to `purchases.subscriptionsv2`
- `tests/infrastructure/googleplay/provider_test.go` — rewritten for the v2 response shape

Frontend (Flutter):
- `lib/features/billing/billing_manager.dart` — new `lastVerificationError` field, set on any
  verification failure (thrown exception, or a technically-successful call that still doesn't leave
  the subscription active), cleared at the start of every new attempt and on success
- `lib/features/billing/upgrade_screen.dart` — surfaces `lastVerificationError` via a SnackBar
- `test/features/billing/billing_manager_test.dart` — new tests for the above

1️⃣ API migration

```
# before
GET /androidpublisher/v3/applications/{pkg}/purchases/subscriptions/{sub}/tokens/{token}
→ {"paymentState": 1, "expiryTimeMillis": "...", "startTimeMillis": "...", "orderId": "...", ...}

# after
GET /androidpublisher/v3/applications/{pkg}/purchases/subscriptionsv2/tokens/{token}
→ {"subscriptionState": "SUBSCRIPTION_STATE_ACTIVE", "startTime": "RFC3339", "latestOrderId": "...",
   "lineItems": [{"productId": "...", "expiryTime": "RFC3339"}], ...}
```

Notable shape differences, not just a URL rename:
- No subscription/product ID in the request path — v2 is token-only; the response's `lineItems`
  lists whatever product(s) the token actually covers.
- Timestamps are RFC 3339 strings, not millisecond-epoch strings.
- No separate free-trial payment state — v2 has one `subscriptionState` enum; a trial period reads
  as `SUBSCRIPTION_STATE_ACTIVE`, the same as a paid period.
- `subscriptionState` values treated as "a real, verifiable subscription" (mirrors the old
  `paymentState == 1 || 2` inclusion, `== 0` exclusion): `ACTIVE`, `IN_GRACE_PERIOD` (a renewal
  payment failed but Google is still retrying — access continues during this window), and
  `CANCELED` (auto-renew off, but the already-paid-for period hasn't ended). `PENDING`, `ON_HOLD`,
  `PAUSED`, `EXPIRED` are excluded. Whether this actually grants access *right now* is still decided
  downstream by `domain.Subscription.IsActive(now)` against the returned expiry time — this only
  decides whether the API gave back a real subscription record worth storing.

2️⃣ Frontend: surface verification failures

`_verifyAndComplete`'s `catch` block used to be `debugPrint`-only. Added `BillingManager
.lastVerificationError`, set on:
- a thrown exception from the verify call, and
- a *non-throwing* call whose resulting status still isn't active (the backend call succeeded but
  the purchase wasn't actually validated as active — a case the old code silently treated the same
  as full success).

`UpgradeScreen` shows this via a `SnackBar` the first time it appears after `onChanged` fires,
tracking what's already been shown so it doesn't re-fire on every unrelated `onChanged` (e.g.
`busy` toggling).

🚀 Result

- Backend purchase verification uses the API Google actually still supports, instead of one that's
  been documented as deprecated for going on three years.
- A verification failure is now visible to the user (with an actionable "try Restore purchases"
  hint) instead of silently leaving them on an unchanged screen with no explanation.

📝 Implementation notes

**What this does *not* rule out.** This investigation started from a single real incident report,
not a live reproduction — I have no access to this app's production server logs, its
`GOOGLE_PLAY_SUBSCRIPTION_ID`/`GOOGLE_PLAY_SERVICE_ACCOUNT_JSON` runtime configuration, or Google's
own current enforcement status for the deprecated endpoint (my knowledge cutoff is January 2026;
today is September 2026 per this session). The v3→v2 migration is unambiguously correct and worth
shipping regardless — using a Google-documented-deprecated endpoint is a real bug whether or not
it's the *specific* cause of this incident — but three other explanations remain equally possible
and are **not** ruled out by this PR:
- `GOOGLE_PLAY_PACKAGE`/`GOOGLE_PLAY_SUBSCRIPTION_ID`/`GOOGLE_PLAY_SERVICE_ACCOUNT_JSON` env vars
  missing or misconfigured server-side — `cmd/api/main.go` silently skips registering the provider
  entirely if any are absent (no fallback, just a log line), which would make every verification
  attempt fail with "provider lookup" — indistinguishable from an endpoint failure without server
  logs.
- The configured `SubscriptionID` not matching the real Play Console product ID.
- The service account's Play Console "financial data" permission being missing, revoked, or newly
  granted but not yet propagated.

All three would produce the identical user-visible symptom (silent no-op) that this PR's frontend
fix now at least makes *visible* — check the backend logs for the actual `/api/payments/verify`
error message (`verify_purchase.go`'s errors are already descriptive: `"provider lookup: %w"` vs.
`"verification failed: %w"` wrapping the real Google API response) to confirm which mechanism was
actually in play for this specific incident.

**Verified, not just implemented.** Backend: full `go test ./... -race` (fresh cache) — new v2-shape
tests cover ACTIVE/trial/grace-period/canceled-but-not-expired (all valid), pending/on-hold/expired
(all invalid), multi-line-item product matching, and empty-line-items error handling. Frontend:
verified the new verification-failure test actually catches the pre-fix behavior by temporarily
removing the `lastVerificationError` assignment and confirming the test failed with exactly the
predicted symptom (`Expected: not null, Actual: <null>`); restored and confirmed green. Full
`flutter analyze` (107 issues, unchanged baseline) and `flutter test` (786 tests, 36 pre-existing
failures in the same `test/features/detail/*` files, unrelated) — no regressions.

**Recommended follow-up, not done here:** a live staging purchase test against the real Play
Developer API (this sandbox has no network path to Google's OAuth2/service-account flow), and
checking production logs for the actual `/api/payments/verify` error from the incident that
prompted this investigation, to confirm which of the explanations above was the real cause.

📝 CR follow-up

**Major confirmed and fixed: SnackBar dedup never reset, reintroducing the original bug on retry.**
`_shownVerificationError` was set once on first failure and never cleared when
`lastVerificationError` went back to `null` (e.g. `BillingManager.purchase()` resetting it at the
start of a new attempt). A *second* failure with the identical fixed message — the realistic
outcome of a persistent server misconfiguration, which this doc's own "what this does not rule out"
section flags as still-possible — compared equal to the already-shown string and was silently
suppressed. Fixed by resetting `_shownVerificationError = null` whenever `lastVerificationError`
itself goes back to `null`, so the dedup only ever suppresses re-showing the *same still-active*
error, never a fresh occurrence of it.

**Major confirmed and fixed: `findLineItem`'s silent fallback made a wrong `SubscriptionID`
undetectable.** The old v3 code had the product ID in the request URL itself, so a stale/wrong
`GOOGLE_PLAY_SUBSCRIPTION_ID` would 404 and surface as an error — one of the three root causes this
doc's own "what this does not rule out" section named. v2's token-only URL lost that free
diagnostic, and `findLineItem`'s unconditional fallback to `items[0]` silently absorbed a mismatch
with zero signal anywhere. Fixed by splitting the fallback by cardinality: exactly one line item
(this app's real shape today) still falls back to it — rejecting an otherwise-real purchase over an
app-side config mismatch would hurt the user more than granting access — but now logs a `WARNING`
naming both the mismatched ID and the env var to check, so the drift is actually visible in
production logs instead of silently tolerated forever. More than one line item with no match now
returns an error instead of guessing which one was intended — genuinely ambiguous, not just a
diagnostics gap.

**Minor confirmed and fixed: unparseable timestamps silently produced a zero-time "valid" result.**
`parseRFC3339UTC` now returns `(time.Time, error)` instead of swallowing a parse failure into
`time.Time{}` — `VerifyPurchase` fails immediately with a clear "startTime"/"expiryTime" error
instead of letting a bad value flow through as a technically-valid result whose zero
`ExpirationTime` would only surface later as a confusing "expiration_time cannot be before
start_time" error deep in `domain.NewSubscription`.

**Minor confirmed and fixed: no dedicated test for `SUBSCRIPTION_STATE_PAUSED` exclusion.** Added
`TestProvider_VerifyPurchase_PausedState_NotValid`.

**Suggested tests added.** `TestProvider_VerifyPurchase_SingleLineItemMismatch_FallsBackWithWarning`
(the realistic single-product misconfig case — pins today's actual fallback-with-log behavior),
`TestProvider_VerifyPurchase_MultipleLineItemsNoMatch_Errors` (the new hard-failure case),
`TestProvider_VerifyPurchase_UnparseableExpiryTime_Errors` /
`_UnparseableStartTime_Errors` (pin the new error-instead-of-zero-time behavior), and
`TestVolatilitySeasonalityProvider`-style two-consecutive-failures widget test
(`upgrade_screen_test.dart`, "shows a SnackBar for two consecutive failed purchase attempts with
the same message").

That widget test caught a real bug **in itself** while being written: the first draft asserted the
second SnackBar was visible without first confirming the *first* one had actually gone away, so it
passed even when I deliberately reverted the dedup fix — a false-negative test. `pumpAndSettle()`
does not reliably fast-forward a `SnackBar`'s own duration-based auto-dismiss `Timer` the way it
does animation frames, so waiting out the real duration proved unreliable in this setup too; fixed
by explicitly calling `ScaffoldMessenger.hideCurrentSnackBar()` between the two simulated failures
and asserting the first message is actually gone (`findsNothing`) before triggering the second —
confirmed this version does fail against the reverted fix (0 widgets found where 1 was expected),
then confirmed it passes against the real fix.

**Full validation (this round).** Backend: `go build ./...`, `go vet ./...` — clean; `go test
./... -race` (fresh cache) — all packages pass, no data races. Frontend: `flutter analyze` — 107
issues, unchanged baseline; `flutter test` — 787 tests, 36 pre-existing failures in the same
`test/features/detail/*` files, unrelated.
