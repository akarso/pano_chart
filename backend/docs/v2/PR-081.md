## PR-081: feat(backend): replace candle-derived fragility proxies with real futures data

🎯 Objective

`application/risk.CandleBasedDataProvider` — the only `FragilityProvider` wired into
`SetupService` (`cmd/api/main.go`) — is explicitly commented `"a placeholder until real
funding/OI/long-short APIs are integrated"`. Today, every fragility/crowding component is derived
from the same OHLCV candles the sideways/setup scorers already consume, not from real positioning
data:

| Component | `FragilityComponents` field | Current proxy | Real signal it should be |
|---|---|---|---|
| Funding rate | `FundingExtremeness` | price deviation from its own SMA | Binance Futures funding rate |
| Open interest | `OIExpansion` | raw trading volume | Binance Futures open interest |
| Long/short skew | `LongShortImbalance` | fraction of green candles | Binance Futures long/short account ratio |
| Liquidation proximity | `LiquidationProximity` | nearest local high/low | real liquidation cluster distance |

`Fragility.Score` (via `Crowding` in `ComputeConfidence`) is weighted up to 30% of setup confidence
for the sideways/compression regimes — the exact regimes this app's core use case targets. As
currently wired, "crowding" is not an independent risk read; it is re-derived noise from data the
sideways detector has already scored, so it cannot warn about a real squeeze the price action
itself hasn't shown yet. This is the highest-leverage fix for the "low risk" half of the app's
premise.

🧱 Scope

Backend only (Go). New port + adapter, existing domain/application logic unchanged:
- `application/ports` — new `FuturesDataPort` (or extend an existing port) for funding rate, OI
  history, and long/short ratio
- `adapters/infra` — new Binance Futures REST adapter implementing it
- `application/risk` — new `BinanceFuturesDataProvider` (replaces `CandleBasedDataProvider` as the
  provider passed to `apprisk.NewService` in `cmd/api/main.go`)
- Redis caching for the new endpoints, following the existing pattern (`RedisCachedVolumeProvider`,
  `RedisCachedSymbolUniverse` in `cmd/api/main.go`)

`domain/risk`, `application/risk/fragility_engine.go`, and the four `*_model.go` scoring functions
are unaffected — this PR only replaces what feeds them, not how they combine.

1️⃣ Funding rate — real data, straightforward

`GET https://fapi.binance.com/fapi/v1/premiumIndex?symbol={SYMBOL}` — public, no auth, returns
`lastFundingRate` directly. One HTTP call per symbol; cache with a TTL matched to Binance's funding
interval (rates settle every 8h but the "last" value updates continuously — a 1-5 minute cache is
reasonable, same order as the existing 24h-ticker volume cache).

2️⃣ Open interest — real data, straightforward

`GET https://fapi.binance.com/futures/data/openInterestHist?symbol={SYMBOL}&period=5m&limit=10` —
public, returns a real OI time series directly usable by the existing `oiExpansion(oiSeries
[]float64)` in `application/risk/oi_model.go` with no change to that function's signature.

3️⃣ Long/short ratio — real data, straightforward

`GET https://fapi.binance.com/futures/data/globalLongShortAccountRatio?symbol={SYMBOL}&period=5m&limit=1`
— public, returns `longAccount`/`shortAccount` ratios directly usable by the existing
`imbalance(longRatio float64)`.

4️⃣ Liquidation proximity — the one component without a clean drop-in replacement

Binance does not publish a public liquidation-heatmap REST endpoint. The only real liquidation
signal available without a paid third-party API (e.g. Coinglass) is the futures liquidation
**stream** (`wss://fstream.binance.com/ws/!forceOrder@arr`), which emits individual forced-liquidation
events in real time with no historical backfill and no aggregation. Turning that into a "nearest
cluster" distance means running a persistent WS consumer, accumulating a rolling window of recent
liquidation events, and clustering them by price — meaningfully more infrastructure than items 1-3
(which are one cached REST call each). Two honest options, pick one before starting:
   - **(a) Phase it separately**: ship 1-3 as PR-081, keep `liquidationProximity`'s candle-derived
     proxy as an explicitly-labeled interim measure (it already is), and scope the WS-based
     real version as its own follow-up PR once 1-3 are validated in production.
   - **(b) Descope for now**: drop `LiquidationProximity`'s weight (`0.25` in `FinalScore`) to 0
     and redistribute it across the three real components, rather than mixing one real signal
     stream into a score that's otherwise real REST data — revisit once the WS pipeline exists.

   This doc recommends (a): items 1-3 alone are a large, self-contained improvement and shouldn't
   wait on the WS infrastructure.

5️⃣ Symbol availability and graceful degradation

Not every symbol in the spot-market universe used elsewhere in this app has a Binance Futures
market. `BinanceFuturesDataProvider.Get` must return a clear "no futures market" error rather than
zeros — `SetupService.Evaluate` already treats a non-cancellation `FragilityProvider` error as
"degrade gracefully, `Crowding` stays at its zero default" (see `service.go`'s existing handling,
added in the PR-076 CR round), so this composes with existing behavior for free; no change needed
there.

6️⃣ Verification

- Unit tests for the new adapter against recorded/fixture Binance responses (matching the existing
  `httptest`-based patterns already used for `FreeTierCandleRepository`/`Binance24hTickerVolumeProvider`).
- A test proving a real "crowded long, extreme funding" fixture produces meaningfully different
  `FragilityComponents` than the old candle-derived proxy would have for the same underlying price
  action — the actual point of this PR.
- Confirm `SetupService`'s existing fragility-cancellation and fragility-error tests
  (`TestSetupService_FragilityCancellation_AbortsInsteadOfDefaultingCrowding`,
  `TestSetupService_FragilityError_DegradesGracefullyWhenNotCancelled`) still pass unchanged —
  they test `SetupService`'s handling of the `FragilityProvider` interface, not the specific
  implementation, so they shouldn't need edits.

🚀 Result

- `Crowding` in setup confidence reflects real futures-market positioning (funding, OI, long/short
  skew) instead of re-derived candle noise — the fragility signal starts doing what its own design
  (weighted by reliability: OI > funding/liquidation > imbalance) was always meant to do.
- Liquidation proximity stays an explicitly-labeled interim proxy pending a follow-up PR for the
  WS-based real version, rather than silently pretending to be something it isn't.

📝 Implementation notes

Implemented items 1-3 as designed (recommendation (a) — liquidation proximity, item 4, stays the
candle-derived proxy pending its own follow-up PR, unchanged from before).

**New port** `application/ports/futures_data.go` — `FuturesDataPort` with `FundingRate`,
`OpenInterestHistory`, `LongShortRatio`, one method per real signal, matching `MarketRiskData`'s
existing field types exactly (no new type conversions needed downstream).

**New adapter** `adapters/infra/binance_futures_client.go` — `BinanceFuturesClient` implements the
port against Binance's public Futures REST API (no key/signature required for any of the three
endpoints used):
- `GET /fapi/v1/premiumIndex?symbol=X` → `lastFundingRate`
- `GET /futures/data/openInterestHist?symbol=X&period=5m&limit=12` → `sumOpenInterest` series
- `GET /futures/data/globalLongShortAccountRatio?symbol=X&period=5m&limit=1` → `longAccount`

Verified the exact response shapes and error behavior against the **real, live API** during
implementation (not just documentation) — this surfaced something the spec didn't anticipate:
`premiumIndex` returns a clear HTTP 400 + `{"code":-1121,"msg":"Invalid symbol."}` for an unknown
symbol, but `openInterestHist` and `globalLongShortAccountRatio` return **HTTP 200 with an empty
array** for the same case — silently "succeeding" with no data rather than erroring. Handled
explicitly: an empty array from either endpoint is treated as an error
(`"no data for symbol %q"`), not as a zero-length-but-valid series, so PR-081 §5's "return a clear
error, not zeros" requirement holds for all three endpoints uniformly despite Binance's own API
being inconsistent about how it signals "no such symbol."

**New composition** `application/risk/binance_futures_data_provider.go` —
`BinanceFuturesDataProvider` replaces `CandleBasedDataProvider` (deleted; `fundingProxy` and
`bullishRatio` deleted with it as now-genuinely-dead code, `nearestClusterProxy` moved over
unchanged since it's still needed for the interim liquidation-proximity proxy). Calls
`FundingRate` → `OpenInterestHistory` → `LongShortRatio` in sequence, returning on the first error
without calling the remaining endpoints (verified: deliberately made `FundingRate` swallow its own
error, confirmed the regression test — `TestBinanceFuturesDataProvider_FundingRateError_
FailsFastWithoutCallingOtherEndpoints` — catches it). Price and the liquidation-cluster proxy still
come from `riskCandleLimit` (50) candles via the existing `ports.CandleRepositoryPort`, unchanged.

**New caching decorator** `adapters/infra/redis_cached_futures_data.go` —
`RedisCachedFuturesData`, mirroring `RedisCachedVolumeProvider`'s existing pattern (per-key cache,
ignore `Set` errors, fall back to `next` on any Redis failure). Per-symbol cache keys
(`futures:funding:{symbol}`, `futures:oi:{symbol}`, `futures:longshort:{symbol}`) rather than the
single fixed key `RedisCachedVolumeProvider` uses, since this data is per-symbol, not
universe-wide. 5 minute TTL, matching the `period=5m` granularity of the underlying OI/long-short
endpoints — caching more aggressively than the data itself updates would be pointless.

**Wiring** (`cmd/api/main.go`): new `PC_BINANCE_FUTURES_BASE_URL` env var (default
`https://fapi.binance.com`), following the exact `PC_BINANCE_BASE_URL` pattern already used for
the spot API. `riskProvider` now composes `BinanceFuturesClient` → `RedisCachedFuturesData` →
`BinanceFuturesDataProvider`, reusing the existing `binanceClient` and `redisClient` instances
rather than creating new ones.

**Verification.** 22 new tests across three files:
- `tests/adapters/infra/binance_futures_client_test.go` — fixtures built from the **live** API
  responses captured during implementation (not hand-guessed), covering all three endpoints' happy
  paths plus both of Binance's error shapes (HTTP 400 and empty-200).
- `tests/adapters/infra/redis_cached_futures_data_test.go` — cache hit/miss/store/Redis-failure-
  fallback for all three methods, mirroring `redis_cached_volume_provider_test.go`'s existing
  coverage shape.
- `tests/application/risk/binance_futures_data_provider_test.go` — happy path (real futures data
  composed with candle-derived Price/NearestCluster), each of the three futures calls' error paths,
  fail-fast ordering, and the existing invalid-symbol/timeframe/candle-fetch/insufficient-data
  cases carried over from the old provider's implicit coverage.

Confirmed `SetupService`'s existing fragility-cancellation and fragility-error tests
(`TestSetupService_FragilityCancellation_AbortsInsteadOfDefaultingCrowding`,
`TestSetupService_FragilityError_DegradesGracefullyWhenNotCancelled`) still pass unchanged, as
predicted — they test `SetupService`'s handling of the `FragilityProvider` interface via a fake,
not this specific implementation.

**Not done in this environment**: a full live server run against real Redis + the real HTTP
handler chain — this sandbox doesn't have a Redis instance available. Confidence instead comes
from (a) the underlying Binance endpoints verified live and matched exactly by fixtures, and (b)
full unit coverage of every composition layer with fakes. Worth a real staging smoke test before
this ships.

**Full validation.** `go build ./...`, `go vet ./...` — clean. `go test ./...` — all packages pass,
no regressions anywhere else in the suite.

📝 CR follow-up

**Blocker confirmed and fixed: symbol case mismatch.** `Get` used the raw, unnormalized `symbol`
argument for the three futures calls while only the candle-repo path got the normalized `sym` —
confirmed via `grep` that `setup_handler.go`/`fragility_handler.go` both call `ParseSymbol` purely
to validate and discard its normalized result (`if _, err := ParseSymbol(symbolStr); err != nil`),
so a request like `/api/token/btcusdt/setup` really does reach this provider with a lowercase
string. Checked the "will very likely 400" claim against the **live** API before fixing anything —
it doesn't: Binance's futures endpoints turned out to be case-insensitive for `symbol` (verified
live for `premiumIndex` and `openInterestHist`). The cache-key-fragmentation half of the finding is
real regardless (`"futures:funding:"+symbol` with `symbol` un-normalized would split identical data
across `btcusdt`/`BTCUSDT`/`BtcUsdt` cache entries), and relying on Binance's undocumented
case-insensitivity would be fragile either way — fixed per the suggested fix: `Get` now computes
`normalizedSymbol := sym.String()` once and uses it for all three futures calls, instead of
`symbol`.

Deliberately did **not** take the broader suggested fix of normalizing in the HTTP handlers
themselves. That's a real, separate architectural inconsistency (pre-existing before PR-081,
harmless before it since nothing downstream ever used the raw string externally), but this
provider's own fix already closes the actual observable bug completely — `sym` is normalized
internally regardless of what the caller passes in, so there's nothing left for a handler-level
fix to protect against from this provider's side. Left the handlers alone to keep this PR scoped to
what it actually touches.

**Major confirmed and fixed: sequential latency.** Rewrote `Get` to run all four fetches (funding,
open interest, long/short ratio, and — since it doesn't depend on the futures calls either — the
candle fetch) concurrently via `errgroup.WithContext`, cutting worst-case latency from ~30s+ to
whatever the slowest single call takes, while `gctx`'s cancellation on the first error keeps the
"don't build a result from partial data" guarantee. This broke the original fail-fast test's literal
claim ("no further futures calls after FundingRate failed") — under concurrency, sibling calls do
start, they just get cancelled via context once one fails. Renamed/updated that test
(`TestBinanceFuturesDataProvider_FundingRateError_FailsCall`) to check only that the call fails, and
added a dedicated concurrency regression test
(`TestBinanceFuturesDataProvider_ConcurrentFetch_DoesNotWaitOutASlowCallAfterAnotherFails`) that
actually proves the latency claim: two calls block until their ctx is cancelled, a third (last in
this type's own program order) fails immediately, and the test asserts `Get` returns promptly
anyway. Deliberately made the *last*-called method the one that fails, not the first — verified
this matters: an earlier draft that failed the *first*-called method (FundingRate) passed even
against a fully sequential implementation, because "return on first error" is already fast when the
failing call happens to run first. Failing the last one and blocking the earlier ones is what
actually discriminates real concurrency from sequential-but-lucky-ordering — confirmed by
temporarily reverting to sequential calls and watching the test hang past its 5s bound.

**Major confirmed and fixed: dedicated shorter timeout + negative caching.** `cmd/api/main.go` now
builds a separate `futuresHTTPClient` (5s timeout, sharing `binanceTransport`'s connection pool)
instead of reusing `binanceClient`'s 10s candle-backfill timeout. `RedisCachedFuturesData` now
caches failures too, under a much shorter `failureTTL` (wired to 45s in `main.go`, vs. the 5-minute
success `ttl`) — a symbol with no futures market (or Binance being down) is no longer re-fetched on
every single request. Verified both the "cached failure returned without calling `next` again" path
and (separately) that disabling failure-caching makes the corresponding new tests fail, the same
verify-before-trusting pattern used throughout this PR.

**Minor confirmed and fixed: `getJSON` error messages.** Non-2xx responses that don't parse as
`binanceAPIError` now include up to 512 bytes of the raw response body in the error, instead of just
the bare status code — covers a proxy/WAF page or a 429/418 body Binance's own error shape doesn't
match.

**Minor confirmed and fixed: missing `getJSON` edge-case tests.** Added coverage for a non-JSON
error body (429 + an HTML page), a network-level failure (`client.Do` against a closed server), and
context-deadline propagation through a hanging handler. The context-cancellation test itself needed
a real fix during development: an `httptest.Server` whose handler blocks forever hangs `Close()`
waiting for the connection to finish, so the unblocking channel has to close *before* `Close()` is
called, not after — got this backwards on the first attempt (two separate `defer`s run their
underlying calls in the wrong relative order for this), fixed by combining both into one explicitly-
ordered deferred closure.

**Minor confirmed and fixed: silent cache-write failures.** `RedisCachedFuturesData`'s `Set` calls
now log on failure (`[futures-cache] failed to cache ...`) instead of swallowing the error
completely — visible in the updated `TestRedisCachedFuturesData_FallsBackOnRedisFailure`'s test
output.

**Suggested test (symbol case) added.**
`TestBinanceFuturesDataProvider_NormalizesSymbolCaseForFuturesCalls` asserts all three futures calls
receive the normalized `"BTCUSDT"` form when `Get` is called with `"btcusdt"` — verified it fails
against the pre-fix code (reverted `sym.String()` back to raw `symbol`, confirmed all three
assertions failed with the lowercase value) before trusting it.

**Full validation (this round).** `go build ./...`, `go vet ./...` — clean. `go test ./... -race` —
all packages pass, no data races (relevant now that `BinanceFuturesDataProvider.Get` and the fakes
exercising it are genuinely concurrent).

📝 CR follow-up (second round): cache poisoning by sibling cancellation

**Blocker confirmed and fixed.** The concurrency fix from the first CR round created a new bug of
its own: `errgroup.WithContext`'s `gctx` is shared across all four goroutines in `Get`
(binance_futures_data_provider.go), so the instant ANY of them errors — including the candle
fetch, which has nothing to do with Binance — the other three's in-flight calls get cancelled via
that same `gctx` and return `context.Canceled`. `RedisCachedFuturesData.cachedFetch` was caching
that exactly like a real Binance rejection, for the full `failureTTL` (45s) — so a transient
candle-repo hiccup could poison an otherwise-healthy symbol's futures cache, and `SetupService`'s
existing `ctx.Err() != nil` safety net (service.go, added to stop cancellation from silently
defaulting `Crowding` to 0) never catches this because it inspects the *caller's* context, not
`Get`'s internal `gctx` — the two are unrelated from `SetupService`'s point of view. Confirmed the
full chain by tracing it end-to-end rather than taking the report at face value: `gctx` reaches
`RedisCachedFuturesData` because `main.go` wires `cachedFuturesData` as `BinanceFuturesDataProvider`'s
`futures` field, and each `g.Go` closure passes `gctx` straight through.

Fixed exactly as suggested: `cachedFetch`'s error branch now checks `ctx.Err() != nil` and skips
caching (propagates the error as-is) when the failure is attributable to the caller's own context
being done, rather than a confirmed fetch failure. Did not additionally give each goroutine its own
child context (the doc's second suggested option) — the `ctx.Err()` check alone fully closes the
observable bug (no more poisoned cache entries) without giving up errgroup's fail-fast latency
benefit from the first CR round; adding independent per-goroutine contexts on top would reintroduce
some of that latency (a slow sibling would no longer get cancelled early) for no additional
correctness benefit once the cache-poisoning itself is fixed.

**Test gap confirmed and closed.** Added
`TestBinanceFuturesDataProvider_CandleFailureDuringConcurrentFetch_DoesNotPoisonFuturesCache`,
wiring the **real** `infra.RedisCachedFuturesData` underneath `BinanceFuturesDataProvider` (not the
bare fake the other tests in this file use) with a `blockingThenSucceedingFuturesPort` whose
`FundingRate` blocks on its ctx exactly like the real `BinanceFuturesClient`'s in-flight HTTP call
would. Forces the candle fetch to fail while `FundingRate` is still blocked, then calls
`FundingRate` again directly through the cache decorator and asserts it gets the real value (a
genuine cache miss), not a cached-failure error. Verified this actually catches the regression: reverted
the `ctx.Err()` guard, reran, and got exactly the predicted failure —
`FundingRate cache appears poisoned by the sibling's cancellation: futures data unavailable (cached
failure): context canceled`. Restored the fix and confirmed green again.

**Minor confirmed and fixed: unbounded cached error length.** Added `maxCachedErrorBytes` (512,
matching `BinanceFuturesClient`'s own `maxErrorBodyBytes` cap) and truncate `err.Error()` before
writing it into the cached failure marker.

**Minor acknowledged, not fixed: unrated-limited cache-write failure logging.** Left as-is — the
reviewer's own framing ("not urgent, but worth a note for prod") reads as a flag for future
attention rather than a request to add rate-limiting now, and a real fix (a token bucket or
similar) is a meaningfully bigger addition than this round's other changes for a scenario (sustained
Redis outage) that's already visible via Redis's own monitoring. Noted here for whoever picks this
up next.

**Full validation (this round).** `go build ./...`, `go vet ./...` — clean. `go test ./... -race`
(with `go clean -testcache` first, to rule out a stale pass) — all packages pass, no data races.
