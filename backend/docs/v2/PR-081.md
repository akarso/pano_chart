## PR-081: feat(backend): replace candle-derived fragility proxies with real futures data

🎯 Objective

`application/risk.CandleBasedDataProvider` — the only `FragilityProvider` wired into
`SetupService` (`cmd/api/main.go`) — is explicitly commented `"a placeholder until real
funding/OI/long-short APIs are integrated"`. Today, every fragility/crowding component is derived
from the same OHLCV candles the sideways/setup scorers already consume, not from real positioning
data:

| Component | `FragilityComponents` field | Current proxy | Real signal it should be |
|---|---|---|---|
| Funding rate | `FundingExtremeness` | price deviation from its own SMA | Binance Futures funding rate |
| Open interest | `OIExpansion` | raw trading volume | Binance Futures open interest |
| Long/short skew | `LongShortImbalance` | fraction of green candles | Binance Futures long/short account ratio |
| Liquidation proximity | `LiquidationProximity` | nearest local high/low | real liquidation cluster distance |

`Fragility.Score` (via `Crowding` in `ComputeConfidence`) is weighted up to 30% of setup confidence
for the sideways/compression regimes — the exact regimes this app's core use case targets. As
currently wired, "crowding" is not an independent risk read; it is re-derived noise from data the
sideways detector has already scored, so it cannot warn about a real squeeze the price action
itself hasn't shown yet. This is the highest-leverage fix for the "low risk" half of the app's
premise.

🧱 Scope

Backend only (Go). New port + adapter, existing domain/application logic unchanged:
- `application/ports` — new `FuturesDataPort` (or extend an existing port) for funding rate, OI
  history, and long/short ratio
- `adapters/infra` — new Binance Futures REST adapter implementing it
- `application/risk` — new `BinanceFuturesDataProvider` (replaces `CandleBasedDataProvider` as the
  provider passed to `apprisk.NewService` in `cmd/api/main.go`)
- Redis caching for the new endpoints, following the existing pattern (`RedisCachedVolumeProvider`,
  `RedisCachedSymbolUniverse` in `cmd/api/main.go`)

`domain/risk`, `application/risk/fragility_engine.go`, and the four `*_model.go` scoring functions
are unaffected — this PR only replaces what feeds them, not how they combine.

1️⃣ Funding rate — real data, straightforward

`GET https://fapi.binance.com/fapi/v1/premiumIndex?symbol={SYMBOL}` — public, no auth, returns
`lastFundingRate` directly. One HTTP call per symbol; cache with a TTL matched to Binance's funding
interval (rates settle every 8h but the "last" value updates continuously — a 1-5 minute cache is
reasonable, same order as the existing 24h-ticker volume cache).

2️⃣ Open interest — real data, straightforward

`GET https://fapi.binance.com/futures/data/openInterestHist?symbol={SYMBOL}&period=5m&limit=10` —
public, returns a real OI time series directly usable by the existing `oiExpansion(oiSeries
[]float64)` in `application/risk/oi_model.go` with no change to that function's signature.

3️⃣ Long/short ratio — real data, straightforward

`GET https://fapi.binance.com/futures/data/globalLongShortAccountRatio?symbol={SYMBOL}&period=5m&limit=1`
— public, returns `longAccount`/`shortAccount` ratios directly usable by the existing
`imbalance(longRatio float64)`.

4️⃣ Liquidation proximity — the one component without a clean drop-in replacement

Binance does not publish a public liquidation-heatmap REST endpoint. The only real liquidation
signal available without a paid third-party API (e.g. Coinglass) is the futures liquidation
**stream** (`wss://fstream.binance.com/ws/!forceOrder@arr`), which emits individual forced-liquidation
events in real time with no historical backfill and no aggregation. Turning that into a "nearest
cluster" distance means running a persistent WS consumer, accumulating a rolling window of recent
liquidation events, and clustering them by price — meaningfully more infrastructure than items 1-3
(which are one cached REST call each). Two honest options, pick one before starting:
   - **(a) Phase it separately**: ship 1-3 as PR-081, keep `liquidationProximity`'s candle-derived
     proxy as an explicitly-labeled interim measure (it already is), and scope the WS-based
     real version as its own follow-up PR once 1-3 are validated in production.
   - **(b) Descope for now**: drop `LiquidationProximity`'s weight (`0.25` in `FinalScore`) to 0
     and redistribute it across the three real components, rather than mixing one real signal
     stream into a score that's otherwise real REST data — revisit once the WS pipeline exists.

   This doc recommends (a): items 1-3 alone are a large, self-contained improvement and shouldn't
   wait on the WS infrastructure.

5️⃣ Symbol availability and graceful degradation

Not every symbol in the spot-market universe used elsewhere in this app has a Binance Futures
market. `BinanceFuturesDataProvider.Get` must return a clear "no futures market" error rather than
zeros — `SetupService.Evaluate` already treats a non-cancellation `FragilityProvider` error as
"degrade gracefully, `Crowding` stays at its zero default" (see `service.go`'s existing handling,
added in the PR-076 CR round), so this composes with existing behavior for free; no change needed
there.

6️⃣ Verification

- Unit tests for the new adapter against recorded/fixture Binance responses (matching the existing
  `httptest`-based patterns already used for `FreeTierCandleRepository`/`Binance24hTickerVolumeProvider`).
- A test proving a real "crowded long, extreme funding" fixture produces meaningfully different
  `FragilityComponents` than the old candle-derived proxy would have for the same underlying price
  action — the actual point of this PR.
- Confirm `SetupService`'s existing fragility-cancellation and fragility-error tests
  (`TestSetupService_FragilityCancellation_AbortsInsteadOfDefaultingCrowding`,
  `TestSetupService_FragilityError_DegradesGracefullyWhenNotCancelled`) still pass unchanged —
  they test `SetupService`'s handling of the `FragilityProvider` interface, not the specific
  implementation, so they shouldn't need edits.

🚀 Result

- `Crowding` in setup confidence reflects real futures-market positioning (funding, OI, long/short
  skew) instead of re-derived candle noise — the fragility signal starts doing what its own design
  (weighted by reliability: OI > funding/liquidation > imbalance) was always meant to do.
- Liquidation proximity stays an explicitly-labeled interim proxy pending a follow-up PR for the
  WS-based real version, rather than silently pretending to be something it isn't.
