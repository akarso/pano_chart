# PR-033: Rate Limiting & Worker Scaling Architecture

## Status
Proposed

## Objective

Introduce a robust, centralized rate-limiting and worker orchestration system to:

- Prevent HTTP 409 / 429 errors from Binance
- Scale candle resolution (e.g., 100 candles)
- Support multi-timeframe scanning
- Allow future feature expansion (breakout, volatility, RSI, etc.)
- Maintain predictable refresh latency

This PR focuses strictly on infrastructure. No scoring logic changes.

---

# 1. Current Problem

Current model:
- Fixed worker pool (20 workers)
- Direct concurrent Binance kline requests
- No global weight control
- No adaptive refresh strategy

Risks:
- Hitting Binance weight limits
- Burst request collisions
- Unpredictable failures under scaling
- Hard cap on feature expansion

---

# 2. Design Principles

1. Centralized request budgeting
2. Deterministic rate control
3. Decoupled fetch and scoring
4. Time-based caching
5. Adaptive refresh scheduling
6. Scalable without increasing worker count

---

# 3. Binance Constraints

Binance uses a **weight-based rate limit** system.

Example (Futures API typical values):
- Kline request weight = 1
- Limit ≈ 1200 weight / minute

Effective safe target:
- 900 weight / minute (75% safety margin)

# 5. Core Components

## 5.1 Global Rate Limiter

### Type

```go
type RateLimiter struct {
    tokensPerMinute int
    bucket          chan struct{}
}
Behavior
Pre-fill bucket with tokensPerMinute

Refill continuously every minute

Each Binance request consumes 1 token

If no token available → worker blocks

Configuration
RateLimitConfig:
    MaxWeightPerMinute = 900
5.2 Worker Pool
Keep:

20 workers

Do NOT increase.

Reason:

Binance limit is weight-based, not concurrency-based.

Increasing workers increases burst risk.

Bottleneck is rate, not CPU.

5.3 Fetch Scheduler
Introduce a scheduler responsible for:

Determining which symbol+timeframe pairs require refresh

Avoiding full-universe refresh every cycle

Staggering updates

8. Caching Layer
Introduce:

type CandleCache struct {
    data map[Key]CachedCandles
}
Where:

Key = symbol + timeframe
Cached entry:

type CachedCandles struct {
    Candles   []Candle
    UpdatedAt time.Time
}
TTL:

5m: 30 seconds

15m: 60 seconds

1h: 180 seconds

Workers:

Check cache first

Skip fetch if valid

9. Request Flow Logic
Worker process:

1. Receive FetchTask
2. Check cache
3. If expired:
       Acquire rate token
       Fetch klines
       Store in cache
4. Send candles to scoring engine
10. Failure Handling
If Binance returns:

409

429

Then:

Temporarily reduce token refill rate by 20%

Log warning

Gradually restore after 60 seconds

This prevents cascading failures.

11. Observability

12. Scalability Analysis
Assume:

300 symbols

3 timeframes

Staggered refresh

Worst-case per minute:

Top 20 × 3 TF × 2 refresh = 120

Top 100 × 3 TF × 1 refresh = 300

Remaining 180 × 3 TF × 0.5 refresh ≈ 270

Total ≈ 690 weight/minute

Within safe 900 budget.

13. Why Backend Heavy Lifting Is Correct
We do analysis server-side because:

Consistent scoring

Controlled API usage

Cached shared results

Device-agnostic performance

Lower client bandwidth

Centralized experimentation

Moving analysis client-side would:

Multiply API calls per user

Break rate budget

Introduce inconsistent results

Backend remains the correct architecture.
