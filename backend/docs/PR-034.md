# PR-034: MetaScore Engine

## Status
Proposed

## Objective

Introduce a generic, modular MetaScore Engine to:

- Compose multiple normalized subscores into a single score
- Support multiple composition modes
- Allow runtime weight tuning
- Enable algorithm reuse across Sideways, Breakout, Trend, etc.
- Support timeframe-specific configurations without duplicating logic

This PR introduces infrastructure only.
No changes to Sideways scoring logic yet.

---

# 1. Design Goals

1. All subscores return normalized value ∈ [0,1]
2. No hardcoded multipliers inside subscores
3. Composition logic centralized
4. Runtime-configurable weights
5. Timeframe profile support
6. Pluggable into any scoring system

---

# 2. Core Concepts

## 2.1 Subscore Interface

Each subscore must implement:

```go
type Subscore interface {
    Name() string
    Compute(data *CandleSet, cfg interface{}) float64 // returns [0,1]
}
Constraints:

Must clamp output to [0,1]

Must not apply weight internally

Must not depend on other subscores

2.2 Composition Modes
type CompositionMode int

const (
    WeightedAdditive CompositionMode = iota
    WeightedMultiplicative
    HybridStructural
)
3. Meta Configuration
3.1 MetaConfig
type MetaConfig struct {
    Mode     CompositionMode
    Weights  map[string]float64
}
Where:

key = Subscore.Name()

value = weight (float64 ≥ 0)

4. MetaScorer Structure
type MetaScorer struct {
    subscores []Subscore
    config    MetaConfig
}
Constructor:

func NewMetaScorer(subscores []Subscore, cfg MetaConfig) *MetaScorer
5. Score Computation
5.1 Execution Flow
1. Compute each subscore
2. Clamp values to [0,1]
3. Normalize weights (optional)
4. Apply composition mode
5. Clamp final result to [0,1]
6. Return
6. Composition Implementations
6.1 Weighted Additive
score = Σ (w_i * s_i) / Σ(w_i)
Characteristics:

Smooth ranking

Stable

Good for experimentation

Default for development

6.2 Weighted Multiplicative
score = Π (s_i ^ w_i)
Characteristics:

Strict filtering

One weak dimension collapses score

Suitable for "Top 20 only" ranking

6.3 Hybrid Structural
Designed for structural detection systems (Sideways, Breakout).

Example:

base = pow(CCS, w1) * pow(OQS, w2)
volAdj = 1 + w3*(VOS - 0.5)
score = base * volAdj * pow(DCS, w4)
Characteristics:

Structure dominates

Secondary modifiers influence but do not dominate

Recommended for production structural detectors

7. Timeframe Profiles
7.1 Important Design Decision
We DO NOT create different algorithms per timeframe.

We create different configurations per timeframe.

Same engine.
Different parameter profile.

7.2 TimeframeProfile Structure
type TimeframeProfile struct {
    Timeframe        string
    CandleCount      int
    SubscoreConfig   interface{}
    MetaConfig       MetaConfig
}
Example profiles:

1m Profile
CandleCount: 120

Higher volatility tolerance

Lower oscillation strictness

Lower drift penalty

Rationale:
1m is noisy and short-lived.
Algorithm must be forgiving.

5m Profile
CandleCount: 100

Medium volatility tolerance

Balanced oscillation requirements

Good for scalping channels.

15m Profile (Primary)
CandleCount: 100–120

Strict channel coherence

Medium volatility optimality

Strong oscillation quality requirement

This should be flagship configuration.

1h Profile
CandleCount: 80–100

Strong drift penalty

Wider acceptable channel width

Lower oscillation density requirement

Because swings are fewer.

8. Why Config Per Timeframe Matters
Because:

Volatility scales nonlinearly

ATR behaves differently

Swing density differs

Channel width relative to price differs

If you do not profile per timeframe:

1m will look chaotic
1h will look dead

Proper profile tuning makes same algorithm usable across scales.

9. Extensibility
MetaScore Engine must support:

Sideways v5

Breakout Detector

Trend Strength

RSI Composite

User-defined advanced sorting (future)

No modifications to engine required.

10. Observability
MetaScorer should optionally expose:

func (m *MetaScorer) ScoreWithBreakdown(...) (float64, map[string]float64)
This enables:

Debugging

UI breakdown

Advanced mode tuning

Calibration workflows

Mandatory for production readiness.

11. Acceptance Criteria
Supports all three composition modes

Supports per-timeframe configuration

No hardcoded weights in subscores

All scores normalized [0,1]

Breakdown available for debugging

Unit tests for all composition modes

12. Future Use
MetaScore becomes the universal scoring backbone of the application.

Sideways v5 will be the first structural implementation using this engine.
Breakout detector will be the second.
Trend classifier will be third.

This architecture allows expansion without rewriting scoring infrastructure.
