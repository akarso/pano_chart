# PR-041: Payment Infrastructure Foundation (Provider Abstraction Layer)

## 1. Objective

Introduce the foundational architecture for payment processing and subscription management.

This PR establishes:

* Payment provider abstraction
* Subscription lifecycle model
* Database schema for purchases and subscriptions
* Unified verification interface
* Provider-agnostic payment flow

No external payment providers are integrated in this PR.

The goal is to enable future integrations with:

* Google Play Billing
* Stripe
* Solana payments

without modifying core application logic.

---

# 2. Architectural Overview

Payment flow will follow a provider-agnostic structure.

```
Client App
    ↓
Purchase Event
    ↓
Payment Provider Adapter
    ↓
Verification Service
    ↓
Subscription Service
    ↓
SQLite Database
```

Each provider implements the same verification contract.

---

# 3. Payment Provider Interface

Define a base interface that every payment provider must implement.

Example:

```
interface PaymentProvider {

    verifyPurchase(purchaseToken: string): PaymentVerificationResult

    getProviderName(): string
}
```

Purpose:

* Standardize verification
* Allow plug-and-play providers
* Prevent business logic duplication

---

# 4. Payment Verification Result

Verification returns a normalized structure.

```
class PaymentVerificationResult {

    bool valid
    string provider
    string externalTransactionId
    string productId
    string userId
    datetime purchaseTime
    datetime expirationTime
}
```

All providers must map their response into this format.

---

# 5. Subscription Service

Central service responsible for subscription state.

Responsibilities:

* Validate purchase results
* Activate subscription
* Extend subscription
* Handle renewals
* Handle expiration checks

Example API:

```
SubscriptionService.activateSubscription(result)

SubscriptionService.isActive(userId)

SubscriptionService.getExpiration(userId)
```

This isolates subscription logic from payment providers.

---

# 6. Database Schema

### 6.1 Users

```
users

id TEXT PRIMARY KEY
created_at DATETIME
```

---

### 6.2 Purchases

Stores every purchase attempt.

```
purchases

id INTEGER PRIMARY KEY
user_id TEXT
provider TEXT
external_transaction_id TEXT
product_id TEXT
purchase_time DATETIME
expiration_time DATETIME
verified INTEGER
created_at DATETIME
```

---

### 6.3 Subscriptions

Tracks active subscription state.

```
subscriptions

user_id TEXT PRIMARY KEY
provider TEXT
product_id TEXT
start_time DATETIME
expiration_time DATETIME
updated_at DATETIME
```

---

# 7. Provider Registry

Introduce a registry for available providers.

Example:

```
PaymentProviderRegistry.register(provider)
PaymentProviderRegistry.get(providerName)
```

Initial registry contains placeholders for:

* GooglePlayProvider
* StripeProvider
* SolanaProvider

Implementation occurs in later PRs.

---

# 8. Purchase Verification Endpoint

Backend endpoint for verifying purchases.

```
POST /api/payments/verify
```

Request:

```
{
  "provider": "google_play",
  "purchaseToken": "...",
  "userId": "..."
}
```

Flow:

```
Request
→ provider lookup
→ provider.verifyPurchase()
→ SubscriptionService.activateSubscription()
→ response
```

---

# 9. Subscription Status Endpoint

Client must be able to query subscription state.

```
GET /api/subscription/status
```

Response:

```
{
  "active": true,
  "expires_at": "2026-03-21T10:00:00Z"
}
```

---

# 10. Security Considerations

* Never trust client purchase validation
* All purchase verification occurs server-side
* Store provider transaction IDs to prevent replay
* Verify expiration times from provider responses

---

# 11. What This PR Does NOT Implement

Not included in this PR:

* Google Play Billing
* Stripe Checkout
* Solana transactions
* Trial logic
* Referral logic
* Webhooks

These will be introduced in subsequent PRs.

---

# 12. Acceptance Criteria

* PaymentProvider interface defined
* SubscriptionService implemented
* SQLite schema created
* Verification endpoint implemented
* Subscription status endpoint implemented
* Provider registry operational

No payment provider should yet be functional.

---

# 13. Strategic Purpose

This PR ensures that payment providers remain modular and interchangeable.

Future payment integrations become isolated modules rather than architectural rewrites.

This keeps payment logic maintainable as the platform expands.
