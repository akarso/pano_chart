PR-036: Evaluation Snapshot Logging Engine
Overview

Introduce a structured, versioned logging system that records evaluation snapshots for every symbol/timeframe analysis cycle.

This PR does not modify any scoring logic.

It adds infrastructure required for:

Future statistical validation

Regime performance analysis

Version comparison (algo evolution)

Edge discovery without refactoring core engine

This enables painless transition from useful tool → research-capable engine.

Goals

Persist all regime scores at evaluation time.

Persist price at evaluation time.

Persist algorithm version metadata.

Keep logging decoupled from scoring engine.

Keep performance overhead minimal.

Enable future forward-return enrichment.

Non-Goals

No backtesting framework.

No statistical calculations.

No performance evaluation yet.

No changes to existing scoring formulas.

Architectural Design
1️⃣ Snapshot Data Model
type EvaluationSnapshot struct {
    Timestamp   time.Time
    Symbol      string
    Timeframe   string

    // Core regime scores
    SidewaysScore      float64
    CompressionScore   float64
    BreakoutUpScore    float64
    BreakoutDownScore  float64
    TrendScore         float64

    // Directional bias (if applicable)
    Bias               string // "up", "down", "neutral"

    // Structural subtype
    ChannelType        string // "parallel", "compression", etc.

    // Market state
    Price              float64
    ATR                float64
    Volume             float64

    // Meta
    AlgoVersion        string
}
2️⃣ Logger Interface

Scoring engine must not know storage implementation.

type SnapshotLogger interface {
    Log(snapshot EvaluationSnapshot) error
}

Default implementation:

type DBLogger struct {
    db *sql.DB
}

Optional future implementations:

CSVLogger

FileLogger

AsyncQueueLogger

NoopLogger

Storage Strategy
Recommended: Relational Table

Example SQL schema:

CREATE TABLE evaluation_snapshots (
    id BIGSERIAL PRIMARY KEY,
    timestamp TIMESTAMP NOT NULL,
    symbol VARCHAR(20) NOT NULL,
    timeframe VARCHAR(10) NOT NULL,

    sideways_score DOUBLE PRECISION,
    compression_score DOUBLE PRECISION,
    breakout_up_score DOUBLE PRECISION,
    breakout_down_score DOUBLE PRECISION,
    trend_score DOUBLE PRECISION,

    bias VARCHAR(10),
    channel_type VARCHAR(30),

    price DOUBLE PRECISION,
    atr DOUBLE PRECISION,
    volume DOUBLE PRECISION,

    algo_version VARCHAR(20)
);
Indexes
CREATE INDEX idx_symbol_timeframe_ts
ON evaluation_snapshots(symbol, timeframe, timestamp);

This is critical for forward-return computation later.

Algorithm Versioning

Hardcode scoring engine version:

const AlgoVersion = "v4.0.0"

Each snapshot must include version.

This allows:

Comparing v4 vs v5

Measuring score drift over time

Validating improvements statistically

Versioning is mandatory for research integrity.

Integration Point

Logging occurs after scoring is complete:

result := scoringEngine.Evaluate(data)

snapshot := BuildSnapshot(result, marketData)

logger.Log(snapshot)

Scoring engine must remain pure and deterministic.

Performance Considerations

Current worker pool: 20 workers.

Concerns:

DB contention

Write amplification

409 from Binance (not directly related, but load matters)

Recommendations

Use async buffered channel for logging.

Dedicated logging worker(s).

Batch insert (optional phase 2).

Example:

snapshotChan := make(chan EvaluationSnapshot, 1000)

One goroutine flushes:

Every N snapshots

Or every T seconds

This prevents scoring slowdown.
