## PR-079: fix(frontend): upgrade to Google Play Billing Library 8.0.0

🎯 Objective

Google Play requires all apps to use Google Play Billing Library 8.0.0+ starting 2026-08-31,
or updates will be rejected. The app currently pulls in Billing Library 7.1.1 transitively via
`in_app_purchase_android`.

🧱 Scope

Frontend only (Dart/Flutter):
- `pubspec.yaml` — bump `in_app_purchase`
- `lib/features/billing/billing_manager.dart`
- `lib/features/billing/upgrade_screen.dart`

1️⃣ Dependency bump
```yaml
# pubspec.yaml — before
in_app_purchase: ^3.2.0

# after
in_app_purchase: ^3.3.0
```
Pulls `in_app_purchase_android` from `0.4.0+5` (Billing Library 7.1.1) to `≥0.5.0`
(Billing Library 8.0.0).

```bash
cd frontend && flutter pub upgrade in_app_purchase in_app_purchase_android
```

2️⃣ API compat check
Review `billing_manager.dart` and `upgrade_screen.dart` for breaking changes in
`in_app_purchase_android` between 0.4.x → 0.5.x (BillingClient major bump typically touches
`PurchaseDetails` / `BillingResponse` handling).

3️⃣ Verification
- Exercise purchase flow on a testing track (sandbox), not just unit tests.
- Confirm `_verifyAndComplete` server-verification path (see PR-078) still behaves correctly
  against the new client.

🚀 Result

- App ships on Play Billing Library ≥8.0.0, unblocking future Play Store updates past the
  2026-08-31 deadline.

📝 Implementation notes

**1️⃣ Dependency bump.** `in_app_purchase` `^3.2.0` → `^3.3.0` via
`flutter pub upgrade in_app_purchase in_app_purchase_android`, resolving
`in_app_purchase_android` `0.4.0+5` → `0.5.3`. Confirmed via that package's own CHANGELOG that
`0.5.0` is exactly the release that "Updates Google Play Billing Library from 7.1.1 to 8.0.0" —
the doc's premise checked out against current reality, not just against pub's version numbers.

**2️⃣ API compat check.** `0.5.0`'s only breaking change is removing `queryPurchaseHistory` /
`queryPurchaseHistoryAsync` (superseded by `queryPurchases`) — grepped `lib/` and `test/`, neither
is referenced anywhere in this codebase. Both `billing_manager.dart` and `upgrade_screen.dart` only
ever touch the platform-agnostic `in_app_purchase` facade (`InAppPurchase`, `PurchaseDetails`,
`PurchaseStatus`, `ProductDetails`, `PurchaseParam`) — none of that surface changed; the Billing
Library major bump is entirely internal to `in_app_purchase_android`'s native layer.
`in_app_purchase_platform_interface` (the dev-only abstract layer `_FakeIapPlatform` in
`billing_manager_test.dart` implements) stayed pinned at `1.4.0`, unaffected — so the test fake
needed no changes either.

**SDK floor.** `in_app_purchase_android 0.5.3` declares `sdk: ^3.12.0` (up from whatever `0.4.0+5`
needed) — same "declared floor must reflect the strictest real dependency" fix applied in the
PR-078 CR round. Bumped `environment.sdk` from `>=3.4.0 <4.0.0` to `>=3.12.0 <4.0.0` to match,
rather than leaving a floor pub's resolver tolerates but that doesn't reflect what actually builds.

**Analyzer baseline.** `flutter analyze` moved from 102 → 107 issues purely from that SDK floor
bump raising the package's effective language version — not from any line this PR touches.
All 5 new hits are `prefer_initializing_formals` info notices on three pre-existing constructors
(`AutoRefreshTimer`, `BillingManager`, `SocialFeedViewModel`) that intentionally expose a public
named parameter (`interval`, `api`/`userId`/`trialManager`, `userId`) over a differently-named
private field. Checked before "fixing inline" per the PR-078 precedent: applying the lint's own
suggestion (`required this._api`, etc.) would rename the named parameter to the private field name,
which callers outside the library cannot pass by name at all — a real breaking change to each
class's public constructor, not a style nit. Left alone as accepted, pre-existing debt surfaced by
a language-version change, not new debt from this PR.

**Verification.** No native `android/` project exists in this checkout to exercise a real
sandbox purchase (per the doc's own step 3️⃣) — `Platform.isAndroid` gates `purchase()`'s IAP-launch
path off entirely on this host, the same structural limit noted in PR-078. Validated everything
that *can* be exercised off-Android: full `test/features/billing/` suite (42 tests, including the
`_verifyAndComplete` server-verification path from PR-078) passes unchanged against the upgraded
packages. Full suite: `flutter test` — 783 tests, 36 pre-existing failures, same 4
`test/features/detail/*` files as the established baseline, unrelated to this change.
`.dart_tool`/`analysis_options.yaml` tooling churn discarded; `pubspec.lock` kept as produced by
the real `pub upgrade` this change needed.

**Plainly stated:** this PR is a dependency-graph and static-analysis verification only. The
actual point of the upgrade — real Billing Library 8.0.0 runtime behavior on-device — is
unverified end-to-end and can't be exercised from this checkout.

📝 CR follow-up

**Major concern confirmed and fixed.** The `sdk:` floor was bumped to match `in_app_purchase_android`'s
real requirement, but `flutter: '>=3.0.0'` was left stale — checked `pubspec.lock`'s own `sdks:`
section (the combined floor pub's resolver computed across the whole graph) and it already read
`flutter: ">=3.44.0"`, so the declared constraint understated what the graph actually needs — same
inconsistency this PR's `sdk:` fix was meant to close. Bumped `flutter: '>=3.0.0'` →
`flutter: '>=3.44.0'` to match. `flutter pub get` after the change re-resolves to an identical
`pubspec.lock` (only the declared floor was too loose, not the resolution itself), and the full
suite (`flutter analyze` 107 issues, `flutter test` 783/36-pre-existing-failures) is unchanged.

**Minor concern (malformed sha256) checked, not valid.** Counted the `in_app_purchase_android`
hash directly: `f7327b5f...cefed9` is 64 hex characters — the standard SHA-256 digest length — and
every other `sha256:` entry in `pubspec.lock` is also 64 characters, so there's no formatting
inconsistency. No lockfile edit needed.
