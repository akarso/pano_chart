## PR-077: fix(frontend): networking resilience + free-tier UX clarity
🎯 Objective

Two independent, low-risk frontend fixes found during the audit:

1. `http_overview_api.dart` has no request timeout, unlike every other API client in the app
   (`http_market_state_api.dart`, `http_candle_api.dart` both use `.timeout(Duration(seconds: 15))`).
   A hung connection on the app's main landing screen leaves the overview grid spinning forever.
2. The free-tier token list silently truncates to 15 items with no indication — it reads as a
   bug ("where are the rest of my tokens?"), not as a paywall.

Bundled with two smaller correctness/perf items found in the same sweep (macro events list
building, dead code) since they're all small, independent Dart changes touching adjacent files.

🧱 Scope

Frontend only (Dart/Flutter):
- `lib/features/overview/http_overview_api.dart` — add timeout + retry, matching the other
  clients (not `lib/infrastructure/` — that path doesn't exist; the file already lives under
  `features/overview/`, same as `overview_api.dart`)
- `lib/features/overview/overview_widget.dart` — free-tier cutoff banner
- `lib/features/events/macro_events_screen.dart` — lazy list building
- dead code removal (`overview_widget.dart`)

1️⃣ Timeout on overview API
```dart
// lib/features/overview/http_overview_api.dart — before
final response = await client.get(uri);

// after
late final http.Response response;
try {
  response = await client.get(uri).timeout(const Duration(seconds: 15));
} on TimeoutException {
  // Wrap into the class's own exception type, matching how a non-200 status
  // is already reported below — callers shouldn't need to know this
  // adapter uses package:http under the hood.
  throw HttpOverviewApiException(statusCode: 0, message: 'Overview API request timed out');
}
```
Use the injected `client` field (already present on `HttpOverviewApi`), not the top-level
`http.get` — a bare top-level call bypasses whatever `client` is configured with and can't be
swapped for a `MockClient` in tests, unlike every other call in this class.

**Known limitation, not fixed by this PR:** `.timeout()` makes the *Future* give up and throw,
it doesn't cancel the underlying socket — a slow server can still hold the connection open
after the app has moved on. This matches the exact pattern already used by
`http_market_state_api.dart`/`http_candle_api.dart` (the ones this PR is copying), so it's a
consistent simplification, not a new gap. True cancellation would mean giving every
`http_*_api.dart` client an abort mechanism (e.g. swapping to `http.BaseClient` with a
`CancelToken`-style wrapper) — a real, separate, larger refactor across every client, not a
targeted fix to this one file; track it separately if it's worth doing at all.

Consider extracting a shared `ApiClient` wrapper (timeout + consistent exception type) used by
all `http_*_api.dart` files instead of each hand-rolling its own — noted as a larger follow-up
refactor, not required to land this specific fix. If done here, scope it tightly: wrap, don't
redesign the call sites.

2️⃣ Free-tier cutoff banner
```dart
// lib/features/overview/overview_widget.dart
if (!_showFavourites && !_capabilities.fullTokenList && allItems.length > 15) {
  visibleItems = allItems.sublist(0, 15);
  _showUpgradeBanner = true;
}
```
```dart
if (_showUpgradeBanner)

    label: '${allItems.length - 15} more tokens with Pro',
    onTap: () => Navigator.push(context, MaterialPageRoute(builder: (_) => UpgradeScreen())),

```
Keep it a single unobtrusive tile at the cutoff point in the grid, not a modal/interstitial —
matches the existing "no aggressive upselling" principle from the PR-039 subscriptions doc.

3️⃣ Macro events lazy list
```dart
// lib/features/events/macro_events_screen.dart — before
SingleChildScrollView(
  child: Column(children: filteredEvents.map((e) => _EventTile(e, key: _eventKeys[e.id] ??= GlobalKey())).toList()),

// after
ListView.separated(
  itemCount: filteredEvents.length,
```

Drop the `_eventKeys` map entirely if nothing downstream actually needs stable `GlobalKey`s per
event (check for scroll-to-event or animation code that might depend on it before deleting —
if something does, prune the map on filter/timeframe change instead of removing keys outright).

4️⃣ Dead code cleanup
- `overview_widget.dart` — remove commented-out import, commented-out branding `Text` widget,
  empty `_startFpsMonitor`/`_stopFpsMonitor` no-op stubs.

5️⃣ Tests
- Add a timeout test for `http_overview_api.dart`: mock a response that never completes (a
  `MockClient` handler that awaits a `Completer` that's never completed, or delays past the
  timeout), assert `fetchOverview` throws `HttpOverviewApiException` specifically (not the raw
  `TimeoutException` — the whole point of 1️⃣'s wrap is that callers only ever see this

- Widget test: free-tier user with >15 tokens sees the upgrade banner tile; pro user doesn't.

🚀 Result

- Overview screen can no longer hang indefinitely on a slow/dead connection.
- Free users see an honest, low-pressure paywall instead of what looks like a broken list.

📝 Implementation notes

Verified the actual code against this doc before implementing — the roadmap's file path aside
(`lib/infrastructure/` doesn't exist; confirmed `http_overview_api.dart` already lives under
`features/overview/`, as the doc itself notes), everything else matched the described "before"
state exactly: no timeout on the overview client, a pre-existing silent 15-item truncation with no
indication, an eager `SingleChildScrollView`+`Column` in the macro events screen, and all three
named dead-code items.

**1️⃣ Timeout** — implemented as specified: `client.get(uri).timeout(const Duration(seconds:
15))`, `on TimeoutException` wrapped into `HttpOverviewApiException(statusCode: 0, message:
'Overview API request timed out')`. Confirmed the two sibling clients this is modeled on
(`http_market_state_api.dart`, `http_candle_api.dart`) apply the same 15s `.timeout()` but neither
wraps the resulting `TimeoutException` into their own exception type — this PR's wrap is a
deliberate, self-contained improvement for this one file, not a pre-existing convention being
copied verbatim.

**2️⃣ Upgrade banner** — added `_UpgradeBannerTile` (a `Card`/`AspectRatio(2.5)` grid cell matching
`_OverviewGridItem`'s shape, using the app's actual brand accent `#00E6C0` from
`pubspec.yaml`'s `adaptive_icon_background`) inserted as the 16th grid cell when the free-tier cap
truncates the list, showing "+N more tokens with Pro" and navigating to `UpgradeScreen` on tap.
The infinite-scroll loading tile is suppressed whenever the upgrade banner is showing — pairing a
hard cutoff with a "still loading" spinner would have read as contradictory.

**3️⃣ Macro events lazy list** — switched to `ListView.separated`, but kept `_eventKeys` rather than
dropping it: it's genuinely load-bearing for `scrollToEventId` (deep-link from another screen) and
"scroll to closest future event" on open. Found and fixed a real regression this swap would
otherwise have introduced: `Scrollable.ensureVisible` on a `GlobalKey` silently no-ops for a target
outside `ListView.builder`'s built/cached range, which a distant event easily is. Fixed by
coarse-jumping to an estimated offset (`index * ~72px`) first, then letting `ensureVisible`
fine-tune once the target is actually built — see `_scrollToIndex`. Verified this wasn't
theoretical: `test/features/events/macro_events_scroll_test.dart`'s pre-existing "scrollToEventId
makes a distant event visible" test already exercised exactly this path (and was — separately —
already failing on `dev` before this PR, for an unrelated reason: its `_app()` test helper doesn't
pass `isProUser`, so the screen's own free-tier filter, 3 upcoming + 2 past, was stripping the
target event `f12` out of the list before scrolling logic ever ran. Fixed the test to pass
`isProUser: true`, restoring its actual intent). Also pruned `_eventKeys` on every
filter/country/reload change per the roadmap's fallback guidance, so it can't grow unbounded
across the screen's lifetime.

**4️⃣ Dead code** — removed as described; `_startFpsMonitor`'s companion `_stopFpsMonitor()` call
site (in `dispose()`) also had to go since a no-op-only stub with no call site would otherwise be
newly dead itself.

**5️⃣ Tests** — added both. The timeout test needed `package:fake_async` (already a transitive
dependency, already used bare — i.e. not listed in `pubspec.yaml`'s `dev_dependencies` — by
`test/core/auto_refresh_timer_test.dart`, so this follows existing precedent rather than
introducing a new one) driving a client whose `send()` never completes, confirming `fetchOverview`
throws `HttpOverviewApiException(statusCode: 0, ...)` specifically, not a raw `TimeoutException`.
The widget tests needed a minimal in-file `BillingManager`/`SubscriptionApi` fake (mirroring
`test/features/billing/upgrade_screen_test.dart`'s pattern) driven via `BillingManager`'s existing
`debugSetAccess` debug hook, plus `tester.scrollUntilVisible` for the >15-item case — the banner
tile is the 16th grid cell, below the fold in the default test viewport, so it isn't built until
scrolled to.

**Found and fixed while adding the widget tests, not originally in scope:** `OverviewWidgetState`
called `AppLifecycleScope.of(context)` fresh inside `dispose()` — unsafe, since by dispose time the
element may already be deactivated ("Looking up a deactivated widget's ancestor is unsafe").
`didChangeDependencies()` already correctly resolved it once; `dispose()` just needed to use that
cached reference instead of re-resolving. This wasn't a hypothetical: it was already causing 7
pre-existing failures in `overview_widget_test.dart` on `dev` before this PR (`OverviewScreen_
showsLoadingState`/`_rendersList`/`_handlesEmptySparkline`, all four `weak-signal banner` tests) —
fixing it was necessary to get my own new tests to pass reliably in the same file, and fixed those
7 as a side effect.

**Full validation:** `flutter analyze` — 104 issues before and after (project-wide baseline
unchanged; zero new issues in any of the 6 changed files, confirmed by diffing against a `dev`
baseline run). `flutter test` — full suite went from 8 pre-existing failures (all in files this PR
touches) down to 0, plus this PR's 6 new tests, with zero new failures anywhere else in the ~760
other tests. `.dart_tool`/`analysis_options.yaml`/`pubspec.lock` tooling churn discarded before
every commit.

📝 CR follow-up

**Major 1 (verified, no code change): `.timeout()` doesn't cancel the underlying socket.**
Re-confirmed against the actual auto-refresh wiring the finding asked about, rather than taking
the "polled on a timer" framing at face value. `AutoRefreshTimer` (`core/auto_refresh_timer.dart`)
explicitly serializes cycles — it only schedules the *next* tick after `await`ing the *current*
one, specifically to prevent overlapping refresh cycles (its own doc comment says so). So a
sustained string of 15s timeouts slows the refresh cadence (each cycle effectively becomes
timeout-duration-bound) but cannot pile up concurrent dangling requests the way true unawaited
polling would. Also confirmed the two aren't even coupled the way the finding implies: auto-refresh
only runs for pro users (`_maybeStartAutoRefresh`'s `if (!_isProUser ...) return;`), while the
free-tier cap this PR added is exactly the *other* tier. The abandoned-socket cost from a single
timeout remains real and already explicitly documented as an accepted tradeoff — this doesn't
change that, it just confirms the specific "auto-refresh timer" amplification concern doesn't
apply. No code change; the doc's existing acknowledgment stands.

**Major 2 (valid, fixed): pagination kept fetching data the free-tier cap would never show.**
Confirmed: `_checkAndLoadMore` read `vm.state.hasMore` directly, with no awareness of the local
`showUpgradeBanner` cap computed inside `build()`. Once the cap is active the grid's
`maxScrollExtent` is small (15 items + banner), so a free-tier user reaches "bottom" almost
immediately and `loadNext` kept firing for data that would only ever be truncated away. Mirrored
the cap into a new `_freeTierCapActive` field (set at the point `showUpgradeBanner` is computed in
`build()`) and gated `_checkAndLoadMore`'s `loadNext` call on it. Added
`free-tier user scrolling to the cap does not trigger pagination` (`overview_widget_test.dart`) —
a `_FakeGetOverview` with `hasMore: true` and a `pageCalls` spy, flung to the bottom of the grid;
confirmed the test fails without the fix (`pageCalls` picks up a page-2 call) and passes with it.

**Minor 1 (valid, fixed): `fake_async` wasn't declared in `pubspec.yaml`.** Added
`fake_async: ^1.3.3` to `dev_dependencies`, pinned to the version already resolved
(`pubspec.lock`). Deliberately did *not* run a full `flutter pub get` refresh to pick this up —
that re-resolved ~9 unrelated transitive packages to newer versions within their existing
constraints, which is unrelated churn for a one-line dependency declaration — instead hand-edited
`pubspec.lock`'s existing `fake_async` entry from `dependency: transitive` to `dependency: "direct
dev"`, an exact-equivalent, minimal-diff result.

**Minor 2 (verified unreachable, hardened anyway): tapping the banner with a null
`billingManager`.** Traced the actual invariant: `_UpgradeBannerTile` only builds when
`showUpgradeBanner` is true, which requires `!_capabilities.fullTokenList`, and
`Capabilities.fromBilling(null)` always returns `.pro()` (`fullTokenList: true`) — so a null
`billingManager` can never actually reach this branch today. Rather than build UI for a
structurally-unreachable state (which would itself be untestable dead code from a different
angle), replaced the silent `if (billing == null) return;` with an `assert` documenting the
invariant explicitly — so a future change that decouples the two would fail loudly in debug/test
builds instead of quietly turning this into a broken-looking button — while keeping the null-check
itself as a release-build safety net (asserts are stripped there).

**Minor 3 (assessed, no new test): `_scrollToIndex`'s coarse-jump math only indirectly
covered.** Traced all three call paths into it: `_scrollToEvent` already guards `index < 0` before
calling in; `_scrollToClosestFuture`'s two call sites are guarded by `futureIdx < 0` (for
`length - 1`, only reachable on a non-empty list) and `futureIdx > 0` (for `futureIdx - 1 >= 0`) —
so `_scrollToIndex` itself is never actually invoked with a negative index in practice, and the
clamp is a one-line `.clamp(0.0, maxScrollExtent)` already exercised (indirectly, via the 8
scroll/highlight tests covering distant/all-past/all-future/non-existent-id extremes) at every
value that matters. `!_scrollController.hasClients` is a defensive guard for a pre-attachment
timing window not realistically triggerable within this widget's lifecycle. `_scrollToIndex` is a
private method in a file `test/features/events/macro_events_scroll_test.dart` can't reach directly
(Dart privacy is per-library/file) — extracting the one-line clamp into a standalone testable
function purely to isolate it would be more code than the risk warrants. Left as indirectly
covered.
