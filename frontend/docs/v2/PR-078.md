## PR-078: fix(frontend): billing/trial hardening + gating consistency
🎯 Objective

Close the gaps found in the pro/trial gating sweep. None of these are exploitable today (every
current call site happens to pass the right value), but they're the kind of fail-open default
that turns into a real leak the next time someone adds a call site without noticing the pattern.

🧱 Scope

Frontend only (Dart/Flutter):
- `lib/features/notifications/notification_settings_page.dart` — fail-closed default
- `lib/bootstrap/main.dart` + `lib/features/billing/capabilities.dart` — fail-closed default
  for deep links when billing is unavailable
- `lib/features/billing/billing_manager.dart` — test coverage for the purchase flow
- `pubspec.yaml` — dependency hygiene

1️⃣ Fail-closed default on notification settings
```dart
// notification_settings_page.dart — before
this.isPro = true,

// after
this.isPro = false,
```
Every current call site (`overview_widget.dart:1140` — `caps.notificationsFull`) already
passes an explicit value, so this is a no-behavior-change safety fix, not a functional one.

2️⃣ Fail-closed deep links when billing is unavailable
```dart
// lib/bootstrap/main.dart — before
isProUser: billingManager?.hasFullAccess ?? true,

// after
isProUser: billingManager?.hasFullAccess ?? false,
```
```dart
// lib/features/billing/capabilities.dart — Capabilities.fromBilling — before
if (billing == null) return Capabilities.pro();

// after
if (billing == null) return Capabilities.free();
```
Currently dead code (billing is Android-only, no `ios/` directory exists in the repo yet), but
this is exactly the kind of default that silently unlocks everything for free the day iOS
support is added before billing is wired up there. Fix now while it's free (no behavior change
today), not later under time pressure.

3️⃣ Billing purchase-flow tests
`billing_manager.dart` has no dedicated test file — `purchase()`, `_onPurchaseUpdated`, and
`_verifyAndComplete` (the actual money-path orchestration) are untested today. Add:
- `TestPurchase_Success_UnlocksAfterServerVerification` — purchase completes only after
  `_verifyAndComplete` confirms server-side, not optimistically on the client purchase event
- `TestPurchase_ServerVerificationFails_DoesNotUnlock`
- `TestPurchase_Pending_ShowsPendingState`
- `TestPurchase_Canceled_ReturnsToFreeState`
- `TestRestorePurchases_ReappliesServerVerifiedState`

Use the existing `trial_manager_test.dart` / `http_subscription_api_test.dart` as the pattern
reference for mocking the HTTP layer.

4️⃣ Dependency hygiene
```yaml
# pubspec.yaml — before
environment:
  sdk: '>=2.18.0 <3.0.0'

# after
environment:
  sdk: '>=3.0.0 <4.0.0'
```
Bump after confirming no Dart-2-only syntax remains and `flutter pub get` / CI passes clean.
Separately, migrate off `flutter_markdown` (deprecated by the Flutter team) to the community
fork (`flutter_markdown_plus` or current recommended replacement — check pub.dev for the
currently-endorsed successor at implementation time) in `news_article_screen.dart` — small,
isolated change, low risk.

👉 Not included in this PR (tracked separately, needs product discussion): the 14-day trial is
entirely client-side (`SharedPreferences` install date vs device clock), trivially reset by
reinstall or clock manipulation. Fixing this properly needs either a server-anchored trial
start (tie to the device identity from backend PR-070 — note reinstall still mints a fresh
device identity today, so this alone doesn't fully close it either) or Play Integrity API
attestation. Worth a dedicated PR once PR-070 ships and the team decides how much trial-abuse
resistance is actually worth building for the current user volume.

🚀 Result

- No fail-open defaults left in the pro-gating surface — every "billing unknown" path now
  defaults to free, not pro.
- The one code path that actually moves money has test coverage.

📝 Implementation notes

Ran a verification pass against current code before implementing (this doc's "before" snippets
were mostly accurate but incomplete — see below).

**1️⃣ Fail-closed default.** `notification_settings_page.dart`'s `isPro = true` → `false`, exactly
as specified (sole call site — `overview_widget.dart:1145`, not 1140 as the doc said — already
passes an explicit value). Also fixed the identical pattern the doc's own audit missed:
`indicator_panel.dart`'s `showIndicatorPanel({..., bool isProUser = true, ...})` — same shape,
same "safe today" call-site profile (`detail_screen.dart` always passes an explicit value), same
risk this item is about.

**2️⃣ Fail-closed deep links — larger than the doc described.** `main.dart`'s
`billingManager?.hasFullAccess ?? true` appears **three times** (macro/setup/market screen
callbacks), not once — fixed all three. `capabilities.dart`'s actual condition is
`billing == null || billing.hasFullAccess` (one combined branch), not the doc's isolated
`if (billing == null) return .pro()` — fixed by flipping to
`billing != null && billing.hasFullAccess`. Also found and fixed the identical pattern in
`billing_manager.dart` itself: `hasFullAccess`'s own fallback,
`_trialManager?.isTrialActive() ?? true` — same "missing dependency defaults to full access"
shape, same dead-code-today safety profile (`TrialManager` is always constructed in the real
composition root, exactly like `BillingManager` itself), not mentioned in the doc's sweep.

Fixing `Capabilities.fromBilling(null)` to fail closed broke an invariant a comment in
`overview_widget.dart`'s upgrade-banner `onTap` explicitly relied on and asserted
("`Capabilities.fromBilling(null)` is always `.pro()`, so a null `billingManager` can never reach
this branch"). With the fix, a null `billingManager` now *can* reach that branch (free tier with
no way to launch a purchase flow). Replaced the assert with a plain graceful no-op — there's
nothing meaningful to do when tapping "upgrade" with no billing manager to launch
`UpgradeScreen` through.

Verified this wasn't just a theoretical concern before committing to it: `overview_widget_test.dart`
has 12 `OverviewWidget(...)` constructions, 8 of which omit `billingManager` entirely — meaning 8
existing tests were implicitly relying on the *old* `.pro()` default without saying so. Checked
each: all use ≤5 items (well under the 15-item free-tier cap threshold), so the capability flip
has no observable effect on any of them — confirmed by running the full suite, not just by this
reasoning. Deliberately left one fail-open spot alone: `overview_widget.dart:508`'s
`_requireAccess()` (a separate, older gating path for feature navigation) has the same
`billing == null → no gating` shape but is explicitly documented as intentional and is actively
relied on by tests that omit `billingManager` to reach pro-gated screens without mocking billing —
changing it needs its own audit of call sites and test impact, out of proportion to fold into this
sweep. Flagged separately for a follow-up decision.

**3️⃣ Billing purchase-flow tests — needed real test infrastructure, and found a hard platform
limit.** No fake `InAppPurchase`/`InAppPurchasePlatform` existed anywhere in this repo; the
existing `BillingManager` test pattern (`upgrade_screen_test.dart`) deliberately stubs out
`init()`/`purchase()`/`restorePurchases()` specifically to avoid touching `InAppPurchase` at all,
which can't exercise the private `_onPurchaseUpdated`/`_verifyAndComplete` money-path logic this
item is actually about. Built `_FakeIapPlatform extends InAppPurchasePlatform` (the real,
pluggable platform-interface layer `InAppPurchase` delegates to) with a controllable
`purchaseStream`, wired via `InAppPurchasePlatform.instance = fakePlatform` combined with
`debugDefaultTargetPlatformOverride = TargetPlatform.linux` — without the override, `flutter_test`
defaults `defaultTargetPlatform` to `android`, and `InAppPurchase.instance`'s first-ever access
unconditionally tries to register (and connect to) the real Android billing plugin, which crashes
outside an actual Android environment.

**Hard platform limit found, not worked around:** `BillingManager.purchase()`'s very first
non-product guard is `if (!Platform.isAndroid) return false;` — `dart:io`'s `Platform`, reading
the actual host OS, not the Flutter-level override above. This means the "launch a purchase"
happy path structurally cannot be exercised by `flutter test` on any non-Android host (this dev
machine included) — no test setup fixes this, since Dart's `Platform` has no test seam. Scoped the
suite accordingly: full coverage of `_onPurchaseUpdated`/`_verifyAndComplete` (reached via
`init()` + the fake stream, which has no platform gate) — success-unlocks-only-after-verification,
verification-failure-doesn't-unlock, restored purchases re-verify identically to fresh ones,
error/canceled/pending all handled correctly, `completePurchase` called only when
`pendingCompletePurchase` is set — plus `restorePurchases()` end-to-end (no platform gate either),
plus the two platform-independent `purchase()` guards (`_product == null`, and confirming the
Android check fires *before* `_busy` is set). Did **not** claim coverage of `purchase()`'s
IAP-launch happy path itself — documented in the test file's own module comment why that's a real
gap, not an oversight. Verified the suite actually catches regressions, not just passes trivially:
temporarily made `_verifyAndComplete` unlock unconditionally (ignoring the try/catch), confirmed
`TestPurchase_ServerVerificationFails_DoesNotUnlock` failed, reverted.

Added `in_app_purchase_platform_interface` as an explicit `dev_dependency` (pinned to the version
already resolved) rather than relying on it resolving transitively, matching the `fake_async`
precedent from PR-077.

**4️⃣ Dependency hygiene.** SDK bumped to `>=3.0.0 <4.0.0` (installed Dart 3.13.2 comfortably
inside it; no Dart-2-only syntax found in a sweep beforehand). `flutter_markdown` →
`flutter_markdown_plus` (confirmed via pub.dev as the actively-maintained continuation of the
same package, same maintainer statement — "the continuation of the original flutter_markdown
package... discontinued... Foresight Mobile has taken over maintenance"), a drop-in API swap
(same `MarkdownBody`/`MarkdownStyleSheet` classes) — only the import line in
`news_article_screen.dart` changed. Ran a real `flutter pub get` for this item specifically (not
a hand-edited lockfile) since it's an actual dependency swap, not just a declaration; the
resulting broader transitive version bumps are the legitimate, expected result of that, not
spurious churn to revert.

`news_article_screen.dart` had no widget test at all before this PR — added one to actually
verify the new package renders real markdown (heading/bold text as formatted output, not raw
`#`/`**` source), not just that the code compiles. Found and fixed a real, pre-existing,
unrelated bug while doing so: `dispose()` calls `viewModel.clearSelectedArticle()`, which
synchronously fires `onChanged` → `setState()` — but `dispose()` never cleared `onChanged` first,
so any *first* test to actually mount-then-unmount this screen would crash on
`'_lifecycleState != _ElementLifecycle.defunct'`. Confirmed by removing the fix and re-running:
the new test failed with exactly that assertion. Fixed by clearing `onChanged` before triggering
the state change, matching the pattern already used elsewhere in this codebase (e.g.
`MacroEventsScreenState.dispose()`).

**Full validation:** `flutter analyze` — 102 issues before and after (baseline unchanged; the one
new info-level suggestion from the new test file was fixed inline, not left as fresh debt).
`flutter test` — full suite: 36 pre-existing failures before and after, all in the same 4
`test/features/detail/*` files unrelated to this PR (confirmed identical failing-test list, not
just count, before and after). 12 new tests added across `billing_manager_test.dart` (11) and
`news_article_screen_test.dart` (1), all passing, each verified to actually fail without its
corresponding fix where a regression scenario was constructible. `.dart_tool`/
`analysis_options.yaml` tooling churn discarded before committing; `pubspec.lock` kept as
produced by the one real `pub get` this PR's dependency changes needed.

📝 CR follow-up

First CR round flagged the `_requireAccess()` deferral above (§2️⃣) as a real inconsistency, not an
acceptable out-of-scope gap: `Capabilities.fromBilling(null)` now fails closed, but
`overview_widget.dart:508`'s `_requireAccess()` — gating the Social Feed and Market Pulse menu rows
— still failed open (`billing == null || billing.hasFullAccess` → `true`), fully unlocking a paid
screen with no billing manager and no purchase prompt.

**Reassessed and fixed.** The "needs its own audit of call sites and test impact" reasoning that
justified deferring this turned out to be wrong: grepped the whole test suite and found **zero**
tests exercise this gating path at all (the 8 tests noted in §2️⃣ that omit `billingManager` only
touch the free-tier *capability* surface, not this separate navigation-gating helper) — so there
was no actual blast radius to audit. Fixed `_requireAccess()` to fail closed
(`billing != null && billing.hasFullAccess` → grant; `billing == null` → block navigation, same
graceful-no-op tradeoff already accepted for the upgrade-banner tap handler in §2️⃣, since
`UpgradeScreen` itself requires a non-null `billingManager`).

Added a real regression test (`overview_widget_test.dart`, `_requireAccess() fail-closed gating`
group) rather than trusting the existing suite's silence: gave `_NavBarIcon` a `Key?` constructor
param (previously key-less) and a stable `ValueKey('overview-menu-nav-icon')` on the menu icon so
the test can find and tap it from outside the widget, then asserts tapping a gated row with no
`billingManager` neither pushes `MarketPulseScreen`/`UpgradeScreen` nor leaves the overview screen.
Verified the test actually catches the regression, not just that it passes: temporarily reverted
`_requireAccess()` to the old fail-open logic and reran — failed (via a `pumpAndSettle` timeout,
since the wrongly-reached `MarketPulseScreen` hits fake APIs designed to `fail()` if ever called);
restored the fix and confirmed green again.

Also closed the two direct-assertion gaps the CR flagged:
- `capabilities_test.dart` (new file): `Capabilities.fromBilling(null)` asserted directly against
  every capability field, plus explicit pro/free cases via a real `BillingManager` +
  `debugSetAccess`. Previously this invariant was only covered indirectly through
  `overview_widget_test.dart`'s incidental low-item-count tests.
- `billing_manager_test.dart`: new `hasFullAccess` group asserting the fail-closed default
  directly (no subscription, no trial → `false`), plus `status.active` override, active
  `TrialManager`, and expired `TrialManager` cases — previously only exercised transitively through
  `purchase()`/`_verifyAndComplete` tests.

Minor concern addressed: `news_article_screen_test.dart` now explicitly drives `dispose()`
(`tester.pumpWidget(const SizedBox.shrink())`) instead of relying on the test framework's own
end-of-test teardown, plus `tester.takeException()` to lock in a clean unmount — this is what
actually exercises the `dispose()` fix from §4️⃣ above, not just the mount/render path.

Stale comment at `overview_widget.dart:507` (understated real-world scope) rewritten as part of the
fix itself — see the updated docstring on `_requireAccess()`.

**Dependency/SDK changes called out explicitly per CR suggestion:** the SDK floor bump to
`>=3.0.0 <4.0.0` and the `flutter_markdown` → `flutter_markdown_plus` migration (§4️⃣ above) are
real, intentional dependency changes in this PR, not incidental lockfile churn — flagging here
again since the CR asked for this to be surfaces prominently rather than left buried in
implementation notes.
