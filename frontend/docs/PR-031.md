# PR-031: Lightweight News Feed via Markdown Files (Filesystem-Based CMS)

## 1. Objective

Introduce a simple, maintainable news/update feed system using Markdown (`.md`) files stored on the server filesystem.

Purpose:

* Announce feature updates (e.g., new 1W timeframe)
* Communicate roadmap items and ETAs
* Reduce support friction from Play Store feedback
* Provide lightweight transparency layer

This is not a full editorial/news platform — only structured product updates and contextual notes.

---

## 2. Design Principles

* No database
* No CMS panel
* No migrations
* Git-versioned content
* Minimal backend logic
* Easy to write and deploy

The system must remain low-maintenance and high-leverage.

---

## 3. Directory Structure

```plaintext
/news/
  2026-03-05-add-1w-timeframe.md
  2026-03-02-fear-greed-index-added.md
  2026-02-28-forward-event-projection.md
```

Naming convention:

```
YYYY-MM-DD-slug.md
```

Date prefix ensures natural sorting.

---

## 4. File Format Specification

Each file must contain YAML frontmatter + Markdown body.

Example:

```markdown
---
title: 1W Timeframe Coming Soon
date: 2026-03-05
status: planned
eta: 2026-03-20
tags: feature, timeframe
---

We've received multiple requests for a 1-week timeframe.

Implementation is scheduled and expected by March 20.

Thanks for the feedback — keep it coming.
```

---

## 5. Frontmatter Schema

Required fields:

* `title` (string)
* `date` (ISO format)
* `status` (enum: planned | released | info)
* `tags` (array of strings)

Optional fields:

* `eta` (ISO date)
* `related_asset` (e.g., BTCUSDT)
* `priority` (low | normal | high)

Validation should be tolerant — missing optional fields must not break parsing.

---

## 6. Backend Implementation

### 6.1 Endpoint

```
GET /api/news?limit=10
GET /api/news/{slug}
```

### 6.2 Processing Flow

1. Read `/news` directory
2. Parse filenames
3. Extract frontmatter
4. Convert Markdown body to HTML
5. Sort by date descending
6. Apply optional limit
7. Return JSON

---

## 7. API Response Format

### 7.1 List Response

```json
[
  {
    "slug": "add-1w-timeframe",
    "title": "1W Timeframe Coming Soon",
    "date": "2026-03-05",
    "status": "planned",
    "eta": "2026-03-20",
    "excerpt": "We've received multiple requests..."
  }
]
```

### 7.2 Single Article Response

```json
{
  "slug": "add-1w-timeframe",
  "title": "1W Timeframe Coming Soon",
  "date": "2026-03-05",
  "status": "planned",
  "eta": "2026-03-20",
  "tags": ["feature", "timeframe"],
  "html": "<p>We've received multiple requests...</p>"
}
```

---

## 8. Frontend Behavior

### 8.1 News List View

* Simple vertical list
* Title
* Date
* Optional status badge:

  * Planned → subtle yellow
  * Released → green
  * Info → neutral

### 8.2 Article View

* Render sanitized HTML
* Show ETA if present
* No comments
* No reactions
* No heavy interaction

Keep it calm and informational.

---

## 9. Caching Strategy

* Cache parsed file list in memory
* Refresh on server restart OR
* Optional: auto-refresh every 5–10 minutes

No database persistence required.

---

## 10. Security Considerations

* Sanitize Markdown → HTML output
* Prevent script injection
* Disallow raw HTML blocks if not required

Content is trusted (written by you), but sanitation is still recommended.

---

## 11. Performance Expectations

* < 500 files supported without issue
* Filesystem read cost negligible
* No pagination required initially
* Limit default to 20 entries

---

## 12. Deployment Workflow

1. Add new `.md` file
2. Commit to repository
3. Deploy
4. Feed updates automatically

No admin UI required.

---

## 13. Strategic Rationale

This system:

* Keeps users informed
* Reduces support noise
* Signals active development
* Adds perceived product maturity

It avoids:

* Database complexity
* CMS overhead
* Feature creep

It aligns with the app’s philosophy:

Structured. Minimal. Intentional.
